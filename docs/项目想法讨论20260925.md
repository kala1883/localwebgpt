可以做。针对你的目标，我建议采用：

> **ChatGPT 原生 MCP 插件＋运行在你电脑上的本地工作区服务。**
> 你继续使用 ChatGPT 网页聊天，ChatGPT 通过工具调用读取、搜索和修改你授权的本地文件，而不是依靠复制粘贴，也不需要先把仓库推送到 GitHub。

目前官方开发者文档已经支持在 ChatGPT 网页端接入具有读写能力的 MCP 工具，并提供了连接私有、本机 MCP 服务的 Secure MCP Tunnel。**所以不必先走“浏览器扩展抓取对话、解析回答、模拟点击”的路线。**([OpenAI Platform][1])

先说明一下：你给出的分享链接，我只读取到了《Gitee插件技术路线》的标题，没有取得完整对话正文。因此下面是基于你这次明确的目标和我核对到的官方接入方式设计的方案，不会假装已经逐条阅读了链接里的讨论。

## 一、这个插件应该是什么样的

我建议暂时叫它 **Local Workspace Bridge，本地工作区桥接插件**。

从使用体验看，你在电脑上安装一个小程序，选择允许访问的目录，然后在 ChatGPT 网页端连接这个插件。

以你的项目为例，可以在本地授权：

```text
工作区名称：TransportAndAI
实际目录：D:\MyProjects\MyApps\transportandai

允许：
  查看目录
  搜索内容
  读取文件
  查看 Git 状态与差异
  提议修改
  经确认后写入

默认禁止：
  读取密钥和环境变量文件
  访问工作区以外的目录
  任意执行终端命令
  自动提交或推送 Git
```

之后，你就可以在 ChatGPT 网页里直接说：

> 读取本地 TransportAndAI 仓库，分析 myagent 和 aigroup 的对象关系，先不要修改。

或者：

> 按刚才的方案修改这三个文件，先展示完整差异，我确认后再保存。

或者：

> 把这份设计方案保存到项目的 docs 目录，不要覆盖已有文件。

**这里操作的应该是你硬盘上当前的文件，包括已保存但未提交的修改，而不是远程仓库中的某个旧版本。**

不过，编辑器里**尚未保存到磁盘的内容**，普通文件服务读不到。首版应明确提示这一点；后续需要读取 VS Code 的未保存缓冲区时，再增加专门的编辑器集成。

## 二、推荐架构：原生工具接入，不接管 ChatGPT 网页

### 1. 总体结构

```text
你在 ChatGPT 网页中提出要求
              │
              ▼
ChatGPT 调用插件提供的 MCP 工具
              │
              ▼
OpenAI Secure MCP Tunnel
              │
       本机主动建立出站连接
              │
              ▼
你的电脑：tunnel-client
              │
              ▼
你的电脑：Local Workspace Service
    ┌────────────────────────────┐
    │ 身份与工作区授权             │
    │ 目录、文件和搜索             │
    │ Git 只读查询                │
    │ 修改预览与审批               │
    │ 写入、冲突检查与恢复          │
    │ 操作记录                    │
    └────────────────────────────┘
              │
              ▼
       已授权的本地目录
```

官方安全隧道的工作方式，是由本地 `tunnel-client` 主动连接 OpenAI、取得 MCP 请求、转交给本地 MCP 服务并返回结果。因此，本地文件服务不需要直接暴露在公网，也不需要开放公网入站端口。([OpenAI Developers][2])

**本地服务负责执行和守住权限边界，ChatGPT 负责理解需求、分析代码和提出修改。不要把权限判断交给模型。**

### 2. 三个部分分别做什么

| 部分           | 职责                                             | 不应该承担的职责                    |
| -------------- | ------------------------------------------------ | ----------------------------------- |
| ChatGPT 插件   | 告诉 ChatGPT 有哪些工具、如何使用、怎样展示结果  | 不能仅靠提示词决定文件访问权限      |
| 本地工作区服务 | 读文件、搜索、构造差异、校验权限、审批和落盘     | 不需要重新实现一套大模型对话系统    |
| 本地管理界面   | 选择目录、设置权限、查看修改、批准写入、断开连接 | 不需要读取你的全部 ChatGPT 聊天记录 |

插件可以包含 MCP 工具、Skill 和可选界面，但**真正赋予文件操作能力的是 MCP 服务，不是单独一份 `SKILL.md`**。首版可以先通过开发者模式接入 MCP 服务，之后再做完整插件封装。([OpenAI Developers][3])

### 3. 为什么不优先做 Chrome 扩展

我不建议把核心执行链路设计成：

```text
读取 ChatGPT 回答
→ 从回答中寻找某种 JSON 或代码块
→ 判断它是不是操作指令
→ 修改本地文件
→ 自动把执行结果发回聊天框
```

这样你需要自己维护“回答和指令的区分、重复执行防护、对话归属、页面变化适配”等问题。

原生 MCP 方案中，ChatGPT 调用的是有明确名称、参数结构和返回结果的工具，官方也提供了相应的工具发现、刷新和确认机制。用这条路径更符合你的目标。([OpenAI Developers][4])

浏览器扩展可以以后作为便利功能，例如显示连接状态、快速选择工作区；**不要让它成为判断是否允许写文件的唯一控制点。**

## 三、先验证接入权限，再开发完整功能

这里有一个需要明确的现实问题：**“平台支持”不等于“你的账号当前已经开放所有入口”。**

截至我这次核对，官方开发者指南写明网页端开发者模式支持 Plus、Pro 等账号以及读写工具；但另一篇帮助中心文章仍保留了“Pro 仅限读取、完整写入限部分组织套餐”的表述，两处资料并不完全一致。不能只凭其中一句话，就保证你的账号现在一定能使用全部功能。([OpenAI Platform][1])

所以，开发的第一个验收点应该非常小：

**在你的真实 ChatGPT 网页账号上，完成一次测试目录内的读取和经确认的写入。**

官方当前给出的接入入口是：开启 Settings → Security and login → Developer mode，然后在 Plugins 中新增 MCP 连接，选择公网 HTTPS 端点或 Tunnel。具体界面仍以账号实际显示为准。([OpenAI Developers][5])

另外，安全隧道还需要单独核实：

* 是否能创建、使用 `tunnel_id`。
* 隧道是否关联到正确的 ChatGPT 工作区。
* 是否具备运行 `tunnel-client` 的权限和运行时 API key。

**ChatGPT 开发者模式权限与 Platform 隧道权限是两套权限，不能混为一谈。**([OpenAI Developers][2])

接入路线建议这样安排：

| 场景                                 | 推荐路线                                            |
| ------------------------------------ | --------------------------------------------------- |
| 你个人自用，能使用安全隧道           | **本地 MCP 服务＋Secure MCP Tunnel**          |
| 无法使用安全隧道，但能接入自定义 MCP | 经过身份认证的公网 HTTPS MCP 入口，再安全转发到本地 |
| 将来公开上架，供其他人使用           | 稳定公网 MCP 服务＋用户认证＋设备配对＋本地客户端   |

官方明确区分了私有隧道与公开插件发布：**Secure MCP Tunnel 可用于私有连接和开发测试，但不能单独满足公开插件上架要求。**([OpenAI Developers][6])

你现在是先给自己用，因此不需要一开始就做多用户云平台。

## 四、工具设计：不只提供一个危险的 `write_file`

我建议首版提供下面这些工具。工具名称是建议设计，不是目前已经存在、可以直接调用的接口。

| 工具               | 作用                       | 关键限制                                |
| ------------------ | -------------------------- | --------------------------------------- |
| `workspace_list` | 列出已授权工作区及能力     | 不枚举整个硬盘                          |
| `file_list`      | 查看目录和文件             | 有深度、条数和分页限制                  |
| `text_search`    | 按内容搜索代码和文档       | 返回文件、行号、片段，遵守敏感文件策略  |
| `file_read`      | 按行或范围读取文件         | 返回版本哈希、编码和截断信息            |
| `git_inspect`    | 查看状态、差异、提交记录   | 只允许固定查询类型，不接受任意 Git 命令 |
| `change_prepare` | 生成不可变的待审修改集     | 不修改目标文件                          |
| `change_get`     | 查询修改集、差异和执行状态 | 不把超时直接当成失败                    |
| `change_apply`   | 应用已经获得授权的修改集   | 必须校验授权、版本和幂等状态            |
| `change_revert`  | 撤销某次插件修改           | 不能覆盖之后产生的新修改                |

### 1. 路径由本地授权决定

不要让模型直接传入任意系统路径：

```json
{
  "path": "C:\\Users\\某用户\\任意文件"
}
```

建议采用：

```json
{
  "workspace_id": "transportandai",
  "path": "apps/myagent/models.py",
  "start_line": 1,
  "end_line": 160
}
```

其中，`workspace_id` 对应的真实根目录只能由你在本机配置。

模型可以选择已经授权的工作区，但不能通过参数注册一个新根目录，或者临时把读取权限升级成写入权限。

### 2. 读取结果必须携带版本信息

建议返回：

```json
{
  "workspace_id": "transportandai",
  "path": "apps/myagent/models.py",
  "sha256": "<整个文件原始字节的哈希>",
  "encoding": "utf-8",
  "newline": "crlf",
  "start_line": 1,
  "end_line": 160,
  "truncated": false,
  "content": "..."
}
```

这样后续修改可以表达为：

> 我基于这个版本提出修改；文件已经发生变化时，不允许直接覆盖。

搜索结果、Git 差异和历史版本读取也应该执行同一套访问控制，避免“禁止直接读取 `.env`，却可以通过搜索或 Git 历史读出来”的旁路。

### 3. 不要把任何“只读”标签当作权限机制

官方要求工具准确声明 `readOnlyHint` 等属性，同时明确指出：**这些标签不能替代服务端的身份验证、授权和确认。**([OpenAI Developers][4])

例如，`change_prepare` 虽然不改源码，但会保存修改集，本身也会改变服务状态，不能为了减少确认弹窗而随意标成完全只读。

## 五、编辑的核心：修改集、批准、版本检查、可恢复

**把文件写进去很容易；不误改、不重复改、不覆盖你自己的修改，才是这个插件真正需要解决的部分。**

### 1. 修改分成“提出”和“应用”

建议流程：

```text
读取文件
  ↓
ChatGPT 提出修改
  ↓
本地服务生成修改集和完整差异
  ↓
你审核并批准
  ↓
本地服务重新校验权限和原文件版本
  ↓
应用修改
  ↓
返回实际写入结果、文件新版本和操作编号
```

`change_prepare` 应把修改内容固定下来，生成 `change_id` 和修改集摘要。

你批准的是：

> 对指定工作区、指定文件，执行这份确定的修改。

而不是：

> 给模型一个可以随意改文件的通行证。

因此，**不能把模型传来的 `approved: true` 当成人类批准。** 首版建议采用本地管理界面的明确批准记录；后续接入其他审批界面时，也要把批准结果绑定到同一份修改集。

### 2. 你在 VS Code 里改过，插件必须发现

例如：

```text
ChatGPT 读取版本 A
你在 VS Code 保存为版本 B
ChatGPT 尝试按 A 应用修改
```

此时应返回明确冲突：

```text
FILE_VERSION_CONFLICT
文件在读取后发生变化，本次修改未应用。
```

然后重新读取、重新生成差异，而不是自动整文件覆盖，也不要使用可能改错位置的模糊匹配强行成功。

这里还需要注意：**本地服务自己的锁只能约束本服务，不能天然阻止其他编辑器同时写入。** 实现时必须验证 Windows 上的并发写入行为；不能把“检查一次哈希＋改名替换”宣传为能完全解决所有外部并发。

严格模式可以把修改先放入隔离副本，再由用户合并。隔离副本要包含当前已保存但未提交的变更，不能简单从 Git 的 `HEAD` 创建后就当成当前工作区。

### 3. 网络超时不能导致重复修改

可能出现：

```text
本地已经写入成功
  ↓
返回结果途中断网
  ↓
ChatGPT 不知道是否成功
```

建议每个应用操作都具有持久化的操作编号和幂等键。重新查询时返回已有执行结果，而不是再次追加内容、再次重命名或再次删除。

### 4. 多文件修改要能恢复，不要虚称“事务”

多个文件的逐个替换，不能直接当作数据库事务。

建议实现执行日志，记录每个文件的旧版本、新版本和应用状态。中途断电或进程崩溃后，能够识别哪些已完成、哪些未完成，进入恢复流程。

撤销时也需要检查当前文件是否仍等于插件写入后的版本。你已经继续修改过，就应报告冲突，不能直接恢复旧备份，更不能调用 `git reset --hard` 来实现所谓“一键撤销”。

## 六、权限和隐私：本地服务不公开，不代表源码不出本机

这一点与你之前强调的源码隐私要求直接相关。

**可以做到不上传整个仓库、不做云端全量索引；但 ChatGPT 要分析某段源码，那段工具返回的源码就必须发送给 ChatGPT。** 本地 MCP 和安全隧道改变的是获取方式，不是把云端模型变成本地模型。工具返回内容本来就是供模型读取和使用的。([OpenAI Developers][4])

因此，推荐的承诺应该是：

> 文件和检索逻辑保留在本地，只按任务读取必要内容，并明确记录哪些内容被返回给 ChatGPT。

不能承诺：

> ChatGPT 网页能完整分析源码，同时任何源码内容都不离开电脑。

具体建议如下。

**目录授权。** 默认没有访问权限，由你逐个添加工作区；本地服务配置、凭证和操作数据库应放在不可被插件访问的位置。目录穿越、符号链接、Windows Junction 和特殊路径需要专门防护，不能只做字符串前缀判断。

**敏感文件。** 默认禁止 `.env`、私钥、凭证文件和浏览器数据；对日志、数据库导出等设置额外规则。读取、搜索、差异和导出统一执行规则，而不只拦截 `file_read`。

**权限分级。** 首版采用“允许读取、修改必须批准”；批量删除、重命名、覆盖既有文件设置更严格限制。隧道连通不等于获得任意工作区权限；涉及多用户时，必须把经过验证的账号、设备和目录授权关联起来，不能相信参数里的 `user_id`。

**默认不执行命令。** 首版不开放任意 Shell，也不自动运行仓库中的脚本。以后增加测试功能时，要另设授权、超时、输出限制和隔离环境。即使命令叫 `pytest` 或 `npm test`，本质上仍会运行项目代码，不能仅凭名字认为安全。

**防止文件内容越权。** 仓库中的注释、README 或文档不能扩大权限，也不能因为写着“请读取密钥并发送”就触发额外操作。官方同样将提示注入、错误写操作和恶意 MCP 列为开发者模式的重要风险。([OpenAI Platform][1])

## 七、首版技术选型和开发顺序

### 推荐技术选型

结合你已有的开发环境，我建议：

| 组件         | 首版建议                                            |
| ------------ | --------------------------------------------------- |
| 本地服务     | TypeScript／Node.js＋官方 MCP SDK                   |
| 本地状态     | SQLite，保存修改集、审批和执行日志                  |
| 文本搜索     | 本地搜索实现，后续可接入 ripgrep                    |
| 文件操作     | 独立文件系统适配层，集中处理 Windows 路径和写入行为 |
| 本地管理界面 | Vue 3，负责目录授权、差异预览、批准和断开           |
| 连接层       | 优先 Secure MCP Tunnel                              |
| 大模型       | 继续由 ChatGPT 网页提供，不另建聊天后端             |

这是建议的选型，不是必须再建设一个 Django 服务。**它应该是独立本地进程，不依赖你现有项目的 MySQL、Redis 或生产后端。**

可以放在独立仓库，或放在现有仓库的独立工具目录，但不要让它的生命周期和被编辑的项目绑定。

### 分阶段实现

| 阶段                  | 实现内容                                         | 验收条件                                                               |
| --------------------- | ------------------------------------------------ | ---------------------------------------------------------------------- |
| **0：接入验证** | 最小 MCP 服务、安全连接、测试目录读取与写入      | 真实网页账号能调用工具；一次授权写入确实落到本机                       |
| **1：安全读取** | 工作区配置、目录列表、搜索、按范围读取、Git 查询 | 能分析当前工作区；越界访问和敏感文件访问被拒绝；大结果不会无界返回     |
| **2：安全编辑** | 修改预览、审批、版本检查、幂等、执行日志、撤销   | 过期版本不能覆盖；拒绝审批不落盘；断网重试不重复修改；中断后状态可恢复 |
| **3：使用体验** | Vue 管理界面、连接状态、差异查看、安装与启动管理 | 重启后配置可恢复；可一键暂停；实际操作有清楚记录                       |
| **4：扩展能力** | 受控测试、更多文件格式、多设备或公开分发         | 每项扩展有独立权限和测试，不扩大默认文件访问范围                       |

**首版文件范围建议先限定为代码和文本文件**，例如 Python、JavaScript、TypeScript、Vue、Markdown、JSON、YAML、TXT。

Word、Excel、PDF 不应该直接套用文本替换工具。后续再增加对应格式的读取和编辑适配器，避免把“可以读写字节”误当作“可以正确编辑文档结构和格式”。

编码也需要明确：首版可以先支持 UTF-8、保留原有 BOM 和换行方式；不认识的编码拒绝自动覆盖，不能悄悄转码导致整文件变化。

## 八、我对这个项目的最终建议

**值得做，而且你的目标不需要先演变成一个庞大的 Agent 平台。**

我建议把 V1 严格收敛为：

> **一个面向 Windows 本地工作区的 ChatGPT MCP 插件：支持授权目录内的检索、读取、Git 状态查看，以及经过差异预览和确认的代码、文本修改。**

暂时不做浏览器自动操作、不做任意终端执行、不做自动 Git 推送，也不做多用户云平台。

还有两个边界需要留在项目说明里：本方案不需要你另外实现模型 API 调用，但官方安全隧道自身要求运行时 API key，不能宣传成“完全不需要 API key”；本地程序不在线时，工具调用也不能执行。([OpenAI Developers][2])

**真正的第一步，是用你当前的 ChatGPT 网页账号，打通“读取一个测试文件 → 生成修改 → 确认 → 写回本机 → 再次读取验证”这一条完整链路。这条链路验收通过后，再接入 TransportAndAI 的真实目录。**

## 一、先明确产品范围

## 1.1 首版要完成什么

| 能力             | 首版设计                                   |
| ---------------- | ------------------------------------------ |
| 授权本地目录     | 用户在本地控制台添加一个或多个工作区       |
| 授权单个文件     | 只开放指定文件，不顺带开放整个父目录       |
| 查看目录         | 分页查看目录和文件，限制深度、条数         |
| 搜索代码和文本   | 本地搜索，返回路径、行号、片段             |
| 读取文件         | 读取硬盘上已经保存的内容，附带文件版本     |
| 查看 Git 状态    | 区分 HEAD、暂存区、工作区，不修改 Git 状态 |
| 查看代码差异     | 按授权文件查看差异，不提供任意 Git 命令    |
| 修改既有文件     | 生成修改集、展示差异、批准后应用           |
| 新建文本文件     | 在已有父目录中创建，禁止覆盖既有目标       |
| 查询执行结果     | 获得实际写入状态、文件哈希、操作编号       |
| 撤销既有文件修改 | 生成新的逆向修改集，再次批准，检查后续修改 |
| 暂停连接         | 停止新访问和新写入，妥善处理正在执行的操作 |

例如，你可以在 ChatGPT 中提出：

> 读取本地 TransportAndAI 的 myagent 和 aigroup，分析对象关系，先不要修改。

或者：

> 按刚才的结论修改相关文件，先展示差异，我批准后保存。

或者：

> 把这份方案保存到 docs 目录中，不要覆盖已有文件。

**这些操作针对本地已保存的文件，包括尚未提交 Git 的修改，而不是远端仓库副本。**

## 1.2 不混入首版的功能

首版不提供任意 Shell、自动安装依赖、自动 Git 提交或推送，也不直接编辑 Word、Excel、PDF 等结构化或二进制文件。

另外，**编辑器中尚未保存的缓冲区，不等于硬盘文件**。首版只处理硬盘版本。VS Code 未保存内容需要后续专用扩展接入，不能通过普通文件读取冒充已经支持。

目录创建、重命名和删除放入 V1.1，作为独立的、显式批准的操作；不为了保存一个文件而悄悄创建目录，也不在发生冲突时自动覆盖、移动或删除目标。

## 二、接入路线与总体架构

## 2.1 平台能力必须设置实测门禁

官方文档已经描述了 ChatGPT 原生读写 MCP 接入和 Secure MCP Tunnel 私有连接。但开发者指南与帮助中心对 Pro 账号写入范围的描述仍有不一致，因此不能把“文档存在这项能力”直接当作“你的账号已经开放”。**第一阶段必须用你的真实网页账号完成一次测试目录内的读取、批准写入和回读。**([OpenAI Platform][1])

安全隧道需要 `tunnel_id`、运行时 API key 和相应权限；它与 ChatGPT 开发者模式权限是不同事项。本地 `tunnel-client` 主动建立出站连接，将请求转发给本地 stdio 或 HTTP MCP 服务。([OpenAI Developers][2])

因此，首版采用：

```text
ChatGPT 网页
    │
    │ 原生 MCP 工具调用
    ▼
OpenAI 私有隧道
    │
    │ 本机主动建立出站连接
    ▼
tunnel-client
    │
    │ stdio
    ▼
MCP Adapter
    │
    │ 经过认证的本地 IPC
    ▼
Local Daemon
    ├── 工作区与权限管理
    ├── 文件读取、目录、搜索
    ├── Git 只读查询
    ├── 修改集与审批
    ├── 写入协调与幂等
    ├── 操作记录与恢复
    │
    ├────────────── 本地 Vue 控制台
    │                 授权、差异、批准、暂停
    ▼
Windows 文件系统保护层
    │
    ▼
用户明确授权的本地目录
```

**本地控制台和模型工具入口必须分开。** 模型可以提出修改，但不能批准修改、添加新目录或调整自己的权限。

## 2.2 组件与技术选择

| 组件               | 建议实现                       | 主要职责                                 |
| ------------------ | ------------------------------ | ---------------------------------------- |
| MCP Adapter        | TypeScript＋官方 MCP SDK       | 工具定义、参数校验、协议、返回结果       |
| Local Daemon       | TypeScript／Node.js            | 工作区、权限、修改集、状态和执行调度     |
| 本地控制台         | Vue 3                          | 添加目录、查看差异、批准、恢复、暂停     |
| 状态库             | SQLite                         | 审批、修改集、幂等、操作状态与执行日志   |
| 快照存储           | 本地受保护的文件目录           | 保存批准修改所需的原始和目标字节         |
| Windows 文件系统层 | 小型 Rust／Win32 辅助模块      | 路径验证、文件身份、独占句柄、写入和刷盘 |
| Git Reader         | 只读文件系统适配层＋Git 读取库 | 查看状态和差异，不执行自由命令           |

这里不需要 Django、MySQL、Redis、Celery，也不需要重新做一套 Agent 对话系统。

**主业务仍然是 TypeScript。引入薄原生层，是为了 Windows 路径与并发写入保护，而不是再造一个复杂后端。**

## 2.3 为什么本机优先使用 stdio

隧道到本地 MCP Adapter 采用 stdio，可避免再开放一个能够直接读取文件的本地 HTTP 端口。

本地 Vue 控制台仍需要控制 API，但它只负责管理，使用独立认证，且不能被 MCP 转发访问。

后续增加 HTTP MCP 兼容模式时，必须校验 Origin、绑定回环地址并实施认证。MCP 规范明确要求考虑本地服务的 DNS rebinding 等风险。([Model Context Protocol][3])

## 三、核心对象与数据模型

建议围绕以下关系设计，不要把授权、会话、修改和执行结果混在一起：

```text
Connection
    │
    └── Grant ── Workspace
                     │
                     └── ChangeSet
                              ├── ChangeItem ── 原始/目标快照
                              ├── Approval
                              └── Operation
                                      └── JournalEntry
```

## 3.1 主要实体

| 实体                  | 作用                     | 关键字段或约束                             |
| --------------------- | ------------------------ | ------------------------------------------ |
| `Connection`        | 一个经过验证的接入主体   | 连接 ID、启用状态、凭据引用、代次          |
| `Workspace`         | 用户授权的目录或文件     | 根路径、卷身份、根文件身份、权限模式、代次 |
| `Grant`             | 连接对工作区的权限       | 读取、搜索、提议、应用等能力               |
| `ChangeSet`         | 一份不可变的修改计划     | 工作区、所有者、摘要、策略版本、状态、期限 |
| `ChangeItem`        | 单个文件的确定修改       | 路径、原文件身份和哈希、目标哈希、快照     |
| `Approval`          | 本地操作者的批准事实     | 修改集摘要、批准人、期限、一次性状态       |
| `Operation`         | 实际执行的一次操作       | 唯一操作 ID、执行状态、结果                |
| `JournalEntry`      | 执行过程中的持久化检查点 | 操作、文件、阶段、观察结果、错误           |
| `Blob`              | 原始与目标内容快照       | 哈希、大小、存储位置、引用与保留状态       |
| `IdempotencyRecord` | 重试去重依据             | 主体、工具、幂等键、请求哈希、结果引用     |
| `AuditEvent`        | 访问与管理记录           | 主体、工具、工作区、返回范围、结果码       |

## 3.2 必须建立的数据库约束

最重要的是：

```text
UNIQUE(change_id)                    —— 一个修改集最多一个应用操作
UNIQUE(principal_id, tool, key)      —— 同一业务请求不能重复创建
```

同一个幂等键携带不同内容，返回 `IDEMPOTENCY_CONFLICT`，不能覆盖旧记录。

同一个修改集即使换一个幂等键再次调用，也只能返回原来的操作，不能再次执行。

**SQLite 管理的是状态与执行事实，不会让用户目录中的多个文件自动获得数据库事务语义。** 文件操作必须另做日志和恢复。([SQLite][4])

## 四、MCP 工具接口设计

首版建议提供 12 个工具，避免一个万能 `execute` 接口承担所有能力。

| 工具                      | 用途                      | 是否改变状态       |
| ------------------------- | ------------------------- | ------------------ |
| `bridge_status`         | 查询连接、版本和可用能力  | 否                 |
| `workspace_list`        | 列出当前连接获准的工作区  | 否                 |
| `file_list`             | 分页查看目录              | 否                 |
| `text_search`           | 搜索代码和文本            | 否                 |
| `file_read`             | 按范围读取文件            | 否                 |
| `git_status`            | 查看授权范围内的 Git 状态 | 否                 |
| `git_diff`              | 查看授权文件的差异        | 否                 |
| `change_prepare`        | 生成不可变修改集          | 是，但不改用户文件 |
| `change_get`            | 查询修改集或操作结果      | 否                 |
| `change_list`           | 查询当前连接的修改历史    | 否                 |
| `change_apply`          | 应用已获本地批准的修改集  | 是                 |
| `change_revert_prepare` | 生成逆向修改集            | 是，但不直接恢复   |

`change_prepare` 会创建持久化修改集，不能为了减少确认而标成只读。工具的 `readOnlyHint` 等标记只帮助客户端理解行为，**不能替代服务端鉴权、参数校验和确认机制**。([OpenAI Developers][5])

## 4.1 路径只能使用工作区内相对路径

允许：

```json
{
  "workspace_id": "ws_transportandai",
  "path": "apps/myagent/example.py",
  "start_line": 1,
  "max_lines": 120
}
```

不允许模型直接传入任意系统绝对路径，也不允许模型通过工具注册新的根目录。

上面的文件名仅为协议示例，不表示已经读取过该文件。

## 4.2 读取结果必须附带版本与范围

建议至少返回：

```text
path
source = disk
sha256                     整个文件原始字节的哈希
encoding / bom / newline
实际返回的行范围
truncated
next_cursor
read_token
consistency = per_file
```

`read_token` 是服务端签发的读取凭证，绑定：

```text
连接身份
工作区及代次
规范路径
文件身份
整个文件哈希
实际返回的范围
有效期
```

它证明后续修改基于哪个版本、哪些已返回内容，**但不代表人类批准**。

逐文件读取也不意味着整个仓库是同一时刻的全局快照。搜索和读取结果应明确自己的范围，不能因为读取了几个文件就宣称已完整检查全仓。

## 4.3 修改使用精确区间，不使用模糊替换

建议修改请求采用：

```json
{
  "workspace_id": "ws_transportandai",
  "idempotency_key": "unique-prepare-key",
  "summary": "调整请求超时常量",
  "items": [
    {
      "op": "edit_text",
      "path": "apps/myagent/example.py",
      "base_sha256": "<原始文件字节哈希>",
      "read_token": "<服务端签发的读取凭证>",
      "edits": [
        {
          "start_line": 12,
          "end_line_exclusive": 13,
          "old_lines": ["REQUEST_TIMEOUT = 10"],
          "new_lines": ["REQUEST_TIMEOUT = 20"]
        }
      ]
    }
  ]
}
```

规则应固定：

**原文件版本必须一致，旧行内容必须精确一致，编辑区间不能重叠，修改范围必须已经读取。** 任一条件不满足就报告冲突，不自动寻找“差不多”的位置。

整文件替换仅允许已完整读取的小文件。截断结果、脱敏结果不能被用来覆盖整个文件。

## 4.4 状态与成功回执

提议完成时返回：

```text
state = PENDING_APPROVAL
workspace_modified = false
```

批准后尚未完成：

```text
state = RUNNING
operation_id = ...
```

真正完成后返回：

```text
state = APPLIED
每个文件的 before_sha256 / after_sha256
每个文件的实际执行结果
tests_run = false
```

**“文件已保存”与“项目测试通过”必须分开。** 首版不运行项目命令，因此不能因为写入成功就宣称代码功能正常。

## 五、安全写入、审批与恢复机制

这是整个项目最重要的部分。

## 5.1 修改集必须先冻结，再批准

推荐流程：

```text
读取文件
  ↓
生成确定的最终字节与完整差异
  ↓
保存不可变修改集
  ↓
本地操作者查看并批准
  ↓
重新检查权限、期限、文件身份和版本
  ↓
执行写入
  ↓
刷盘、回读、验证
  ↓
保存实际回执
```

批准必须绑定：

```text
change_id
完整修改集摘要
连接主体
工作区及代次
策略版本
原始版本
批准期限
```

修改内容、目标路径或原始版本发生变化，就必须生成新修改集。

**不能接受模型传来的 `approved: true`；不能因为用户在聊天里说“批准”，就把一个普通工具参数当作本地审批凭证。**

首版本地控制台提供“批准并应用”，直接进入同一套执行服务。ChatGPT 同时调用 `change_apply`，也只会关联同一个操作。

## 5.2 Windows 并发不能只靠“先算哈希，再写文件”

下面的流程存在竞争窗口：

```text
检查哈希一致
   ↓
用户在 VS Code 保存了新内容
   ↓
插件覆盖文件
```

因此本方案增加原生文件系统层：

> 固定相关目录和文件身份，在同一个受保护句柄内完成校验、写入、截断、刷盘和回读。

Windows 文件共享模式支持阻止冲突的读、写、删除打开请求；不能取得所需句柄时，应返回占用错误，而不是退回普通写入。([Microsoft Learn][6])

### 首版明确选择的写入语义

建议采用 `guarded_inplace`：

* 正常执行期间，用独占句柄防止普通并发保存干扰。
* 写入前持久化原始与目标快照。
* 在同一句柄内验证并修改。
* 写后刷盘并核验哈希。
* 进程崩溃可能留下部分字节，由恢复机制处理。

**这不是崩溃原子的文件替换，也不是多文件 ACID 事务。**

不能一边要求目标文件保持拒绝删除的独占句柄，一边又承诺无条件通过重命名替换该文件。不同写入方式必须分别证明其真实语义。

原生保护不能通过验收时，只开放读取和提议，不能降低安全标准来开放直写。

另一个边界是：插件写完以后，编辑器可能再次保存旧的未保存缓冲区。普通文件服务不能完全控制这种行为，后续 VS Code 集成需要用编辑器文档版本解决。

## 5.3 多文件操作使用执行日志，不假装一次事务

每个文件记录：

```text
写入意图
原文件身份和版本
已开始写入
已刷盘
已回读验证
实际结果
```

所有恢复快照必须先持久化，才允许修改用户文件。刷盘使用相应文件系统能力，并检查实际错误返回。([Microsoft Learn][7])

总体状态建议：

```text
PENDING_APPROVAL
    ├── REJECTED / EXPIRED / INVALIDATED
    └── APPROVED
           ↓
         QUEUED
           ↓
       VALIDATING
           ├── CONFLICT / FAILED_NO_CHANGE
           ↓
        APPLYING
           ├── APPLIED
           ├── ROLLED_BACK
           └── RECOVERY_REQUIRED
```

## 5.4 崩溃恢复按实际文件状态判断

| 重启后观察到的情况         | 处理方式                                 |
| -------------------------- | ---------------------------------------- |
| 文件仍是原状态             | 结合日志判断未应用或已恢复，不重放旧批准 |
| 文件已经是目标状态         | 记录核验到目标状态，不再次写入           |
| 文件是第三种内容           | 保留当前内容，进入人工恢复               |
| 文件身份变化或新建归属不明 | 保留现场，不猜测归属                     |
| 状态库或快照损坏           | 关闭写入，不初始化空库继续运行           |

尤其要防止：

> 插件崩溃后，你已经继续修改了文件；插件重启却自动拿旧备份覆盖你的新修改。

因此，**恢复时遇到第三种内容，默认保留，不强行覆盖。**

## 5.5 撤销不是 Git 重置

撤销应生成一个新的逆向修改集，再次批准，并验证当前文件仍符合上次应用后的版本。

禁止使用：

```text
git reset --hard
git clean
git checkout
git stash
```

来实现插件的一键恢复。插件拥有的是某次批准修改的权限，不是整个工作区的所有权。

## 六、访问权限与隐私防护

## 6.1 路径防护必须集中实现

所有读取、搜索、Git 和写入都必须经过同一层 `FsGuard`，不能分别写几套不一致的路径判断。

需要覆盖：

| 风险                             | 处理要求                 |
| -------------------------------- | ------------------------ |
| `..`、绝对路径、盘符和 UNC     | 拒绝                     |
| Windows 设备路径、ADS、保留名称  | 拒绝                     |
| 尾空格、尾点、大小写与短名称别名 | 规范化并按实际身份校验   |
| 符号链接、Junction、硬链接       | 首版保守拒绝             |
| 父目录被替换                     | 固定父目录句柄并验证身份 |
| 工作区根被移动或替换             | 原授权代次失效           |
| 两个路径指向同一物理工作区       | 拒绝重叠可写授权         |

Windows 的硬链接和 Junction 确实可能使表面路径不对应独立对象，因此仅做字符串前缀检查不能作为安全边界。([Microsoft Learn][8])

## 6.2 区分“搜索排除”和“安全拒绝”

`node_modules`、构建产物、缓存等主要是检索性能问题，用户可以在本地调整排除规则。

`.env`、私钥、凭证、插件自身状态目录等属于安全拒绝。**模型不能取消这些规则，也不能通过 Git 差异、搜索片段、快照或错误信息绕过去。**

敏感内容检测只能作为附加防护，不能承诺识别所有秘密。涉及脱敏的读取结果，禁止直接用于编辑原文件。

## 6.3 Git 查询也必须是真正只读

建议不使用自由 Git 命令，而使用可注入文件系统的读取库，将全部写方法拒绝。

例如，isomorphic-git 的当前 `statusMatrix` 文档明确指出，默认行为可能刷新 `.git/index` 的 stat 缓存；设置 `refresh:false` 才避免这项刷新。因此实现必须同时使用 **`refresh:false`＋底层只读文件系统**。([Isomorphic Git][9])

Git 解析器可以拥有必要元数据的内部读取权限，但这不能变成模型任意读取 `.git`、任意 blob 或历史秘密的入口。

首版遇到不支持的 linked worktree、外置 gitdir、对象格式等，应明确报告“不支持该 Git 布局”，普通文件能力仍可继续使用。

## 6.4 不上传全仓，不等于源码完全不出本机

设计上不建云端全量索引，不上传整个仓库。

但 ChatGPT 要分析某段源码，工具返回的这段源码就会进入 ChatGPT 的处理范围。**本地隧道不是把云端模型变成本地模型。**([OpenAI Developers][5])

本地审计应记录哪些文件、哪些范围、多少字节被返回，但默认不再将源码正文完整复制进日志。

## 七、本地控制台与默认限制

## 7.1 控制台页面

| 页面       | 内容                                           |
| ---------- | ---------------------------------------------- |
| 连接状态   | 本地服务、隧道、版本、当前主体、暂停开关       |
| 工作区管理 | 添加目录或单文件、权限模式、排除规则、重新验证 |
| 待批准修改 | 完整文件清单、差异、修改量、风险、有效期       |
| 操作详情   | 逐文件执行结果、哈希、操作状态                 |
| 冲突与恢复 | 原版本、目标版本、当前版本，以及安全处理入口   |
| 历史与审计 | 工具访问、返回范围、审批与修改记录             |

源码、Markdown、HTML 都按文本展示，不执行其中的脚本，不自动加载外部图片。

首版不做“部分批准”。用户只批准部分文件时，应生成新的修改集，防止批准内容和实际执行摘要不一致。

## 7.2 建议初始限额

这些是产品设计初值，不是平台官方限制。

| 项目               |                            初值 |
| ------------------ | ------------------------------: |
| 可编辑文本文件大小 |                           2 MiB |
| 单次返回正文       |                          64 KiB |
| 单次读取行数       |     最多 400 行，同时受字节限制 |
| 目录页             |                     最多 200 项 |
| 搜索页             |                 最多 100 个匹配 |
| 搜索时间预算       |    3 秒，超时返回明确的部分结果 |
| 单修改集文件数     |                           20 个 |
| 修改集最终文件总量 |                           8 MiB |
| 修改集有效期       |                         24 小时 |
| 批准有效期         |                         10 分钟 |
| 单工作区写并发     |                               1 |
| 已终结操作快照保留 | 初始 7 天；未决恢复快照不得清理 |

这些限制可以由本地操作者调整，不能由模型通过参数扩大。

## 十、最终验收与开发执行要求

这个项目不能仅以“ChatGPT 成功改了一次文件”为验收标准。至少必须证明：

| 验收项                       | 必须结果                           |
| ---------------------------- | ---------------------------------- |
| 用户只要求分析               | 不写入、不产生隐含修改             |
| 批准前或拒绝后               | 工作区字节完全未变                 |
| 文件在读取后被编辑器保存     | 冲突，不覆盖                       |
| 同一修改集重复调用           | 返回同一操作，不重复写入           |
| 写完后应答丢失               | 查询恢复到实际结果，不再执行       |
| 多文件中途失败               | 逐项事实明确，可恢复，不假报全成功 |
| 崩溃后用户继续编辑           | 保留当前内容，不自动拿旧快照覆盖   |
| 通过链接或特殊路径逃逸       | 拒绝，授权外文件不变               |
| 搜索或 Git 读取敏感文件      | 不绕过访问策略                     |
| 连接停用、权限收紧、批准过期 | 旧请求不能继续执行                 |
| 插件升级或卸载               | 不删除用户仓库，不静默丢弃未决恢复 |
| 文件保存成功但未测试         | 明确说明“已落盘，未运行项目测试” |

对执行开发的 Agent，建议统一要求每个任务提交：

```text
任务编号
实际改动文件
实现说明
实际执行的测试命令、环境与退出码
负向测试证据
未执行项与原因
已知限制
回退方式
```

**不能只靠 mock 宣称 Windows 文件系统测试通过，也不能只靠 MCP Inspector 宣称 ChatGPT 网页验收通过。**

实际开发的第一批只下发 **LWB-001～LWB-004**：先打通你的真实网页账号和本地测试文件，再证明 Windows 路径、并发和恢复方案成立。之后按依赖推进只读能力、修改提议、批准写入和产品化，**不要一开始就暴露一个可任意覆盖本地文件的 `write_file` 工具。**
