# Local Workspace Bridge：ChatGPT 网页本地仓库与文件插件

版本：design-v1.0  
日期：2026-09-25  
状态：**架构与实施计划；尚未实现服务，尚未执行实机或账号验收。**

## 0. 决策摘要

产品目标：在 ChatGPT 网页中，通过原生工具读取、搜索用户电脑中已经保存的仓库和文本文件，提出确定的修改，经本地操作者批准后写回原目录，并获得可查询、可核验、可恢复的执行结果。

建议采用 **私有 MCP 连接 + 独立本地服务 + 本地批准控制台**。不依赖浏览器 DOM 抓取，不依赖 TransportAndAI 的后端，不要求把仓库推到 GitHub/Gitee，不建设新的模型聊天服务。

首版平台是 Windows 本地 NTFS、单用户、代码/文本文件。V1 支持既有父目录中的文件创建和既有文件修改；重命名、删除和目录创建在 V1.1；Office/PDF、终端执行、多用户公开分发和未保存的编辑器缓冲区在 V2。

关键取舍：**权限不由模型判断；修改先冻结再批准；原生句柄负责路径和并发；多文件用持久化日志和恢复，不伪称跨文件事务。**

全部接口、限额、目录和状态名均为本方案拟定，不是已存在的产品能力。

## 1. 外部接入事实与先决门禁

### 1.1 已核实的平台路线

OpenAI 官方文档描述了 ChatGPT 开发者模式接入读写 MCP 工具，以及通过 Secure MCP Tunnel 接入私有服务。隧道客户端在本机主动连接 OpenAI，再将请求转发给可达的 stdio 或 HTTP MCP 服务，不需要把本地文件端点直接暴露到公网。[S1][S3][S4]

官方资料目前仍有账号范围的不一致：开发者指南写明 Pro/Plus 等网页账号可使用读写工具；帮助中心另一篇文章仍将 Pro 描述为读/fetch 范围。因此本方案不保证特定账号已获得写权限，必须用用户真实账号验收。[S1][S2]

隧道需要 Platform tunnel_id、运行时 API key 和相应权限。Platform 隧道权限、ChatGPT 开发者模式权限以及工作区关联是不同事项。隧道没有自动把本地服务变成多用户鉴权系统。[S3]

### 1.2 G0 必须取得的证据

| 验证项 | 通过证据 | 不通过时的处理 |
|---|---|---|
| 网页原生工具接入 | 真实 ChatGPT 会话成功发现并调用测试工具 | 标记 BLOCKED，不用 DOM 自动化绕过 |
| 网页写能力 | 在专用测试目录完成确认后写入与回读 | 只保留读取，不把写工具标记为只读 |
| 隧道运行条件 | tunnel-client 在目标 Windows 环境可正常运行、断线重连 | 记录具体缺失项；不能猜测支持环境 |
| 调用身份边界 | 证明该隧道/连接只授予目标私人用户或明确的可信主体 | 共享组织隧道不得直接授权个人目录 |
| 路径与写入保护 | Windows 句柄并发/目录交换 PoC 通过 | direct_write 保持关闭 |
| 版本兼容 | 记录已通过的 SDK、协议、客户端与运行时版本 | 不以“latest”作为可复现交付版本 |

MCP Inspector 只能证明局部协议工作，不替代网页账号验收。资料截至本设计日期核查；后续平台变化应更新兼容性记录，而不改写旧测试事实。

### 1.3 发布路线

V1 私人使用优先采用 Secure MCP Tunnel。公开插件分发需要稳定、公开可达的 HTTPS MCP 端点及相应认证/审查，不能仅凭本地端点、临时隧道或 Secure MCP Tunnel 宣称可公开发布。[S3][S5]

V1 不开发公网中继。账号或隧道门禁未通过时，可以继续做本地 Inspector 验证，但不能宣称用户的“ChatGPT 网页本地读写”目标已完成。

## 2. 产品范围与操作语义

### 2.1 版本边界

| 能力 | V1 | 后续 |
|---|---|---|
| 授权多个不重叠目录、单独文件 | 支持 | 多设备/多用户另做 |
| 文件列表、路径定位、字面量搜索、分段读取 | 支持 | AST/符号图按需求增加 |
| 已保存但未提交的工作区内容 | 支持 | 不要求先推远端 |
| Git HEAD/index/worktree 的只读状态和授权文件差异 | 受支持布局内支持 | 历史、linked worktree、submodule 扩展 |
| 新建文本文件、精确编辑既有文本 | 本地批准后支持 | 大文件按独立协议扩展 |
| 创建父目录、重命名、删除 | 不隐式执行 | V1.1 显式操作与额外门禁 |
| 撤销既有文件修改 | 新修改集 + 新批准 + 当前版本匹配 | 撤销创建涉及删除，随 V1.1 |
| 未保存的 VS Code 缓冲区 | 不支持 | 独立编辑器扩展 |
| DOCX/XLSX/PDF 结构编辑 | 不支持 | 独立格式适配、隔离处理、可视化验收 |
| Shell 命令执行 | 仅由单独的 `command_exec` workspace grant 显式开放；同用户权限，不是沙箱，可能访问授权根之外并联网；限时/限输出，不保证回滚 | 普通文件访问仍使用文件 grant；shell 风险见 ADR-005 |
| Chrome 扩展/ChatGPT 页面脚本 | 不需要 | 仅可作为便利入口，不承载权限 |

首版支持 Python、JS/TS、Vue、Markdown、JSON、YAML、TXT 等 UTF-8 文本。读取可以明确报告其他编码；写入遇到未知编码、混合换行或二进制时拒绝，不静默转码。

### 2.2 三条核心使用流程

**只读分析**：选择已授权工作区 → 定位相关模块 → 搜索 → 按范围读取 → 返回带路径、行号、版本的材料 → ChatGPT 分析。此流程不产生修改集。

**修改既有代码**：读取目标范围 → 精确编辑提议 → 本地生成完整差异 → 操作者批准 → 执行器重新校验 → 写入、刷盘、回读 → 返回实际回执。

**保存方案**：确认目标工作区和相对文件路径 → create_text 提议 → 检查目标不存在且父目录已存在 → 本地批准 → 不覆盖创建 → 回读验证。目标已存在时必须重新走编辑提议，不能自动覆盖。

### 2.3 数据源与隐私边界

本地工具处理的是硬盘已保存内容，不是编辑器的未保存缓冲区。逐文件快照不代表整个仓库同一时刻的全局快照；输出应注明 `consistency=per_file`。

不上传整个仓库、不建云端全量索引，但返回给 ChatGPT 的源码片段和差异会离开本机。工具元数据和结果就是模型可用的数据来源。[S5] 本地 UI 展示本地完整差异时不需要额外上传所有差异；MCP 结果仅返回必要摘要或用户任务所需范围。

撤销本地权限不能收回已经返回 ChatGPT 的内容。本地快照用于恢复，也属于应保护和有限保留的用户数据。

## 3. 总体架构与信任边界

```text
ChatGPT 网页
   │ 原生 MCP 工具调用
   ▼
OpenAI 私有隧道
   │ 本机主动建立的出站连接
   ▼
tunnel-client（受保护配置与运行时凭证）
   │ stdio，固定的 MCP 适配器进程
   ▼
MCP Adapter ──认证的本地 IPC──┐
                              ▼
                        Local Daemon
                  ┌──────────────────────┐
                  │ 连接身份/工作区/策略   │
                  │ 目录、读取、检索、Git  │
                  │ 修改集/批准/操作状态   │
                  │ 执行协调/审计/恢复     │
                  └──────────────────────┘
                       │            ▲
                 受限原生 IPC       │ 单独认证的控制 API
                       ▼            │
               Windows FsGuard   本地 Vue 控制台
               / Write Executor  授权、差异、批准、暂停
                       │
                用户明确授权的根目录

SQLite、快照、凭证、安装目录：在授权根之外，模型永远不可访问。
```

### 3.1 运行组件

| 组件 | 实现建议 | 责任 |
|---|---|---|
| MCP Adapter | TypeScript + 已锁定的官方 MCP SDK | schema、工具发现、协议、连接身份转交 |
| Local Daemon | TypeScript/Node.js | 统一业务规则、状态、调度和控制 API |
| Windows FsGuard | 小型 Rust/Win32 辅助模块或等效审计过的原生模块 | 文件身份、路径固定、独占句柄、写入与刷盘 |
| Console | Vue 3 | 本地资源授权、完整差异、批准与恢复 |
| 状态库 | SQLite | 修改集、批准、执行日志和幂等事实 |
| 快照存储 | 受 ACL 保护的内容寻址 blob 目录 | 旧/新原始字节、完整性校验与恢复 |
| Git Reader | 只读虚拟 fs + 经验证的 Git 读取库 | 不执行 Git CLI，不刷新用户索引，不提供网络 |

逻辑模块不是微服务，不引入 Redis、Celery、MySQL 或新模型 API。原生辅助模块存在的原因是 Windows 文件系统安全与并发，不是让其承担业务逻辑或任意命令执行。

### 3.2 为什么本机优先 stdio

隧道已支持转发给 stdio/HTTP。[S3] V1 优先 stdio 连接 MCP Adapter，使模型入口没有可被任意网页直接访问的本地 HTTP 文件服务。适配器再经认证 IPC 调用唯一 daemon。

HTTP MCP 仅作为经过认证的测试/兼容模式，不暴露控制 API。使用 Streamable HTTP 时校验 Origin，绑定回环地址并实施真实认证；MCP 规范明确要求考虑 DNS rebinding 等风险。[S6]

### 3.3 身份规则

单用户 V1 的主体是本地配置的 `connection_id`，通过专用适配器/IPC 凭据得到。此主体对应一个被明确限制的私有隧道配置。所有该连接上的请求共享其权限，不能假装知道请求来自哪一段 ChatGPT 对话。

`conversation_label`、模型传入的 `user_id` 或 MCP 会话标识都不作为授权证据。不同连接只能使用本地明确分配给它们的工作区；多用户隔离需要后续 OAuth/设备绑定，而不是向工具参数添加 user_id。

### 3.4 控制面与模型面分离

模型面可以读、提议、查询、请求应用已批准修改。它不可以添加目录、批准修改、修改安全策略、导出凭证、清除恢复记录或更新插件。

本地控制面拥有上述管理能力，但仅对经本地启动器认证的操作者开放。授权令牌不通过 MCP 返回；不能把 `approved:true`、网页截图或普通工具参数解释为人类批准。

## 4. 不变量与威胁模型

### 4.1 发布必须保持的 14 条不变量

| 编号 | 不变量 |
|---|---|
| I01 | 未在本地授权的物理对象不能被读取或写入 |
| I02 | 工作区根、连接权限和安全规则不能由模型扩大 |
| I03 | 路径必须按实际打开的文件身份判断，而非字符串前缀 |
| I04 | 搜索、Git、快照、缓存和错误不得旁路读取策略 |
| I05 | prepare 不改变用户工作区 |
| I06 | 批准绑定唯一修改集摘要、主体、工作区代次、策略和有效期 |
| I07 | 应用前重新验证全部基线；文件变化不能强行覆盖 |
| I08 | 同一修改集最多一个应用操作，即使更换幂等键 |
| I09 | 超时不是失败证据；执行事实由持久化记录与文件状态协调 |
| I10 | 无法证明安全写入时拒绝，不降级弱路径/弱锁实现 |
| I11 | 多文件不是 ACID；任何部分/未知结果必须显式暴露 |
| I12 | 撤销不能覆盖后续人工修改，也不能重置 Git 暂存区 |
| I13 | 密钥、审批状态库、恢复快照目录对模型永远不可挂载 |
| I14 | 只有实际终态回执可支持“已保存”；落盘不等于已通过项目测试 |

### 4.2 主要防护对象

防护模型误操作、恶意仓库提示文本、路径穿越/链接、错误重试、普通编辑器并发、网络断开、服务崩溃、磁盘错误、网页跨站请求与错配连接。

不宣称抵抗已控制当前 Windows 账户的任意恶意进程、管理员/内核、原始磁盘写入或不诚实存储硬件。代码编辑可能影响下一次构建或启动，因此 package 脚本、CI、编辑器任务等需风险提示；“不执行 Shell”不等于编辑任何代码都无风险。

### 4.3 目录与内容规则

硬拒绝至少包括 `.env` 及常见变体、私钥/凭证、插件自身状态目录、系统启动/浏览器凭证目录；`.env.example` 不应被模型自动豁免，操作者可在明确的本地策略中为确定样例另设规则。

搜索排除包括依赖、编译产物、缓存、媒体、大型数据等，可按项目本地调整。这类性能排除不等于安全拒绝，二者必须分开存储。

内容检测只能提供附加防护，不能保证识别一切秘密。命中高置信度秘密时不向模型返回完整内容；已经脱敏的读取结果禁止获得可编辑票据。

## 5. 工作区和 Windows 文件系统规则

### 5.1 工作区登记

本地示例：

```json
{
  "display_name": "TransportAndAI",
  "kind": "directory",
  "root_path": "D:\\MyProjects\\MyApps\\transportandai",
  "mode": "read_propose_apply_with_local_approval",
  "enabled": true
}
```

这是本地控制 API 的配置，不是 MCP 工具参数。服务端生成 workspace_id，保存规范长路径、卷身份、根目录身份和 generation。单文件挂载将允许路径缩到唯一文件，不能扩散到父目录其他内容。

V1 不支持 UNC、网络盘、WSL 映射路径、未验证云占位/同步目录、大小写敏感目录特例和特殊文件系统直写。路径含未知重解析能力时拒绝，不靠 extension 判断普通文件。

### 5.2 路径处理

工具只接受 `workspace_id + relative_path`，内部统一 `/` 分隔。

拒绝绝对路径、盘符形式、UNC、设备命名空间、`..`、NUL/控制字符、ADS 冒号、保留设备名称、尾点/空格等混淆。按句柄逐级固定祖先目录，验证每一级非 reparse，并验证最终路径与文件身份。末级使用 OPEN_REPARSE_POINT 并不等于所有中间目录都安全。[S7]

Windows 的 Junction、符号链接和硬链接均可能使表面路径不对应独立对象。[S8] V1 对链接/硬链接采取保守拒绝；大小写和 8.3 别名须用实际规范路径/身份消歧，不能仅以字符串中出现 `~` 判定。

服务状态目录和已挂载根的物理别名也必须防重复授权。原地更换目录或重新授权后 generation 变化，全部旧票据和修改集失效。

### 5.3 文件版本

内部版本至少包括：

```text
workspace_generation
canonical_relative_path
volume_identity
file_identity
raw_bytes_sha256
size
encoding / bom / newline
relevant_attributes
```

文件身份在同内容安全保存后变化也可触发保守冲突。不能只用 mtime 或 size；也不能把读取正文重新编码后的哈希当作原文件字节哈希。

### 5.4 首版实际写入方式

写入模式名建议 `guarded_inplace`：既有文件在同一独占句柄内验证基线、写入、截断、刷盘、回读。微软的文件共享模式明确支持阻止冲突的读/写/删除打开请求；不能取得所需句柄时操作必须失败。[S7]

该模式的取舍是：在正常执行期间保护普通并发保存，同时保留文件身份和 ACL；**进程崩溃时不保证目标只有旧/新两个完整版本，可能留下部分字节**。因此必须有执行前持久化快照、执行日志与恢复。

不同时声称“目标保持拒绝删除的独占句柄”又“能够无条件 rename 原子覆盖目标”。如果以后使用替换式写入，应以新的 ADR 和竞争/崩溃测试证明真实语义，不混用两种保证。

只使用 Node 的“先 hash 再 writeFile/rename”不足以达到本方案写入约束。原生验证未通过或句柄能力不足时，保留 read/propose，关闭 direct_write。

## 6. MCP 工具契约

### 6.1 工具清单

| 工具 | 关键输入 | 输出与限制 | readOnlyHint |
|---|---|---|---|
| bridge_status | 无 | 当前连接别名、版本、能力和限制；无凭证 | true |
| workspace_list | 无 | 当前连接获准的工作区别名与能力，不返回全部本机根 | true |
| file_list | workspace_id, path, cursor | 有界目录页；授权范围内 | true |
| text_search | workspace_id, query, path_glob, cursor | 路径/行号/片段、扫描范围和截断信息 | true |
| file_read | workspace_id, path, line range/cursor | 字节版本、实际范围、读取票据、完整性提示 | true |
| git_status | workspace_id, path scope | HEAD/index/worktree 状态，授权范围内 | true |
| git_diff | workspace_id, path, comparison | 内部读取生成差异，不支持任意命令/对象 ID | true |
| change_prepare | workspace_id, items, idempotency_key | 不可变修改集和 PENDING_APPROVAL | false |
| change_get | change_id 或 operation_id | 状态、分页差异/结果；每次重新鉴权 | true |
| change_list | workspace_id, cursor | 当前连接的有限修改集列表 | true |
| change_apply | change_id, idempotency_key | 只消费有效本地批准，返回唯一 operation_id | false |
| change_revert_prepare | change_id, idempotency_key | 新逆向修改集，不直接恢复 | false |

change_prepare 虽不修改工作区，却改变持久化修改集状态，不能伪标为只读。change_apply 保守标注 destructiveHint=true；openWorldHint=false 只表示范围是授权私有资源，不代表无需服务端授权。官方明确表示 annotations 不能代替鉴权、校验和确认。[S5]

### 6.2 读取示例

```json
{
  "workspace_id": "ws_transportandai",
  "path": "apps/myagent/example.py",
  "start_line": 1,
  "max_lines": 120
}
```

```json
{
  "ok": true,
  "data": {
    "path": "apps/myagent/example.py",
    "source": "disk",
    "sha256": "<entire-raw-file-sha256>",
    "encoding": "utf-8",
    "bom": false,
    "newline": "crlf",
    "start_line": 1,
    "end_line_exclusive": 121,
    "truncated": true,
    "consistency": "per_file",
    "read_token": "<server-issued-signed-proof>",
    "next_cursor": "<opaque-cursor>",
    "content": "..."
  },
  "request_id": "req_example"
}
```

文件名和字段内容仅为契约示例，不表示已读取该仓库文件。读取票据绑定调用主体、工作区代次、规范路径、文件身份、全文件哈希、实际返回行范围和有效期；票据不授予审批或写入权限。可用签名载荷实现，避免将每次读取都建成业务对象。

### 6.3 精确编辑示例

```json
{
  "workspace_id": "ws_transportandai",
  "idempotency_key": "prepare-client-generated-unique-key",
  "summary": "调整请求超时常量",
  "items": [
    {
      "op": "edit_text",
      "path": "apps/myagent/example.py",
      "base_sha256": "<entire-raw-file-sha256>",
      "read_token": "<server-issued-signed-proof>",
      "edits": [
        {
          "start_line": 12,
          "end_line_exclusive": 13,
          "old_lines": ["REQUEST_TIMEOUT = 10"],
          "new_lines": ["REQUEST_TIMEOUT = 20"]
        }
      ]
    }
  ]
}
```

行号从 1 开始，区间左闭右开。old_lines 必须与基线精确匹配；新/旧数组单个元素不能包含换行字符。编辑区间不重叠，并且必须在读取票据的已见范围内；插入要求邻接上下文已读。全文件哈希和精确行内容共同约束，不能 fuzzy match，也不能自动“找一个差不多的位置”。

内部维护行到原始字节的映射，保留未变字节、BOM 和原换行。整文件替换只允许已完整读取的小文件；没有返回全文件的票据不允许替换全文。空文件、末尾换行、仅 BOM 文件必须有专门测试。

### 6.4 修改集结果

```json
{
  "ok": true,
  "data": {
    "change_id": "chg_example",
    "state": "PENDING_APPROVAL",
    "approval_required": true,
    "digest": "<canonical-change-digest>",

```

模型返回 summary 是不可信文案。真实预览必须由本地旧/新快照生成。更改任何文件、字节、目标路径或基线都创建新修改集，不能覆盖已审批记录。

### 6.5 应用与回执

```json
{
  "change_id": "chg_example",
  "idempotency_key": "apply-client-generated-unique-key"
}
```

成功示例：

```json
{
  "ok": true,
  "data": {
    "change_id": "chg_example",
    "operation_id": "op_example",
    "state": "APPLIED",
    "recovered": false,
    "files": [{
      "path": "apps/myagent/example.py",
      "state": "VERIFIED",
      "before_sha256": "<old-hash>",
      "after_sha256": "<new-hash>"
    }],
    "tests_run": false,
    "message": "已验证文件落盘；未运行项目测试。"

```

暂未完成返回 RUNNING 和 operation_id；等待审批返回 APPROVAL_REQUIRED，不挂起连接等待人点击。单个模型回合不能保证在本地点击批准后自动继续：本地可直接执行，下一次用户交互再查询，不承诺无依据的 ChatGPT 主动唤醒。

### 6.6 错误与重试分类

| 错误码 | 意义 | 自动重试 |
|---|---|---|
| WORKSPACE_NOT_GRANTED / POLICY_DENIED | 没有当前授权 | 不重试、不换路径绕过 |
| WORKSPACE_GENERATION_CHANGED | 根或策略已改变 | 重新授权/重新读取 |
| PATH_UNSAFE / LINK_UNSUPPORTED | 路径或文件形态不支持 | 不弱化校验 |
| FILE_VERSION_CONFLICT / READ_TOKEN_STALE | 基线已变 | 重读并创建新提议 |
| FILE_BUSY | 不能取得句柄 | 有界重试；批准仍须有效 |
| ENCODING_UNSUPPORTED / BINARY_UNSUPPORTED | 非 V1 可编辑文本 | 不转码覆盖 |
| APPROVAL_REQUIRED / APPROVAL_EXPIRED | 无有效本地批准 | 等待操作者或新批准 |
| IDEMPOTENCY_CONFLICT | 同键不同请求 | 修正客户端，不能覆盖旧记录 |
| RESULT_TRUNCATED / SEARCH_BUDGET_EXCEEDED | 有界部分结果 | 缩小范围/使用游标 |
| RECOVERY_REQUIRED | 实际状态需协调 | 先查询与本地恢复，禁止再次应用 |
| STORAGE_UNAVAILABLE | 状态库/快照/空间故障 | 停写，保留现场 |

协议层无效请求与业务错误分开；工具执行失败按锁定 SDK 的 isError 机制返回，同时提供上述结构化错误。PENDING_APPROVAL/RUNNING 是正常工作流状态，不伪装系统失败。

## 7. 数据模型与约束

| 表/实体 | 核心字段 | 关键约束 |
|---|---|---|
| connections | id, principal_kind, enabled, generation, credential_ref | 身份来自认证 IPC，不来自模型 |
| workspaces | id, kind, canonical_root, volume_id, root_file_id, generation, policy_version, mode | 禁止重叠可写根与未验证别名 |
| grants | connection_id, workspace_id, capabilities, enabled | 权限交集计算，每次请求重查 |
| changesets | id, owner_connection_id, workspace_id, root_generation, policy_version, digest, state, expires_at | 内容不可变 |
| change_items | change_id, seq, op, canonical_path, base_file_id/hash, target_hash, old_blob/new_blob, encoding | 同一物理文件不能重复操作 |
| approvals | id, change_id, digest, actor, expires_at, state, consumed_by | 精确绑定、一次性消费 |
| operations | id, change_id, state, worker_instance, started_at, finished_at, result | UNIQUE(change_id) |
| journal_entries | operation_id, seq, item_id, stage, observed_file_id/hash, error_code | 有序追加；先意图、后目标写 |
| blobs | id, sha256, size, storage_ref, refcount, retention_state | blob 持久化后才能引用进入可执行计划 |
| idempotency_records | principal_id, tool, key, request_hash, result_ref | UNIQUE(principal_id,tool,key) |
| audit_events | id, subject, action, workspace_id, metadata, timestamp | 无源码正文/凭证 |
| schema_version | version, applied_at, checksum | 不兼容版本拒绝运行 |

SQLite 采用短事务、外键、持久化约束和有界 busy_timeout。WAL/FULL 为拟定初始配置，须在目标环境故障测试；SQLite 的原子提交语义不扩展到用户工作区文件。[S9][S10]

### 7.1 修改集摘要

规范化摘要输入至少包括版本号、调用连接、工作区及代次、策略版本、操作有序列表、规范路径、旧对象身份/哈希、最终字节哈希、创建不存在前提、编码与执行模式。字段顺序和 Unicode/路径规范化必须固定。

批准时间和修改集内容分别存储；不能因为 summary 相同就认为批准适用。实际 blobs 再次验哈希，防止数据库指向被替换的文件。

### 7.2 幂等语义

同一 prepare 键 + 同一 request_hash 返回同一个修改集；同键不同请求返回冲突。相同 change_id 无论几个 apply 键，只关联一个 operation。

批准消费、操作认领和状态条件更新放入短事务。网络断线、工具超时、进程重启都不能删除幂等事实。过期清理可以清理不再需要的原文，但已执行修改集的唯一性/终态墓碑要保留，不让旧 ID 成为可再次执行任务。

## 8. 审批、执行和恢复状态机

### 8.1 正常状态

```text
PENDING_APPROVAL
   ├── REJECTED
   ├── EXPIRED
   ├── INVALIDATED
   └── APPROVED
          └── QUEUED
                 └── VALIDATING
                       ├── CONFLICT / FAILED_NO_CHANGE
                       └── APPLYING
                             ├── APPLIED
                             ├── ROLLED_BACK
                             └── RECOVERY_REQUIRED
```

APPROVED 不表示已写，QUEUED 不表示成功，APPLIED 必须具有核验后的回执。RECOVERY_REQUIRED 可在核验后协调为 APPLIED（recovered=true）、ROLLED_BACK，或继续等待人工。

### 8.2 执行步骤

1. 读取唯一 operation 与有效批准，检查当前连接、工作区、策略、到期状态。
2. 获取工作区写互斥；按固定顺序固定目录和既有目标句柄。
3. 重新核验全部既有文件身份和原始哈希；任一冲突则在写入前退出。
4. 验证新文件父目录；创建不存在只能作为前提，最终仍使用 CREATE_NEW。
5. 确保全部旧/新快照已持久化并校验；数据库记录执行意图。
6. 对每个目标在受控句柄中写入，记录阶段，FlushFileBuffers 后回读校验。[S11]
7. 成功持久化最终回执后释放资源。失败时在仍有安全句柄的范围内有界恢复；不能恢复则阻断该工作区写入并标记 RECOVERY_REQUIRED。

数据库事务不能跨越等待批准或全部文件写入过程；数据库与文件系统的先后边界必须有故障注入测试。

### 8.3 创建竞争与部分完成

V1 只在已有父目录创建文件。检查“尚不存在”之后若另一程序创建同名目标，CREATE_NEW 必须失败，不覆盖。

创建可能在多文件计划中晚于前几项修改；此时失败可能触发对已改项的受控恢复，而不是谎称所有文件一直未变。新文件创建后到身份入库之间崩溃属于可能的模糊状态，不能猜测所有同名内容都属于插件。

### 8.4 恢复判定

| 实际观察 | 处理 |
|---|---|
| 当前身份/内容符合原状态 | 该项可能尚未应用或已恢复；结合日志协调，不重放旧批准 |
| 当前符合目标状态 | 标记目标已达并记录恢复核验；不用再次写入 |
| 当前是第三种内容 | 保留当前文件，进入人工恢复，不自动覆盖 |
| 身份变化、日志缺失或新建归属不明 | 保留现场，要求本地核验 |
| 快照/数据库损坏 | 工作区写能力关闭，不初始化空库继续工作 |

内容等于目标并不总能证明是谁写的。恢复回执应说明“核验到目标状态”，不编造执行归属或时间。

### 8.5 撤销

撤销是新修改集，不是把旧记录删除。恢复既有文件要求当前文件仍为上次应用后的期望状态；否则生成冲突。V1 撤销新增文件不自动删除，随 V1.1 删除能力发布。

不得运行 git reset --hard、git clean、checkout 或 stash 来实现插件撤销。插件只拥有自己批准修改的范围，不拥有用户整个工作区历史。

### 8.6 暂停和撤权

暂停立即阻断新调用和排队应用，并让未发出的读取结果重新通过撤权校验。已开始的低级文件写不能神奇撤回，需在下一安全边界停止/恢复；界面显示真实的“正在停止”或“需要恢复”。

不能为了宣称立即停用而直接杀死写进程，然后掩盖部分写入状态。

## 9. Git、搜索和大仓库处理

### 9.1 Git 读取不经过自由命令

V1 建议使用接受自定义 fs 的 Git 读取库。isomorphic-git 官方文档支持注入 fs；其当前 statusMatrix 文档还明确说明 refresh:false 可避免刷新 .git/index 的 stat 缓存。[S12][S13]

实现时双重约束：设置 refresh:false，同时底层只读 fs 的所有 write/unlink/mkdir/chmod 方法都拒绝。库出现未预期写入就失败，不允许为“让状态查询成功”开放写权限。

Git 元数据解析器仅访问必要的 HEAD、index、refs、objects 等内部范围；模型不能使用任意 raw object ID 获取 blob。git_diff 必须按授权路径解析旧/新内容，并执行同样的敏感内容检查。读取库支持按树/提交与路径读取 blob，可作为实现基础。[S14]

不提供 HTTP 模块，不启动 Git CLI，不执行 hooks/textconv/external diff。V1 对外置 gitdir、alternates、未支持对象格式和特殊索引返回 GIT_LAYOUT_UNSUPPORTED；普通文件读取仍可使用。

查询注明比较对象与固定 commit ID。工作区字节差异、Git 的换行/属性语义可能不同，不能声称支持所有 Git 行为；在 fixture 中明确验证支持范围。授权过滤后的状态只是可见范围，不是全仓安全审计。

### 9.2 搜索

先文件树/模块定位，再受限内容搜索，再读取关键范围。V1 采用本地字面量检索，避免建立全仓向量索引和复杂数据同步。

搜索不直接把目录交给一个会任意跟随链接的外部进程；先经过统一 FsGuard。若后续用 ripgrep 加速，也必须处理路径替换和出站策略，不能用工具默认行为代替安全边界。

输出 include scanned_files、skipped_files、truncated、deadline_exceeded、scope。不能把未扫描文件或权限跳过文件算作无命中。

### 9.3 建议初始限额（可本地调整，不是平台限制）

| 项 | 初值 |
|---|---|
| 可编辑文本文件原始大小 | 2 MiB |
| 单次返回正文 | 64 KiB |
| 单次读取 | 最多 400 行且遵守字节上限 |
| 目录页 | 最多 200 项 |
| 搜索页 | 最多 100 个匹配且不超过正文限制 |
| 单次搜索时间预算 | 3 秒，超时返回有界部分结果 |
| MCP 单请求 JSON | 1 MiB，含编码膨胀 |
| 修改集文件数 | 20 |
| 修改集最终文件字节总量 | 8 MiB |
| 修改集有效期 | 24 小时 |
| 本地批准有效期 | 10 分钟，执行开始时再次校验 |
| 全局读取并发 / 单工作区写并发 | 4 / 1 |
| 连接每小时出站内容初始预算 | 32 MiB，超额由本地操作者调整 |
| 终结操作快照保留 | 7 天起步；未终结/恢复引用不清理 |

未使用的设置不应先建设复杂管理系统，首版可以配置文件 + 本地控制台摘要。

## 10. 本地控制台与安装布局

### 10.1 控制台页面

| 页面 | 内容 |
|---|---|
| 连接与状态 | 本机服务、隧道、当前连接主体、版本、门禁、暂停 |
| 工作区 | 添加目录/单文件、别名、只读/批准写入、排除规则、重新验证 |
| 待批准 | 明确文件清单、完整 diff、风险、有效期、拒绝/批准并应用 |
| 操作详情 | 状态、逐文件哈希、实际写入结果、是否运行测试 |
| 冲突/恢复 | 原内容/目标内容/当前内容，保留当前、重新提议、本地恢复 |
| 历史与审计 | 工具调用、返回文件范围、出站字节、修改/批准记录 |

浏览器页面不能凭空获得任意本机路径：Windows 本机控制台通过受信 daemon 调用系统目录/文件选择器，同时保留粘贴路径和本地 CLI 注册。不要把浏览器目录选择 API 当作能直接返回可用系统绝对路径的通用方案。

### 10.2 批准交互

主按钮是“批准并应用”，原子保存批准并通过唯一应用服务排队。模型的 change_apply 即使同时到达也只看到同一个 operation。没有默认部分批准；用户挑选部分文件时重新生成修改集并重新审核摘要。

源码/Markdown/HTML 一律按文本展示；禁止外部图片、远程脚本和未经转义的 HTML。模型撰写的“安全说明”与系统计算的风险事实分区展示。

### 10.3 本地文件布局

```text
%LOCALAPPDATA%\LocalWorkspaceBridge\
  bin\
  config\
  db\bridge.sqlite
  objects\
  logs\
  diagnostics\
```

这些目录不放进被编辑的仓库。操作日志默认不记录源码正文、原始搜索文本或凭证；恢复快照按必要范围存储，并具备保留/清理策略。SQLite 不是自动加密数据库，本方案不宣称仅因使用 LocalAppData 就能抵抗同账户恶意程序。

安全测试从 P1 持续增加，P6 是独立复查，不是第一次安全测试。V1.1/V2 不应混入首版关键路径。

### 12.2 单任务交付要求

每个开发任务必须交付：实际改动文件、实现提交、对应测试、执行环境、命令与退出码、负向证据、已知限制和回退方式。未执行的 Windows/ChatGPT 测试标为 NOT_RUN，不能以“代码看起来正确”替代。

## 14. 部署、灰度与回退

第一轮只暴露临时测试根；第二轮在业务仓库测试副本启用只读；第三轮逐个真实工作区启用只读；G4/G6 通过后，按本地显式批准开放小范围写入。

功能开关建议：`read_enabled`、`git_enabled`、`proposal_enabled`、`direct_write_enabled`、`recovery_required`。未提供能力不应继续在工具描述中暗示可用。

遇到越权或数据完整性问题，立即关停新写入并保留执行日志/快照；对进行中的操作按安全边界处理。软件回退只回退二进制和兼容代码，不能为了回滚插件而回滚用户仓库。较新 schema 不兼容旧程序时必须拒绝启动。

安装包和更新包具有可核对来源、哈希、依赖清单与构建记录。首版无可信自动更新链路时，选择人工更新，不接收模型提供的下载地址作为更新来源。

## 15. 成功标准与明确不承诺的事项

V1 成功标准是：用户能在 ChatGPT 网页对本地授权的代码/文本提出自然语言需求，看到真实检索结果和完整待审差异，在本地批准后得到精确落盘与可恢复的操作事实。

不承诺账号权限必然开放、不承诺源码绝不出本机、不承诺整个仓库一致快照、不承诺任意文件格式、不承诺普通文件系统具有跨文件事务、不承诺模型能自动在用户本地批准后被主动唤醒、不承诺没有实机证据的 Windows 并发安全。

这些不是放弃目标，而是产品必须准确暴露的能力边界；任何扩展都通过新增契约、测试和授权进入，而不是削弱默认安全规则。
