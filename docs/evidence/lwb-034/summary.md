# LWB-034 · 实现安全暂停与紧急停用 — 证据

**采集方式：** `node --import tsx scripts/evidence/lwb-034.ts`（**退出码 0**；**61 PASS / 0 FAIL / 5 NOT_RUN**）
**采集环境：** Windows 11 Home China 10.0.26200 / Node v22.20.0 / win32 x64 / PowerShell 7.6.6 / **真 NTFS**（`%TEMP%` 下的临时工作区）
**测试套件：** 见文末「测试套件」一节（类型检查、FsGuard 导入检查、`node --test` 各自的退出码与计数）
**原始日志：** 未入库（`*.log` 在 `.gitignore` 中，与 `lwb-006` ~ `lwb-033` 一致），
本次运行落在 `docs/evidence/lwb-034/raw.log`。下文引用的每条 `PASS` / `NOTE` 行均为运行输出的**逐字**摘录；
唯一的例外是少数长报告被 `…` 截短（截短处不影响该行要说明的事实，完整值在 `raw.log` 里）。

**门禁结论：G4 未通过**（依据与理由见 `docs/evidence/g4-write.md`）；上游 G0 未通过、G1 无判定记录、
G2 未通过、G3 未通过、验收负责人未指定。**四个能力开关在本任务交付后照旧全关**，
因此 `direct_write_enabled` 仍然为假 —— 本任务的**全部**取证都在 `os.tmpdir()` 之下，
真实工作区一个字节都没被碰过。

**这一轮里最要紧的一句话：紧急停用不得靠「把写进程杀掉」来实现。**
验收标准的原话是「不会粗暴杀写进程而**假装零影响**」，它禁掉的正是那件最省事的事：
发一个终止信号，界面回到「已暂停，一切正常」。那样做的后果是盘上留着半份内容、
状态库里写着 `APPLYING`、而没有任何人知道 —— 因为知道这件事的那个进程已经没了。
本任务走的是另一条路：**不杀进程，只中止意图**（§1）。写盘的手在**自己的**安全边界上
停下，因此它能把「我停了 / 我写到一半」如实落库；而「已经算好、还没发出去的结论」
在返回前被工具面拦下（§1 的第二半）。

## 0. 这一轮的证据是在什么装置上采的

三条步骤的原文：

> 1. 暂停立即阻断新读取/新应用并废止排队授权。
> 2. 进行中的写在安全边界停止或受控恢复；无法立即停止时界面显示正在停止。
> 3. 停用后阻止未发出的工具结果；记录已返回给 ChatGPT 的内容无法撤回。

三条验收标准的原文：

> (a) 紧急停用不会粗暴杀写进程而假装零影响。
> (b) 暂停后重连不重放旧批准。
> (c) 操作处于恢复态时，界面和工具均如实报告。

| 段 | 装置 | 为什么非这样不可 |
| --- | --- | --- |
| §0 | 真 NTFS 工作区 + 真 `PowerShellWinfsBackend` + 真 `WinfsGuard.ps1` | 「写到一半被停住」要有一个**真的写到一半**的现场，桩里的写入是原子的，那一格造不出来 |
| §1 | 闸门装在 `WinfsOps.writeFileGuarded` 上（第一个文件真的落盘之后、第二个开始之前） | 这一格问的是「**盘上**已经变了一个文件时按下停用会怎样」，因此闸门必须在那一次 `WriteFile` 返回之后 |
| §1 / §3 / §4 | 真工具面（`makeToolHarness`）+ **生产那个** `registerPauseOperations` 控制面 | 「工具面与控制面说的是同一件事」不能靠两份手写桩对齐 —— 桩对齐是写测试的人自己说的 |
| §1 / §1.7.1 | 真 `audit_file_access` 行（`delivered = 1`） | 「收不回来」这个读数如果只看 0，与一个**恒为 0** 的计数器无法区分 |
| §2 | 真协调器（真 `AbortController`、真租约、真操作行） | 「正在停止」说的是那**一件**正在写的操作，而不是一句措辞 |
| §5 | **真库文件**（`openDatabase({ path })` → `closeDatabase` → 再 `openDatabase`） | 同一个进程里的 `isPaused()` 说明不了重启之后还在，而「忘记自己停过」是这一格最坏的失效方向 |

**装置自述（§0 逐字）：**

```
PASS §0.1 原生护栏后端可用（真 CreateFileW / WriteFile / 真共享模式） — backend=powershell-pinvoke exclusive_handle=true flush=true
```

注入点画出来是这样，它决定了下面每一条断言能证明什么：

```text
  真 applier 的内部次序：vet → 快照 → recordIntent → 逐条目 writeOne
                                                          ↑
                                        a.txt 写完（盘上真的变了）
                                                          ↓
                                        ← 这里按下紧急停用
                                                          ↓
                                        b.txt 的 writeOne 开头看到中止 ⇒ 抛
```

于是盘上**必然**留下一个已经改过的文件。这一格的全部含义就在这个「必然」上：
一个「停用之后什么都不该变」的世界会让 §1 的每一条断言一起变绿，而它是错的。

## 1. 写到一半按下停用（步骤 3 的前半句、验收 1）

### 1.1 影响是**真的**，而且账实相符

```
PASS §1.3 盘上第一个文件是**被批准的那些字节**（影响真的发生了） — 实际="A-new\nA-rest\n" 之前=27e7fceb5265…(64)
PASS §1.3.1 第二个文件一个字节都没动（写盘的人自己在安全边界停了）
PASS §1.3.2 授权外看门文件（工作区内）一个字节都没动
PASS §1.3.3 授权外看门文件（工作区外）一个字节都没动
PASS §1.5 修改集与操作都停在 RECOVERY_REQUIRED — change=RECOVERY_REQUIRED
PASS §1.6 逐条目日志：写了第一个、第二个按待恢复处理 — 阶段=item_intent → item_written → item_flushed → item_verified → write_recovery_required
```

`§1.3` 与 `§1.3.1` 必须成对读：**一个文件变了，另一个一个字节没变**。
只证前者的实现（「停用之前先把这次执行跑完」）会让「紧急」二字失去意义；
只证后者的实现（「停用 = 什么都没发生」）正是验收标准点名禁止的那种假装。
`§1.6` 是账本对齐盘上现场的那一步：写到第一个文件的那四条阶段齐全，
而收尾那一行是 `write_recovery_required` —— 不是「失败」，也不是任何一句「已收场」。

### 1.2 撤回的是**结果**，不是那次写入（步骤 3 的前半句）

```
PASS §1.2.1 这次调用的结果被撤回：错误码 PAUSED、说的话是「未发送」而不是「未执行」 — PAUSED：本地服务在本次调用进行中被紧急停用；本次结果未发送。
PASS §1.4 结果被撤回：审计里这一行是 deny / REVOKED_BEFORE_RETURN — outcome=deny reason=REVOKED_BEFORE_RETURN code=PAUSED
PASS §1.4.1 一个字段都没出去（delivered 为空），而目标两个文件都记着 — delivered=0 attempted=2
PASS §1.4.2 撤回的是回执，不是那次写入（盘上的字节仍然是被批准的那一份）
```

这一节里最容易做错的是**措辞**。「未执行」与「未发送」对操作者意味着完全不同的两件事：
前者是「盘上没动，我可以再来一次」，后者是「盘上**可能已经动了**，而你没有拿到那份回执」。
因此判据是两条一起：`delivered` 为空（一个字段都没出去）**且** `attempted` 记着那两个文件
（它确实碰过它们）。把「碰过但没答」记成「没碰」是另一种谎。

`PAUSED` 这个错误码本身就出现在两个不同的地方（第 1 步「未执行」与第 5 步「已撤回」），
因此审计行里必须另有一个字段把两者分开 —— 那就是 `reason: REVOKED_BEFORE_RETURN`。

### 1.3 步骤 3 的后半句：已经交出去的内容收不回来

「记录已返回给 ChatGPT 的内容无法撤回」是一条**要能被查出来**的话，因此它有一个读数：
`PauseService.status().unrecallable_file_rows`（口径见 `AuditRepo.countDeliveredFileAccess`
——「已经离开本进程」的**更大**的那一侧，理由是偏小的读数会让人以为漏得没那么多）。

```
PASS §1.0.1 装置自检：停用之前真的有一次读取把内容交出去过 — 读到的=a.txt 已交出的文件访问行=5
PASS §1.7.1 控制面数得出「已经交出去、收不回来」的内容，而被挡住的那次读取不计入 — unrecallable_file_rows=5 停用前交出去的=5
```

两行合起来才成立：`§1.0.1` 先证明这个读数**能不是 0**（否则它可能是一个把 `delivered`
读错成常量的计数器，那与一个正确的计数器在「只看 0」的断言下长得一模一样），
`§1.7.1` 再证明它**没有**把停用期间被挡住的那次读取算进去（那次一个字节都没交出去）。
那里的 5 不是 1：`change_prepare` 的两次读取也把内容交回给了调用方，它们同样算「收不回来」——
这个数偏大是对的，偏小才是危险的。

读数在**控制面**（`service.pause_status`）上，不在工具面上：工具面的 `pause` 只有三个计数
（`BridgeStatusData.pause`），「有多少内容已经出去过」不给模型看。

### 1.4 停用期间：写入被挡住，而服务**仍然答得出话**

```
PASS §1.7 暂停立即阻断新读取 — PAUSED：本地服务处于暂停状态，已阻断新读取与新应用。
PASS §1.8 停用期间 `bridge_status` 照答，且如实说「停着」 — paused=true paused_at=2026-09-26T11:46:24.139Z
PASS §1.9 上面这些字符串里没有本机绝对路径
PASS §1.13 那之后护栏栈仍然活着（我们停的是写入，不是进程）
PASS §1.13.1 解除暂停之后读得到文件（写盘人没有被杀掉）
```

`§1.7` 与 `§1.8` 是**刻意**的两格：工具面第 1 步挡的是工作区类操作，
而 `bridge_status` 不在那一类里 —— 一个被暂停的服务如果连「为什么不能用了」都拒绝回答，
操作者就只能去翻日志，而那正是紧急时刻最不该发生的事。

`§1.13` / `§1.13.1` 是「不粗暴杀进程」的直接判据：停用之后护栏栈仍然可用、
解除之后文件读得到。**我们停的是写入，不是进程。**

### 1.5 恢复之后：重连看到的是**如实的账**

```
PASS §1.10 解除暂停：状态回到未停用
PASS §1.11 恢复之后重读回执：RECOVERY_REQUIRED，且不说「已保存」 — state=RECOVERY_REQUIRED in_progress=false recovered=false
PASS §1.12 回执里的哈希与独立回读的一致 — 回执=eb9c00b9507d…(64) 回读=eb9c00b9507d…(64)
PASS §1.14 撤销/恢复都没有把批准变回可用 — findActive=undefined
```

这里要盯住的是 `in_progress=false` 与 `state=RECOVERY_REQUIRED` **同时**成立：
它已经停下来了（不是还在跑），而它停在的地方需要人工核验（不是「收场了」）。
`§1.12` 把回执里的哈希与一次独立回读对上 —— 一分如实报告的基本功是**它说的数就是盘上的数**。

### 1.6 三条装置自检（少了它们，上面每一条都可能验的是空气）

```
PASS §1.1 装置自检：只写了一个文件就停住了 — 真的落盘的文件=a.txt
PASS §1.2 装置自检：紧急停用真的被按下过
```

闸门挂在盘那一层，而它有没有响过**没有任何别的东西**能证明：
一个没挂上的闸门会让这次执行一路写成 `APPLIED`，于是「撤回」那一组断言全部失败、
而「盘上第一个文件变了」那一组**照样通过**。因此闸门自己先自报一次。

## 2. 「正在停止」是一个读数，不是一个说法（步骤 2 的后半句）

```
PASS §2.1 按下那一刻报告里有一条「正在停止」 — 条数=1
PASS §2.2 那条记录指的就是账上这一次操作（不是随便凑一条） — 报告=op_e96a27ea353545658ef9b85a586e4b39 账上=op_e96a27ea353545658ef9b85a586e4b39
PASS §2.3 它的状态是 APPLYING（真的在写，不是排队） — state=APPLYING
PASS §2.4 持有者就是本进程，且这一格不是「抢锁」 — holder_pid=16236 slot_blocked=false
NOTE §2.5 这一格与「停用瞬间完成」的区别 — 界面若只说「已暂停」，操作者会把「有一个写入还握着写盘权」当成「已经没事了」——`stopping` 这个列表存在的唯一理由就是让那句话说不出口
```

步骤 2 的原文是「无法立即停止时界面**显示正在停止**」。这一格的意义全在
`§2.2` 上：报告里那一条必须**就是**账上那一次操作（操作号逐字相等），
而不是一条「看起来像」的记录。一个凑出来的读数会让界面在真正要紧的那一刻
指错方向 —— 而操作者此刻唯一的动作就是「照这个线索去处理」。

`holder_pid` 是本工程**唯一**一处把进程号交给界面的地方，它只出现在控制台这条通道上
（工具面的 `bridge_status` 只有计数）。这与「进程号不出站」是同一条纪律的两面。

## 3. 暂停废止排队授权与本地批准（验收 2）

```
PASS §3.0 按下之前：修改集 APPROVED、批准 ACTIVE
PASS §3.1 按下停用：状态变成暂停，且带时刻
PASS §3.2 那条已批准的修改集在废止清单里，且被记成 INVALIDATED — from=APPROVED to=INVALIDATED approval_id=apr_5ae37110adf44eb7a20de940fdd889ab
PASS §3.3 落库：修改集已经不是可应用的状态
PASS §3.4 那条本地批准被记成 REVOKED（不是「时间到了」） — approval.state=REVOKED
PASS §3.5 恢复：状态回到未停用，且不恢复任何批准
PASS §3.5.1 恢复之后那条修改集仍然是作废的（一次带副作用的深呼吸不是恢复）
PASS §3.6 重放被拒（错误码粗粒度，原因是撤销） — code=APPROVAL_EXPIRED reason=APPROVAL_REVOKED
PASS §3.6.1 给人看的那句话说是「撤销」，不是「过期」 — 本地批准已被操作者撤销。
PASS §3.7 被作废的批准不得改动文件
PASS §3.8 恢复之后新提案照常落地（否则上面那句「写不进去」只是「这装置不写盘」） — state=APPLIED…
```

验收 2 的原文是「暂停后重连不重放旧批准」。这句话有两半，而**第二半容易被漏掉**：
`§3.5` 证明恢复不恢复任何批准（这是刻意的：紧急按钮不是一次「带副作用的深呼吸」），
`§3.6` 证明那条旧批准**真的**不能用 —— 而且回答里给的是「撤销」不是「过期」。
两者的下一步完全不同：一个是「有人按过停用，重新准备一次修改集」，
另一个是「等一会儿再来」—— 对一次**紧急**动作来说，后一句话是错的。

`§3.8` 是这一节的对照组：恢复之后**新**提案照常落地。
少了它，上面那一整组「写不进去」的断言可能只是在描述一个「本来就不写盘」的装置。

错误码本身是**粗粒度**的（`APPROVAL_REVOKED` 与「过期」共用 `APPROVAL_EXPIRED`，
与 `packages/policy` 的 `approvalFailures` 逐条对齐），因此判据落在
`details.reason` 与给人看的那句话上 —— 这两处才是「为什么不能用」。

## 4. 恢复态：工具面与控制面说的是同一件事（验收 3 的前半）

```
PASS §4.0 结果被撤回（步骤 3） — 本地服务在本次调用进行中被紧急停用；本次结果未发送。
PASS §4.1 工具面：数得出那一次待恢复，且不再把这条算作「正在写」 — recovery=1 stopping=0 unrevoked=0
PASS §4.2 工具面：限制说明里有一句讲这次待恢复 — 有 1 个写入操作处于待恢复状态，需要本地操作者核验；在它被处理之前，本工具面不会对相关文件做出任何承诺。
PASS §4.3 控制面：说得出是**哪一次**（操作号、修改集、工作区都对得上） — recovery_operations=[{"operation_id":"op_ebd7d99141d04dc98def44d55b33866e","change_id":"chg_81b84efc-4e80-4873-9ee2-93d8ea3f8360","workspace_id":"ws_0001"}]
PASS §4.4 两面说的是同一个数 — 工具面=1 控制面=1
PASS §4.5 废止清单是空的：那条修改集已经作废，不再是「排队授权」 — unrevoked=[] stopping=0
PASS §4.6 恢复之后复读：同一个 RECOVERY_REQUIRED，不说「已保存」也不说「找不到」 — state=RECOVERY_REQUIRED in_progress=false
PASS §4.7 逐条目日志里收尾那一行写着按待恢复处理 — 阶段=item_intent → item_written → item_flushed → item_verified → write_recovery_required
PASS §4.8 上面这些字符串里没有本机绝对路径
```

验收 3 的原文是「界面和工具均如实报告」。**工具那一半在这里；界面那一半是 NOT_RUN**
（见文末未执行项：控制台的按钮属 LWB-035 之后的界面任务）。本任务交付的是它背后的
三个读数与两个操作，界面还没接上 —— 这句话必须写在这里，而不是让「均如实报告」看起来已经全部成立。

`§4.4` 是这一节的核心：两面**数出同一个数**，而且这个数的来源是同一个
`PauseService.status()`（不是两处各算一遍）。`§4.1` 里 `stopping=0` 与 `recovery=1`
同时成立也是刻意的：这条操作已经不再握着写盘权了，因此它不该继续出现在「正在写」里 ——
两个列表回答的是两个不同的问题。

## 5. 暂停活过重启（步骤 1 的持久面）

这一节用的是**真库文件**：`openDatabase({ path })` → `closeDatabase` → 再 `openDatabase`。

```
PASS §5.0 未暂停时：信号不是中止的
PASS §5.1 按下停用：落库了，且带时刻 — paused_at=2026-09-26T11:46:24.825Z
PASS §5.2 重开之后库里仍然写着「停着」
PASS §5.3 中止信号**一出生就是中止的**（在途写入不会因为在停用期间重启而继续）
PASS §5.4 重启不重写「上次暂停于」（那会让它变成一个关于重启时刻的假话） — 重启前=2026-09-26T11:46:24.825Z 重启后=2026-09-26T11:46:24.825Z
PASS §5.5 解除暂停：换了一个**没有**中止的新信号
PASS §5.6 解除之后库里也确实不再写着「停着」
NOTE §5.7 这一节用的库是**文件库** — 同一个进程里的 `isPaused()` 说明不了重启之后还在，而「忘记自己停过」正是这一格最坏的失效方向
```

`§5.3` 是这一节里最要紧、也最容易漏的一格。暂停落库之后重启，新的
`PauseService` **一出生就带着一个已经中止的信号**：这样在停用期间被认领的每一次执行
都会在第一个安全边界停下（它一个字节都还没碰）。少了这一格，
「重启之后暂停还在不在」就只回答了状态查询那一半 —— 而真正危险的是写入那一半。

`§5.4` 是「如实」两字落到一个时间戳上：重启**不**重写 `paused_at`。
顺手更新它看起来更「新鲜」，但它会让这个字段从「操作者是什么时候按的」
变成「本进程是什么时候起来的」—— 一次重启把一句**假话**写进了一条安全记录。

## 回退约束的落实

任务书原文：**关闭相关能力开关；保留执行日志与未决恢复数据；不得通过覆盖用户文件实现代码回滚。**

- **关闭相关能力开关**：本任务**没有**新开任何开关（`direct_write_enabled` 照旧为假，
  四个开关全关，工具面一律 `POLICY_DENIED`）。暂停动作只**增加**阻断：
  `service.pause` 之后连本来（在门禁放开的世界里）可用的读取也被第 1 步挡住（§1.7）。
- **保留执行日志与未决恢复数据**：§1.6 / §4.7 的逐条目日志齐全（
  `item_intent → item_written → item_flushed → item_verified → write_recovery_required`），
  而 §1.11 / §4.6 证明恢复之后那条操作**仍然**报 `RECOVERY_REQUIRED`：
  暂停没有把任何未决数据「收尾掉」。§1.14 与 §3.x 证明被作废的批准没有被恢复成可用。
- **不通过覆盖用户文件实现代码回滚**：本任务的全部取证都在临时目录里；
  每一次「没变」的断言都打在**盘上的字节**上（§1.3.1 / §1.3.2 / §1.3.3 / §3.7），
  而**没有**任何一次执行是靠「写回去」来让断言通过的 —— 停用中止的是意图，
  它不替任何人回滚已经落下的字节（§1.3 就是「那个字节留在了盘上」）。

## 这一轮里发现并改掉的两处

**一处是产品里的真实缺陷**，它的形态是「两个时钟」。

1. **`PauseService.engage()` 用两口钟写下了同一件事的两个时刻**
   （`packages/executor/src/pause.ts`）。这一步要同时做两件带时刻的事：
   把 `paused_at` 落库、并调 `invalidateMany(…, now)` 去作废排队授权 ——
   而后者拿这个 `now` 与 `approvals.expires_at` 比大小，那个时刻是 `Repositories`
   的那口钟写下的。原实现里 `engage()` 取的是 `new Date()`，于是当两口钟不一致时
   （测试夹具的锚定钟、任何注入过的钟、或只是跨过一次时钟调整的真实进程），
   一次「操作者按下了停用」会被**记成**「那条批准本来就过期了」。
   杀伤面不是措辞：审计里因此**看不见有人按过这个按钮**，而这条记录的全部意义
   就是它。修法是给 `PauseServiceDeps` 加一口可注入的钟（`now?: () => string`，
   默认仍是真实当下），装配根与测试装置都传**同一口**钟。
   缺陷是证据脚本 §3 撞出来的（`details.reason` 期望 `APPROVAL_REVOKED`、
   实际 `APPROVAL_EXPIRED`）—— 而它之所以能被撞出来，正是因为那条断言查的是
   **原因**而不是错误码：两者共用 `APPROVAL_EXPIRED`，只看码的话这一格是绿的。

**一处是装置本身。**

2. **夹具的协调器没有接上停止信号**（`tests/tools/harness.ts`）。
   `ExecutionCoordinator` 在 LWB-034 起接受一个外部停止源（`stop?: () => AbortSignal`），
   而装配根接上了、测试夹具没接 —— 于是「按下紧急停用」在真盘用例里
   对**在途写入**是一个空操作：盘上第二个文件照样会被写掉。
   这一点是本任务的真盘用例 §1 撞出来的（它断言「第二个文件一个字节都没动」），
   杀伤面也正是它的价值所在：一个**没接上**停止源的装置会让
   「在途写入在安全边界停下」这半条验收在一个**永远不会通过**的断言上暴露出来 ——
   但如果那一格恰好没被写下来（比如只断言了「盘上第一个文件变了」），
   整个 §1 会在停用根本没生效的情况下全绿。修法是在 `defaultCoordinator()`
   里接上 `stop: () => pauseService.stopSignal()`，并让 `PauseService` 与协调器
   在夹具里是**同一个**实例（两个实例会造出两个互不知晓的信号）。
   两处均记在 `docs/PROGRESS.md` 的偏离项 **135–136**。

**另外两处不是本任务的缺陷，但这一轮顺手改掉了**，因为它们会让证据本身变成假话：

3. **两条「模式版本」的钉子会随下一次迁移变成假失败**（`scripts/evidence/lwb-030.ts`
   与 `tests/unit/recovery-persistence.test.ts`）。它们写的是 `KNOWN_SCHEMA_VERSION === 7`，
   而本任务新增迁移 **v8**（`service_pause`）的那一天，两条断言就同时红了 ——
   红的原因与它们要证明的事毫无关系。判据改成从 `MIGRATIONS` **推导**
   （「v7 那一版在表里，且名字是 `recovery_authorizations`」「表里最后一版等于当前模式版本」）。
   一条会随无关改动变红的钉子，最终会被下一次「顺手把数字改大」修掉 ——
   而那正好是它本来的用处被抹掉的那一刻。
