## 1. 门禁原文，以及它与 G2 的一处关键差别

`docs/LWB_COMPLETE_PLAN.md` §12 的分期表：

```
| P3 提议与审批 | 019–025 | 精确文本编辑、冻结 diff、本地审批和状态机 | G3：批准前工作区字节零变化 |
```

**这句话与 G2 的形状不同，必须说清楚，否则这一节会被读成两个极端之一。**

| | G2 的原文 | G3 的原文 |
| --- | --- | --- |
| 文字 | 真实网页读取**且**内容出站可追踪 | 批准前工作区字节零变化 |
| 有没有提到网页 | **有**（「真实网页读取」） | **没有** |

G2 的判定之所以干脆，是因为它的原文里就写着「真实网页」四个字 —— 那四个字没满足，
G2 就没通过，与本地做得多好无关。

**G3 的原文里没有这四个字。** 它说的是一条可以在本机完全观测的性质：**批准之前，
工作区的字节数变化是零**。这句话今天**已经证得了**（见 §2），而且是拿真实字节证的，
不是拿意图证的。

那么为什么判定仍然是「未通过」？三条理由，按分量排序：

1. **任务书的步骤 3 要求真实网页。** LWB-025 的 `execution_steps` 第 3 条逐字写着
   「**真实网页测试**批准前无文件变化、拒绝无变化、改摘要旧批准无效」。
   它是 NOT_RUN。门禁原文可以读成「本地证得即可」，但**任务书对同一件事的要求读不成那样**。
2. **这条门禁今天比将来更容易满足，因而今天的通过含金量是打折的。**
   「批准前零变化」的完全形态需要「批准**后**会变化」作为对照 ——
   否则一个**根本没有写入能力**的系统也满足它。今天的实际情况正是后者的近似：
   执行协调器（LWB-026）尚未交付，工作区在任何路径下都不会变。
   因此 §2 证到的强命题是「**提议路径**自己不写」（这条不空洞，见 §2.2），
   而「批准前零变化」这句话里的**对照项**要到 LWB-026 之后才存在。
3. **上游悬着，且没有人被授权签署。** G0 未通过、G1 无判定记录、G2 未通过（§4）。

### 1.1 一处**被记录下来的少数读法**

按本仓库处理边界争议的既有做法（`g2-read.md` §1.2 的偏离项 61 就是「两种读法都写下、
按 NOT_RUN 记、不自行选一个」），这里如实记下另一种读法：

> **读法 B：** G3 的原文只说「批准前工作区字节零变化」。这句话在 §2 已被真实字节证得，
> 且 LWB-025 的三条验收标准**全部**在本机成立。因此 G3 应判**通过**，
> 待办项只剩「验收负责人签署」。

**本文件不采纳读法 B，理由就是上面第 1 条**：任务书对同一阶段的同一件事明确要求真实网页测试，
而那条测试从未跑过。但读法 B 不是荒谬的 —— 它成立的唯一缺口是「谁被授权说这句话」。
把它写在这里，是为了让将来翻这份文件的人看到：**这个分歧是被看见之后才搁置的，
不是被忽略掉的。**

### 1.2 什么能让 G3 通过

按上面的分析，只需要三件事，且**都不需要改代码**：

| # | 动作 | 谁 |
| --- | --- | --- |
| 1 | 完成 LWB-002（真实账号 + Secure MCP Tunnel），在真实网页上让模型提议一次并确认工作区无变化 | 操作者 |
| 2 | 交付 LWB-026 之后**重取一次**本条门禁（那时「批准后会变」的对照项才存在） | 本仓库 |
| 3 | 指定**验收负责人**并签署（`docs/adr/001-scope.md` §6 至今空缺） | 操作者 |

第 2 条不是形式要求。**一条「零变化」的断言，其强度取决于「本来会不会变」** ——
今天不变是因为没有写入方，明天不变才是因为提议路径守住了。

## 2. 已证的部分：批准前工作区字节零变化

这一半有**两条互相独立的证据线**，各自在不同的任务里采，装置也不同。

### 2.1 证据线一：LWB-020 的三条独立证据

`node --import tsx scripts/evidence/lwb-020.ts`（退出码 0；**57 PASS / 0 FAIL / 9 NOT_RUN / 36 NOTE**）
在真实夹具副本 + 真实 NTFS 身份 + 真实护栏上给出：

| 证据 | 它单独能证明什么 | 它单独**不能**证明什么 |
| --- | --- | --- |
| 运行期护栏的写方法调用 **0** 次 | 根本没走到写那一层 | 绕开护栏直接 `fs` 的实现能通过 |
| `prepare.ts` 源码静态扫描 **0** 处写方法名 | 源码里没有写调用 | 间接调用（经由别的模块）能通过 |
| 整棵目录树 **138 项**逐字节快照（含 `mtime`、含目录项增删） | 观察到的落盘状态没变 | 「写了又还原」能通过 |

### 2.2 证据线二：LWB-025 的四条独立证据

`node --import tsx scripts/evidence/lwb-025.ts`（退出码 0；**65 PASS / 0 FAIL / 4 NOT_RUN**）
覆盖的是**新接入的三个提议工具**（`change_prepare` / `change_get` / `change_list`）：

```
PASS 整棵工作区目录树逐项相同 — 138 项全部比对通过
PASS 运行期护栏的写方法一次都没被调用 — writes=[]
PASS 状态库里没有这条修改集的任何批准记录 — 实际 0 行
PASS workspace_modified 恒为 false — 实际=false
PASS next_action 明说尚未写入任何文件
```

**为什么这一半不空洞。** 「提议路径自己不写」这句话如果只由「目录树没变」来证，
一个「先写再还原」的实现同样通过。让它不空洞的是那条**运行期护栏台账**：
它把真实后端的 `writeFileGuarded` / `createFileGuarded` 包了一层 `Proxy` 逐次记录，
本次采集里是**空**。护栏**本来会被调用**（同一台账里逐次记下了 `resolvePath` 与
`readFileGuarded` 的真实调用），因此「没有写」是**判据挣来的**，不是「没东西可调」。

**一个细节值得留在门禁文件里**：`withLedger` 用 `Proxy` 而不是对象展开，是因为真实后端的
方法在**原型**上，`{...backend}` 会把它们全丢掉 —— 那会让写台账恒为空，
而恒为空的写台账恰好能让「一次都没被调用」永远通过。这类装置自身的失效模式
值得写进门禁文件，因为它决定了这条证据能不能被信任。

### 2.3 「批准前」这三个字在今天的边界

- **已实现的**：提议路径（LWB-019 ~ LWB-025）与批准路径（LWB-021 / LWB-024）
  各自有独立证据。
- **未实现的**：执行协调器（LWB-026）。因此**没有任何一次写入发生过**，
  也**没有一次批准被消费过**。
- 这条边界的直接后果写在 LWB-024 与 LWB-025 两份证据的 `NOT_RUN` 里，
  都是同一句：**「门拒绝」与「文件没被写」在证据强度上不是一回事**，
  两条并列存在，不互相顶替。

4. **不得把本地 Inspector / 测试装置的成功读成网页验收的一半。**
5. **回退方式受任务书约束**（LWB-025 `rollback`）：关闭相关能力开关；保留执行日志与未决恢复数据；
   **不得通过覆盖用户文件实现代码回滚**。

- **G3：未通过。** 门禁原文（批准前工作区字节零变化）的**可本地观测那一半已经证得**，

  G3 的判定因此也只是证据陈述，不是一次被授权的签署。

  「门禁原文没提网页所以这条不算数」。
