**采集方式：** `node --import tsx scripts/evidence/lwb-033.ts`（**退出码 0**；**111 PASS / 0 FAIL / 6 NOT_RUN**）
**采集环境：** Windows 11 Home China 10.0.26200 / Node v22.20.0 / win32 x64 / PowerShell 7.6.6 / **真 NTFS**（`%TEMP%` 下的临时工作区）
**测试套件：** 见文末「测试套件」一节（类型检查、FsGuard 导入检查、`node --test` 各自的退出码与计数）
**原始日志：** 未入库（`*.log` 在 `.gitignore` 中，与 `lwb-006` ~ `lwb-032` 一致），
本次运行落在 `docs/evidence/lwb-033/raw.log`。下文引用的每条 `PASS` / `NOTE` 行均为运行输出的**逐字**摘录；
唯一的例外是少数长报告被 `…` 截短（截短处不影响该行要说明的事实，完整值在 `raw.log` 里）。

**门禁结论：G4 未通过**（依据与理由见 `docs/evidence/g4-write.md`）；上游 G0 未通过、G1 无判定记录、
G2 未通过、G3 未通过、验收负责人未指定。**四个能力开关在本任务交付后照旧全关**，
因此 `direct_write_enabled` 仍然为假 —— 本任务的**全部**取证都在 `os.tmpdir()` 之下，
真实工作区一个字节都没被碰过。

**这一轮里最要紧的一句话：账上必须说得出「不知道」。**
护栏进程被杀掉时，调用方拿到的是客户端**合成**的一条失败 —— 它一个字节的下落都没说。
这一轮之前，那句话被印成了「已进入破坏性区域」（把一个未知印成了已知）。
现在的判据是三句（`TOUCHED` / `NOT_TOUCHED` / `UNKNOWN`），第三句说的是
「这个回答可能根本没到过护栏，因此它进没进破坏性区域没有被报告过」—— 它不描述磁盘，
它描述**我们手上有什么证据**（§2.3）。

## 0. 这一轮的证据是在什么装置上采的

三条步骤的原文：

> 1. 覆盖并行保存、同内容换文件身份、目录交换、目标创建竞争、文件占用和权限变化。
> 2. 覆盖断网、服务退出、原生辅助进程退出、磁盘满、短写、刷盘错误和数据库忙。
> 3. 每个持久化边界反复执行故障注入并核对授权外文件、实际字节和恢复日志。

三条验收标准的原文：

> (a) 未授权文件保持不变；无并发覆盖、重复追加和错误的 APPLIED。
> (b) 第三种状态不会自动覆盖。
> (c) G4 未通过时 direct_write 永远不对真实目录启用。

| 段 | 装置 | 为什么非这样不可 |
| --- | --- | --- |
| §0 | 真 NTFS 工作区 + 真 `PowerShellWinfsBackend` + 真 `WinfsGuard.ps1` | 能挡住一次写入的是**内核的共享模式**、**文件身份**与**硬链接计数**，不是我们声明的那几个字符串 |
| §1 ~ §5 | 真第三方动作（Node 的 `rename` / `rm` / `writeFile`）+ 真协调器 | 竞争必须落在「阶段 A 已经核对过、字节还没落下去」那一格，而那只有把真执行跑起来才存在 |
| §6 | 护栏自己的 `holdHandle`（真 `CreateFileW` + 真共享模式）、真 `chmod` | 「占用」与「权限」是两种不同的内核拒绝，它们的错误码必须来自内核 |
| §7 | 护栏自己的崩溃实验（真 `SetEndOfFile` + 真半份 `WriteFile` + 真 `[Environment]::Exit`） | 「助手死了」与「盘上真的是半截」是两件事，缺一条这一节就只是「一个返回值长什么样」 |
| §8 | **真文件库** + 第二个连接的真 `BEGIN IMMEDIATE` | `:memory:` 的两个连接是两个不同的库，「忙」在内存库上没有对应的真实机制 |
| §9 | 七棵源码树 + 检测器自查 + 反向探针 | 断网这一格要证的是**没有故障面**，那是一件关于代码的事，不是一次运行的结果 |
| §10.3 | 真子进程 + 真 `SIGKILL` + 真启动恢复 | 「服务退出」在同一个进程里造不出来：`daemon-death.test.ts` 起一个真执行者，等它停住，再打死它 |

**装置自述（§0 逐字）：**

```
PASS §0.1 原生护栏后端可用（真 CreateFileW / WriteFile / 真共享模式） — backend=powershell-pinvoke exclusive_handle=true flush=true
PASS §0.2 跨文件事务为假（I11：一次执行的原子性不覆盖用户文件） — crash_atomic_replace=false
PASS §0.4 工作区根是一个真 NTFS 目录，身份由**当场探测**得到 — volume_id=c6e22015…(8) file_id=01760000000a…(16)
PASS §0.5 两个授权外看门文件真的在盘上（工作区内一个、工作区外一个） — inside=39 字节 outside=40 字节
```

§0.4 是这一整套证据的地基：工作区身份不是写死在夹具里的字符串，而是**当场**向卷与文件
问出来的（`volume_id` + `file_id`）。路径前缀在这个仓库里从来不是身份（I05 / I03），
所以任何一条「写到了对的地方」的结论，都必须踩在当场取回的对象身份上。

## 1. 竞争五格（步骤 1、验收 1）

五格共用一套装置（`tests/windows/concurrency/rig.ts`），并且每一格都带一个**授权外文件**
的固定纪律：工作区内一个修改集**从未提起过**的兄弟文件 + 工作区**外面**一个文件，
每次运行前后取三项指纹（内容哈希 + 大小 + 最后写入时刻）逐项比对。

| 格 | 注入了什么 | 结果 |
| --- | --- | --- |
| §1 并行保存 | 阶段 A 之后第三方覆盖目标 | `ROLLED_BACK`，盘上是**第三方那一份**（逐字节） |
| §2 同内容换身份 | `rm` + `writeFile`：字节一样、对象换了 | `ROLLED_BACK`，失败原因是**文件 ID 不符**而不是哈希不符 |
| §3 第三种状态 | 第三方写下第三个版本 | 第三态**原样留着**，既没被覆盖成我们的目标，也没被「恢复」成基线 |
| §4 目录交换 | 目标**之上**那一级换成同名新目录 | 旧对象被挪到旁边仍是基线；新目录里的同名文件一个字节都没被碰 |
| §5 目标创建竞争 | `CREATE_NEW` 之下同名文件已被别人建出来 | `ROLLED_BACK`（Win32 80），别人建的那一个原样留着 |
| §6 文件占用 / 权限变化 | 真共享模式占住 / ACL 改成只读 | `CONFLICT`（FILE_BUSY / Win32 32）与 `ROLLED_BACK`（PERMISSION_DENIED / Win32 5） |

前五格的逐字判据（取自 §1 ~ §5）：

```
PASS §1.1：**没有错误的 APPLIED** — state=ROLLED_BACK
PASS §1.2 盘上就是第三方保存的那一份（逐字节）
PASS §2.0 装置自查：注入真的换掉了对象，而字节**一模一样** — file_id 00df0000000a…(16) → 00e00000000a…(16)，sha256 相同=true
PASS §2.1：失败原因指名了 /FILE_VERSION_CONFLICT/ — …目标对象已不是被批准的那一个：期望文件 ID 00df0000000a4977，实际 00e00000000a4977…
PASS §3.2 第三态**原样留着**（既不是我们的目标，也不是基线）
PASS §3.4 也不得被「恢复」成基线
PASS §4.3 **新目录里的同名文件**一个字节都没被碰 — sha256=c08b3e221fb6…(64)
PASS §4.4 被批准的那一个（已挪到旁边）仍然是基线 — sha256=82ad8608493c…(64)
PASS §5.2 别人建的那一个**原样留着**（逐字节） — sha256=86cfa2ad50c6…(64)
```

§2 这一格值得单独说一句：它验的是**身份**，不是哈希。「字节一样、对象换了」正是
编辑器另存为、`git checkout` 覆盖、解压覆盖在小文件上的形态 —— 一个只比内容哈希的
护栏会放它过去，然后这一次写入就落在了一个从未被批准的对象上。装置自查那一行
（`file_id … → …`，`sha256 相同=true`）保证注入**真的**换掉了对象。

**六格都有对照组**，这是这一节不空洞的关键：

```
PASS §1.5 对照：无人竞争时必须写成（否则 §1.1 验的是空气） — state=APPLIED
PASS §2.3 对照：同样的字节、没有换对象 ⇒ 写得成 — state=APPLIED
PASS §5.6 对照：建出来的字节与目标**逐字节相同**（BOM 与 CRLF 都在）
PASS §6.5 对照：同样的字节、无人占用 ⇒ 写得成 — state=APPLIED
PASS §6.9 对照：权限没被动过 ⇒ 写得成 — state=APPLIED
```

§2 与 §6 的对照夹具还多一条**受控对照**：两个夹具的基线**逐字节相同**
（`§6.1 受控对照：两个夹具的基线逐字节相同`），因此两者之间唯一的差别就是那一个注入。

## 2. 故障五格（步骤 2）

### 2.1 原生辅助进程退出 + 短写（§7）

让护栏**自己**在写入中途死掉：真 `SetEndOfFile`、真写一半、真 `[Environment]::Exit(43)`。
盘上因此留下**真的半截** —— 长度等于目标的一半、字节逐位等于目标前半段：

```
PASS §7.1 护栏助手进程真的起来了（进程表里看得见它） — pid=34976
PASS §7.3 终局是 RECOVERY_REQUIRED（不是 APPLIED，也不是干净的失败） — state=RECOVERY_REQUIRED
PASS §7.6 盘上是**真的半截**（长度 = 目标的一半，字节逐位等于目标前半段） — 盘上 16 字节 / 目标半截 16 字节（目标全长 33）
PASS §7.9 账上是 意图 → 失败 → 恢复被跳过 — 阶段=item_intent → item_failed → item_restore_skipped
PASS §7.10 账上没有「已恢复」（护栏不可用时不假装收场了）
PASS §7.11 折叠结论是「说不清」 — aggregate=unfinished
PASS §7.14 它**不在** `listUnfinished()` 里（那个入口问的是另一个问题）
```

`§7.14` 是这套记账里很容易走错的一步：待恢复的操作**不是**「未完成的操作」——
前者要人处理，后者是下一个进程要扫的。两个入口问的是两个问题
（`listUnfinished()` 只选 `QUEUED` / `VALIDATING` / `APPLYING`）。

### 2.2 三值判定：这个回答到底说了什么（§7.15 ~ §7.17）

```
PASS §7.15 这条失败是「护栏不可用」那一类（客户端合成，根本没到过护栏） — code=NATIVE_GUARD_UNAVAILABLE touched=false observed=false
PASS §7.16 它被读成三值里的**不知道**（不是 TOUCHED，也不是 NOT_TOUCHED） — verdict=UNKNOWN
PASS §7.17 账上那一条失败记的是**同一个**错误码（判决与记录同源） — 条目日志里的错误码=NATIVE_GUARD_UNAVAILABLE、GUARD_UNAVAILABLE_PROVES_NOTHING
```

`§7.16` 与 `§7.17` 合起来说明的是：**「没被证明」不等于「被否定」**。
`NATIVE_GUARD_UNAVAILABLE` 有可能是客户端合成的「没连上护栏」—— 响应根本没从护栏回来，
那么「`touched` 缺席」与「进程被杀」是同一种情形。判据因此按**证据**分三层：

| 情形 | 判定 | 依据 |
| --- | --- | --- |
| `touched === true` | `TOUCHED` | 护栏**说过**它进了破坏性区域 |
| `touched` 缺席且码不是 `NATIVE_GUARD_UNAVAILABLE` | `NOT_TOUCHED` | 护栏的契约是「只在没进破坏性区域时才省略 `touched`」 |
| `touched` 缺席且码是 `NATIVE_GUARD_UNAVAILABLE` | `UNKNOWN` | 这条失败可能是客户端合成的，根本没到过护栏 |

### 2.3 数据库忙（§8，步骤 2 与步骤 3）

两个落点各验一次，而两者走的是**两条不同的代码路径**：

```
PASS §8.1 状态库写不进去时，这次执行**抛出去**（不交回一个它记不下来的结论） — database is locked
PASS §8.2 记不上账就不许写：盘上仍是基线 — sha256=7f37e31ae801…(64)
PASS §8.3 修改集停在 VALIDATING — state=VALIDATING
PASS §8.4 一个条目日志都没有
PASS §8.5 停在 VALIDATING 的操作被 `listUnfinished()` 找到（启动恢复找的就是它）
PASS §8.9 认领的事务整个失败 ⇒ 操作仍是 QUEUED、连 operation_id 都没有 — state=QUEUED operation_id=null
PASS §8.11 对照：文件库 + 同样的注入位置、没有锁 ⇒ 写成（否则上面几条验的是空气） — state=APPLIED
PASS §8.12 对照：成功的四个阶段齐全 — 阶段=item_intent → item_written → item_flushed → item_verified
```

这一格真正要回答的问题是「状态库写不进去时，这次执行会留下什么」。这套记账有一条硬规矩
（`apply.ts` 阶段 B 的注释）：**`APPLYING` 那一格是「字节可能已经在盘上」的唯一记录** ——
于是「记不上账」与「不写」必须是同一件事。§8.2 与 §8.4 就是它的判据。

### 2.4 断网：它没有故障面（§9）

这一节不注入任何东西。它证明的是一件**关于代码**的事：一次写入的字节从批准记录走到磁盘，
沿途没有任何一个网络调用点。

```
PASS §9.1 执行段的源码真的被扫到了（不是空目录） — 共 36 个 .ts 文件
PASS §9.1 执行段里没有一个网络导入、也没有一个不需要导入的网络调用
PASS §9.2 反向探针：同一条判据在 `packages/ipc/src/client.ts` 上命中 `node:net` — 命中=node:net
PASS §9.3 执行段拉起的**子进程**只有本地 pwsh 助手（stdio 管道，`-NoProfile`）
PASS §9.4 护栏助手脚本里没有任何网络 cmdlet — 脚本 56728 字符
```

`§9.2` 是这套静态检查的**自查**：一条什么都不会命中的判据与一条**正确**的判据看起来一样，
因此判据必须在**已知会命中**的文件上命中一次。检测器与它扫的七棵树一起写在这里，
而不是写在测试文件里 —— 因为要证的不是「有一个检查」，是「执行段里没有那条边」。

## 3. 服务退出：真 SIGKILL 一个真执行者（步骤 2、`tests/fault-injection/daemon-death.test.ts`）

这一格是本仓库此前**缺的那一格**。「服务退出」此前只有两个近似：LWB-030 的「重启」
其实是**关掉库连接再打开**（那个进程一直活着，`finally` 全都规规矩矩跑完了），
LWB-026 的 `SIGKILL` 杀的是**假写盘人**（盘上没有半个现场可收拾）。

现在起的是一个真执行者（同一份文件的 `--worker` 分支：真 `PowerShellWinfsBackend`、
真 `createNativeApplier`、真 `ExecutionCoordinator`、真状态库与快照库），
它停在两个**确定的**停机点上，父进程等到它报出位置才动手，用 `SIGKILL` 打死它，
然后跑**真**启动恢复：

| 停机点 | 盘上 | 账上 | 恢复的结论 | 恢复写了几个字节 |
| --- | --- | --- | --- | --- |
| 动笔**之前** | 基线原封不动（连 `mtime` 都没动） | `item_intent` | `ROLLED_BACK` / `ALL_ORIGINAL` | **0** |
| 动笔**之后** | 已经是目标内容 | 还是 `item_intent` | `APPLIED` / `ALL_TARGET` | **0**（指纹三项全同） |

第二行值得盯着看：账上最后一句关于这个条目的话是「我打算动它」，而盘上它已经动完了。
把「可能」变成确定的，是恢复那一步**重新观测**出来的事实，不是任何一条补记 ——
恢复**没有**替执行者补记 `item_written`。逐条目日志回答的是「执行者自己做完了什么」，
而「后来发生了什么」由**回执**回答（`TARGET_REACHED`）。两者混起来，
那四个阶段就再也读不出「有没有跑完」了。

两条「零字节」的断言都打在**指纹**上（内容哈希 + 大小 + 最后写入时刻），
而不是打在报告的措辞上。这一格还带一条反向探针：同样的装置、同样的执行者、**不杀**，
必须一路写成 `APPLIED` 并走完四个阶段（`intent → written → flushed → verified`）——
少了它，一个「这套装置本来就写不成」的世界会让上面两条「没报 APPLIED」一起变绿。

**这一格没有构造的东西**：真正落在一次 `WriteFile` **之内**的死亡。护栏是一次
`WriteFile` 写完整个 payload 的（`WinfsGuard.ps1` 的 `Invoke-GuardedWrite`，不切块），
因此那个窗口在一个系统调用之内，只能靠概率去撞 —— 而撞出来的东西没法复现，
也就没法当证据。上面那两个停机点就是它的**确定等价物**。这条如实记在 §11。

## 4. 反复执行与授权外文件（步骤 3）

同一个故障跑三轮，逐项比对盘、账与工作区目录：

```
PASS §8.13 三轮的盘、账与工作区目录**逐项相同**（无累积、无重复追加） — 三轮都是：(无日志)
PASS §8.14 三轮都停在「什么都没写」的那一格（三条一样错的记录也能互相通过） — 阶段=0 条 未完成=1
PASS §8.15 工作区里只有基线的两个东西 — src,unrelated.txt
```

反复的理由不是覆盖率，是**累积**：一个每次失败都往状态库或工作区里多留一点什么的实现，
单轮看不出来，三轮就看得出来。因此判据是「第一轮长什么样，后面每一轮就必须还是那个样」，
**再加**一条「第一轮那一格本身是对的」—— 三条一样错的记录也能互相通过。

授权外文件在这一轮里出现的位置是：每一格运行前后各取一次三项指纹
（`expectCanariesIntact`），以及 §8.15 的目录清单 —— 后者能发现「多留了一个文件」，
而前者能发现「留了一个内容相同、身份不同的文件」。

## 5. 门禁与四个能力开关（验收 3）

`apps/daemon/src/gates.ts`：

```
platform_ready       = g0_platform_verified && compatibility_section3_passed
read/git/proposal    = platform_ready
direct_write_enabled = platform_ready && native_guard_verified && g4_concurrency_fault_passed
```

三件事值得记在这里：

1. `BRIDGE_GATES` 是一个**全为 `false` 的常量**，注释写明「这是一处需要人去改的常量，这是刻意的」。
   因此在当前仓库状态下启动 `npm run daemon`，四个能力开关全关、工具面一律 `POLICY_DENIED` ——
   **这是当前门禁下的正确结果，不是故障。**
2. **G4 自己是 `direct_write_enabled` 的一个与项**（这一轮新加的 `g4_concurrency_fault_passed`）。
   「G4 没通过时直写关着」这件事因此写在推导里，不依赖任何人的记性。
3. 16 格门禁取值穷举写在 `tests/unit/gate-combinations.test.ts`（6 例）：直写**有且仅有**
   在三条门禁全过时为真，且门禁关着时的工具说明里**不得**把不可用的能力说成可用。

## 回退约束的落实

任务书原文：**关闭相关能力开关；保留执行日志与未决恢复数据；不得通过覆盖用户文件实现代码回滚。**

- **关闭相关能力开关**：`direct_write_enabled` 现在多一个与项 `g4_concurrency_fault_passed`（§5），
  而它在今天为假；LWB-032 §7 / §8 已经钉住「开关关掉时真正的写入被拒、且不建立操作行」。
- **保留执行日志与未决恢复数据**：§7.13 与 §8.5 分别确认「待恢复的操作从那个入口找得到」
  与「停在 `VALIDATING` 的操作被 `listUnfinished()` 找到」；§7.11 的折叠结论是 `unfinished`
  而不是任何一种「收场了」。
- **不通过覆盖用户文件实现代码回滚**：本任务的全部取证都在临时目录里，
  而每一格的判据都是**盘上的字节**（§1.2、§2.1、§3.2、§5.2、§7.6）——
  这一轮里没有任何一次执行是靠「写回去」来让断言通过的；恢复的两条自动路径
  （§3 的两个停机点）都是**零字节**定案。

## 这一轮里发现并改掉的三处

**两处是产品里的真实缺陷**，共同点是「库这一层看不见」：单元测试全绿，
而出问题的那条路径只有把真护栏、真进程、真盘用起来之后才会走到。

1. **一句自相矛盾的回滚报告**（`packages/executor/src/apply.ts`）。`rolled_back` 允许带着
   `untouched` 的条目，而 `untouched` 最主要的两种成因（基线哈希不符、对象已经换人）
   本身就意味着**盘上已经不是执行之前的样子了**。原来的措辞一律说「工作区回到执行之前的样子」，
   于是同一份报告里会同时出现「独立回读看到的是…与基线不同」与「工作区回到执行之前的样子」。
   现在按 `untouchedCount` 分成两句话。一份自相矛盾的报告比一句含糊的话糟得多：
   它把「别人改过盘」这件事从报告里说没了，而那正是操作者此刻最需要知道的。
2. **把一个未知印成了已知**（`packages/executor/src/native-adapter.ts` + `packages/recovery/src/service.ts`）。
   见 §2.2：护栏失败原来被压成两句二选一，而客户端合成的 `NATIVE_GUARD_UNAVAILABLE`
   一个字节的下落都没说，却被印成了「已进入破坏性区域」。判据现在是三句，
   三处报告 + 一处恢复日志同时改用 `guardVerdictClause`。

**一处是装置本身。**

3. **「助手还在不在」的探测器每次把自己数进去**（`tests/fault-injection/fault-rig.ts` 的
   `guardHelperPids`）。查询自己也是这个 node 进程的 pwsh 子进程，而它的命令行里就写着
   `WinfsGuard.ps1` 那半句过滤器 —— 于是每一次调用都比实际多一个 PID。
   杀伤面不止于多一个数：「助手还在不在」正是这一组用例里唯一用来证明**故障真的落地了**
   的观察，而一个每次都比实际多一个的探测器会让「还看得见」与「已经不在」这两句话同时变得不可信。
   这个缺陷是本脚本 §7.1（断言进程表里恰好一个助手）撞出来的。
   三处均记在 `docs/PROGRESS.md` 的偏离项 **132–134**。
