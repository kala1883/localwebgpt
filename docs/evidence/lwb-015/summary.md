## 1. 验收标准逐条

### 验收标准 1 · 搜索能找到已保存未提交的变更，不需要云端索引

```
PASS 刚写下的字节立刻搜得到，且命中位置与磁盘上的字节一致 — 命中=["src/app.ts:2","src/many.txt:1","src/many.txt:2","src/many.txt:3","src/many.txt:4","src/many.txt:5","src/util.ts:1"] 首条 column=10 片段="  return \"zzneedlezz\";"
PASS 这些命中确实来自本次读取（读到的字节数与计数字段对得上） — scanned_files=4 scanned_bytes=208
PASS 内容改了，下一次搜索立刻看到改后的（同一个进程，因此也没有进程内缓存） — 改写前=[] 改写后=["change/live.txt:1"] 片段="after zzneedlezz"
PASS 整次搜索没有写下任何索引或缓存：搜索前后整棵树逐条相同 — 搜索前 24 条 / 搜索后 24 条 / 新增=[] 消失=[]
PASS 「不需要索引」的结构性证据：护栏的写操作与建文件操作一次都没有被调用 — writeFileGuarded=0 次 createFileGuarded=0 次 / 读取 11 次 / 列举 5 次
PASS 覆盖范围对得上：结果里的「扫了多少 / 拒了多少 / 跳过了多少」与这棵树一致 — scanned=11(期望 11) denied=3(期望 3) skipped=0(期望 0) 未被看到=2（目录里的文件不算「跳过」） secret=4（scanned 的子集，内容已被抽走）
PASS 真的没有匹配时说得清：complete=true 且命中为空（不是「没看完」） — 命中 0 条 / complete=true / scanned=1 / skipped=3（glob 未匹配）
```

**「不需要云端索引」不是一句声明，是四条各自独立的观察。**

1. **沙箱里没有 Git 仓库。** `src/` 下的字节是刚写下去、从未提交的普通文件 ——
   「已保存未提交」与「已提交」在搜索眼里没有区别，因为它根本不知道 Git 存在。
   第二行的 `scanned_bytes=208` 与磁盘上的文件大小逐字节相同（4 个文件、
   208 字节，可用 `wc -c` 复核），因此那些片段确实是从**本次**读取的字节里切出来的。
2. **判据落在位置与内容上，不是「碰巧有那条路径」。** 第一行断言的不只是
   「命中了 `src/app.ts`」，还有 `column=10` 与片段逐字等于
   `  return "zzneedlezz";` —— 一个「只按文件名匹配」的实现会返回同样的路径，
   但给不出列号，也切不出这段片段。
3. **同进程内改写立刻可见。** 第四条比较的是同一个进程里的两次调用：
   任何进程内缓存都会让第二次返回第一次的答案。第三次比较的是磁盘上的树 ——
   搜索前后逐条相同，一个索引文件/缓存目录都会在这里现身。
4. **写操作零调用。** 计数器把 `writeFileGuarded` / `createFileGuarded` 包起来，
   真被调到就抛错（不是「记一笔然后放行」）。这是「不写盘」的**结构性**证据：
   索引不可能存在，因为它从来没有被写下来过。

**第七条是前六条的反面，缺了它前六条可以被一个「什么都不返回」的实现满足。**
它要求 `complete=true` 且命中为 0 时，**遍历确实走完了**那棵子树
（`scanned=1`，另外 3 个文件因 `path_glob` 被排除）。「没有匹配」这句话只有在
`complete=true` 时才允许被当真，而这条把那个词与它描述的事实钉在一起。

**第六行是计数与磁盘的对账，不是常量断言。** 期望值由 `@lwb/policy` 的规则表
作用在 `readdir` 读到的真实目录上算出（`expectedCounts()`），实现里没有任何一个
数字是抄进断言的。对账过程顺带钉下了两件容易漏的事实：

- **目录不进任何计数**（契约里三个计数说的都是文件）。没进入的目录里的文件
  **从未被看到** —— 于是 `.ssh/id_rsa` 既不在 `denied_files` 里，也不在
  `skipped_files` 里（`未被看到=2`：它和 `node_modules/pkg/index.js`）。
  把「跳过的目录里的文件」算成 `skipped_files` 会让每一份真实仓库上的每一次
  搜索都报一组虚高的数字。
- `denied=3` 里的第三个不是路径规则拒的：`ghp_000…000.txt` 按路径规则是
  **允许**的，它被拒是因为**名字本身**命中了 `github-token`（`screenText(name).has_certain`）。
  归宿相同、判据不同 —— 对账函数里把这条写成了两个并列的条件。

### 验收标准 2 · 秘密标记不会出现在命中片段中

```
PASS 四种凭证形态（令牌与命中同行 / 令牌在别的行 / 私钥正文 / 片段起点字边界）都不返回内容 — secret_files=4 泄露片段=[] 命中=["secrets/likely.txt:1"]
PASS 被抽走内容的文件连**文件名**都不返回 — 结果里出现过的路径=["secrets/likely.txt"]
PASS 整份文件的凭证被抽走时，本次搜索**不失败**，其余文件照常返回 — complete=false 边界=["SECRET_WITHHELD"] 原因=有 4 个文件里出现高置信度凭证，其内容已被整份丢弃，不会返回其中任何内容。
PASS likely 档的赋值形状：片段被脱敏，标记值不出现，且如实标了 redacted — redacted=true 片段="zzneedlezz password = \"[REDACTED:keyword-secret-value]\""
PASS 片段起点处的字边界：整份文本判不出、片段判得出，且这个文件仍然被整份丢弃 — 整份文本 has_certain=false / 片段 has_certain=true / 该文件 secret=1 命中=0
PASS 硬拒绝与搜索排除的路径：名字与内容都不出现在结果里（`.env.example` 同样不豁免） — 泄露片段=[] / denied=3 excluded=0
PASS 「没扫到」的判据是护栏**从没被问过**这些路径，不是「结果里碰巧没有」 — 列举过的路径=["","change","docs","secrets","src"] / 读过的路径数=11
```

**判据是 `JSON.stringify(结果)` 里不含那些片段。** 只断言「不在 `matches` 里」
是不够的：泄露可以从 `incomplete_reason`、错误消息、乃至游标载荷里发生。
样本是 `ghp_`、`PRIVATE KEY`、`MIIEowIBAAKCAQEA`（私钥正文前缀）、
`AKIABBBBBBBBBBBBBBBB`（AWS 键形状）、`hunter2hunter2` 五个片段。

**四种形态各有一条真实夹具，因为它们的拦截点不同：**

| 夹具 | 凭证在哪 | 拦在哪一层 |
|---|---|---|
| `secrets/on-line.txt` | 与命中**同一行** | 文件级预筛（逐片筛查也能拦住） |
| `secrets/other-line.txt` | 在**没有命中**的那一行 | 文件级预筛（逐片筛查**拦不住**：那一片里没有凭证） |
| `secrets/notes.txt` | 私钥**正文中间**（命中也在正文里） | 文件级预筛（逐片筛查**拦不住**：跨行形状被切成一行后没有规则认得出） |
| `secrets/boundary.txt` | 命中行的**片段起点正好是令牌** | **逐片**筛查（文件级预筛**拦不住**：整份文本里前边界不成立） |

第三与第四行是这份表格的两个极端，也是两条设计各自的存在理由：

- **「判整个文件」的代价与理由。** 前两列的三种形态都只有文件级预筛拦得住，
  而它的代价是**每个被扫描的文件都要跑一遍全量筛查**（实测 16 MiB 约 73–264 ms，
  视内容而定）。这与 `file_read` 的代价同阶（那条路径本来就把整个文件交给
  `emitContent` 筛一遍），真正的兜底是 deadline（每个文件之前判一次）。
- **逐片那一遍不是冗余。** 第五行的两个布尔是**在屏幕上算出来的**：
  `screenText(整行).has_certain === false` 而 `screenText(片段).has_certain === true`。
  原因是 `\b` 在**输入起点**处成立 —— 令牌前面接一个词字符时整份文本判不出，
  而从令牌第一个字符起切的片段判得出。反过来也成立（私钥那一条）。
  两个判定**互不蕴含**，因此两道都在。

**`secret_files` 是「内容被抽走」，不是「本次搜索失败」。** 第三行明确要求
一次搜索里有 4 个文件被丢弃时，其余文件照常返回、并且用 `complete=false` +
`SECRET_WITHHELD` 说清楚覆盖范围有洞。与 `file_read` 的处置（certain 档
**抛错**）不同，理由写在 `scan.ts` 文件头：一次局部的问题不该毁掉整次操作，
但「丢了什么」必须说出来。

**likely 档是另一种处置，单独采一条。** `password = "hunter2hunter2"` 不会被
拦下，而是被**脱敏**（`redacted=true`，片段里是 `[REDACTED:keyword-secret-value]`）。
断言的是三件事同时成立：标记值不出现、`[REDACTED:` 出现、**命中词仍然在**
（脱敏不该把定位信息一起抹掉）。

**最后两行的对象是路径而不是内容。** 第七行的判据是护栏**从没被问过**
`.ssh` / `node_modules` / `junction`，也**从没读过** `.env` / `.env.example` /
`.ssh/id_rsa` / `node_modules/pkg/index.js`：一个「先读进来再过滤」的实现会给出
同样的结果对象，但它已经把那些字节读进了进程内存。被硬拒绝的文件连列出都没有
（`列举过的路径=["","change","docs","secrets","src"]`）。

### 验收标准 3 · 超时返回部分结果而非错误宣称没有匹配或已经检索全仓

```
PASS 装置前提：`src` 一次搜完是 7 条命中（后面几条「提前停下」的用例都以它为分母） — 命中=["src/app.ts:2","src/many.txt:1",…,"src/util.ts:1"]
PASS 时间预算到点：返回**已经找到的**命中，不是空结果，也不是错误 — 命中 6 条=["src/app.ts:2","src/many.txt:1","src/many.txt:2","src/many.txt:3","src/many.txt:4","src/many.txt:5"] / 读了 2 个文件
PASS 并且明说「没检索全仓」：complete=false + deadline_exceeded + 原因里带预算值 — complete=false deadline_exceeded=true 原因="已达到时间预算 3000 ms，本次搜索提前结束，结果只覆盖已扫描的部分；请用 next_cursor 继续。"
PASS 并且给出可续读的游标（锚点落在最后一条已返回的命中之后，而不是从头再来） — truncated=true 游标=已签发（457 字符）
PASS 用那条游标续读：与第一次的部分结果拼起来，恰好等于一次搜完（不重不漏） — 第一段 6 条 + 续读 1 条 = ["src/app.ts:2","src/many.txt:1",…,"src/util.ts:1"]
PASS 真时钟下预算为 0：一个文件都没读，且**仍然**声明不完整（不是「没有匹配」） — 命中 0 条 / 读 0 个文件 / complete=false / 原因="已达到时间预算 0 ms，本次搜索提前结束，结果只覆盖已扫描的部分；没有可续读的位置，请缩小 path 范围或收窄查询后重试。"
PASS 字节预算到点：同样返回已找到的部分结果，并说清是字节上限而不是时间 — 命中 1 条=["src/app.ts:2"] / scanned_bytes=51 / 读了 1 个文件 / 原因="已达到单次扫描字节上限 40 字节，本次搜索提前结束，结果只覆盖已扫描的部分；请用 next_cursor 继续。"
PASS 取消：返回已经找到的部分结果，标 cancelled，且**不**声称已经检索全仓 — cancelled=true 命中 1 条 / complete=false / 原因="本次搜索已被取消，返回的是已经找到的部分结果。"
PASS 分页：翻完所有页与一次搜完逐条相同（页满时那条「还有更多」的证据是真的） — 一次搜完 7 条 / 分 3 页 / 拼接 7 条 ["src/app.ts:2","src/many.txt:1",…,"src/util.ts:1"]
PASS 游标与查询绑定：换一个查询串复用同一个游标会被拒绝，而不是拿它继续扫 — 码=READ_TOKEN_STALE 理由=CURSOR_QUERY_MISMATCH
PASS 目录装不下时取第二个窗口：排在护栏硬上限之后的候选照样被扫到 — 命中=["w/z.txt:1"] denied=1004（> 护栏硬上限 1000）/ scanned=1
PASS 硬拒绝的文件一个字节都没读：走完整个目录的代价是列举，不是读取 — scanned_files=1 scanned_bytes=33
```

**这一条有两个反面**，两个都要防：

- 「宣称没有匹配」—— 提前停下时返回空结果，调用方会以为真的没有。
- 「宣称已经检索全仓」—— 返回了一部分却不说，调用方会以为这就是全部。

第一行是**分母**：`src` 一次搜完是 7 条。没有它，后面几条「返回了 6 条」
可以是一个永远只返回 6 条的实现。

**时间预算那条用的是计数假时钟，因为真时钟测不了这个形状。** `clock()` 在
每个候选文件**之前**被读一次（`search.ts` 的 `offerFile`），因此「扫了两个文件
之后超时」可以确定地造出来 —— 磁盘、字节、护栏全是真的，只有读数被替换。
真时钟下想造出「恰好第三个文件前超时」，只能靠等，而等出来的用例在机器变快或
变慢时会翻面（本项目的测试套件里真出现过这类翻面，见 §4.3）。
作为对照，第六行是**真时钟**：`search_time_budget_ms: 0` 让 deadline 在第一次
判断时就已经过期，`确定地`得到「一个文件都没读 + 仍然声明不完整」。
两条一起才说明这条路径既不依赖假时钟，也不依赖「碰巧超时」。

**第五行是「可续读」这三个字的分量所在。** 一条游标只要签发得出来，
就总能通过「形状对不对」的检查；只有把它**再用一次**，才能知道它指的
位置对不对：第一段 6 条 + 续读 1 条 = 一次搜完的 7 条，一条不重、一条不漏。
锚点取的是**最后一条已返回的命中**而不是「从头再来」（第三行），
因此续读不会重复返回已经给过的片段。

**第十行的判据刻意有两条，缺一不可。** 第二工作区里 1005 个条目 > 护栏的
1000 条窗口，`z.txt` 排在第二个窗口里。只断言「找到了 `z.txt`」会被一个
「只取第一个窗口 + 恰好没找到也不报错」的实现蒙混过关；只断言
`denied_files=1004` 又说不清遍历是否真的推进了。两条一起才说明
`after_name` 续窗这条路真的走通了。第十一行补上代价的那一面：
1004 个硬拒绝文件**一个字节都没读**（`scanned_files=1`）。

## 2. 实测：只有真实文件系统才暴露的行为

### 2.1 名字即凭证的文件走的是**另一条**判据

`ghp_000…000.txt` 按路径规则是**允许**的（`classifyFile` 返回 `allow`），
它被拒是因为**文件名本身**命中了 `github-token`。这条只有把计数与真实目录
对账时才会浮出来：`denied=3` 而按路径规则算只有 2 个。写进 `expectedCounts()`
之后，这个数字从此是**算出来的**，不是抄下来的。

### 2.2 没进入的目录里的文件，既不算「拒绝」也不算「跳过」

`.ssh` 是**目录**，`HD-CREDENTIAL-STORE` 在列举阶段就把整个条目丢弃，
因此 `.ssh/id_rsa` 从未被枚举 —— 它不在 `denied_files` 里，也不在
`skipped_files` 里，在 `files_seen` 里也没有。Junction 同理（重解析点不进入）。
把这两种文件算进任何一个计数，都会让计数与「实际看过的文件」脱钩，
而计数正是调用方判断覆盖范围的唯一依据。

### 2.3 覆盖率与「整次调用看不完」在搜索里是同一件事

护栏的目录窗口（1000）与搜索的页面上限（100）都可能先到。第十行那一条
证明的是「窗口续取在搜索路径上也成立」：桩里 `has_more` 从来没有为真过
（`tests/search/` 的桩镜像了 1000 这个上限，但夹具从来没有大到越过它），
因此这条只有真实护栏 + 真实大目录才测得出来。

## 3. 偏离项与设计取舍

### 3.1 预筛判**整个文件**，代价是每个文件一次全量筛查（偏离项 33）

判据取自整份解码后的文本，而不是「拼出来的片段里有没有」。理由见
验收标准 2 的表格（跨行形状的凭证在被切成一行的片段里认不出来）。
代价是实测的：16 MiB 约 73–264 ms（视内容而定），而这是**每个被扫描的文件**
都要付的，不管它有没有命中。三处缓解写在 `scan.ts`：
`MAX_READABLE_FILE_BYTES` 在读取之前就把超大文件挡在外面、
`MAX_SEARCH_SCANNED_BYTES` 管住一次调用的总量、deadline 兜底。
本任务**没有**做「先看有没有命中再决定要不要全量筛查」这种优化：
那会形成一个「命中越少筛得越少」的形状，而漏筛的那一类正是
「凭证所在的行没有命中」的文件。

### 3.2 逐片筛查保留，因为它管的不是同一件事（偏离项 34）

两个判定互不蕴含（§1 验收标准 2 的表格）。这条**在本任务里被证成了事实**，
而不是留在注释里：第一版夹具只做了前边界那一半，于是两个布尔都是 `false`
—— 也就是说那条用例当时测的是「没有凭证的文件」（见 §4.1）。
现在两侧都在屏幕上断言，夹具一旦落不到边界上，用例立刻失败。

### 3.3 `secret_files` 是 `scanned_files` 的子集，且不让整次搜索失败（偏离项 35）

与 `file_read` 的 certain 档**抛错**不同：搜索里被抽走内容的文件计入
`scanned_files` 与 `scanned_bytes`（字节确实读了），另外单独计
`secret_files`，并把 `complete` 置为 false。理由是 `file_read` 与搜索的
粒度不同：前者一次只有一个文件，失败是准确的描述；后者一次几百个文件，
一个文件里的凭证不该让剩下的 99% 变成一条错误 —— 那样在大仓库里搜索
永远不会成功。但**两个口径必须一致**：同一个文件不可能「整体读不出来、
但能搜出一部分」，所以含高置信度凭证的文件在两条路径上都不出站内容。

### 3.4 `skipped_files` 的边界：目录里的文件不算「跳过」（偏离项 36）

`skipped_files = 搜索排除/重解析点的**文件** + 不匹配 glob + 超出单次可读上限 + 打不开`。
没进入的目录里的文件不在其中（它们从未被看到）。这与 LWB-014 的偏离项 31
是同一条道理的另一面：覆盖范围的计数只在「本来看得到、这次没给」的范围内说话。

### 3.5 搜索不读时钟、不持有状态（偏离项 37）

`clock` 与 `now` 都由调用方注入，分页位置全在签名的游标里。
因此：进程重启不丢游标（不需要服务端会话）、测试可以把时间预算对齐到
假时钟、而「超时」这件事不依赖系统时间（`Date.now()` 会被系统时间调整影响，
可能倒退）。代价是调用方必须把两个量都传对，而它们的**刻度必须一致** ——
本任务的测试套件真的栽在这上面过（§4.3）。

### 3.6 限额的调用方覆盖入口仍未接线（偏离项 38，接偏离项 28）

`SearchLimits` 的每一项都可以由本地操作者收紧，**但这条通路本身没有实现**
（与偏离项 28 登记的 `validateLimitOverride` 无调用方是同一件事）。
本任务里它只被测试与证据脚本用来构造边界，**不得**读成「已经生效」。
接线属 LWB-018。

## 4. 采集过程中发现并修复的真实缺陷

### 4.1 证据脚本自己造了一条「测的不是它声称在测的东西」的用例

「片段起点处的字边界」这条第一次采集是 **FAIL**，输出是
`整份文本 has_certain=false / 片段 has_certain=false` —— 两个都是 false，
说明**这条夹具根本没有落在边界上**。原因是我只做了前边界那一半：
令牌前面接了词字符（让整份文本判不出），但没有在令牌**后面**接非词字符，
于是 `aws-access-key-id` 的**尾**边界不成立，整行与片段都不匹配这个规则。

修法不是改断言，是把夹具补全成一个**真的**边界：前接词字符、后接非词字符、
命中列取两倍窗口前置量（让片段窗口的起点正好是令牌的第一个字符）。
补全之后两个布尔分别是 `false` / `true`，用例才第一次测到了它声称的那件事。

教训与 LWB-013 §4.1、LWB-014 §4.1 同一条：**一个用例「跑了」和「验到了它
声称在验的东西」是两件事。** 这次的形态更隐蔽 —— 它没有报错，只是很安静地
通过了断言里的「不返回内容」那一半（因为文件里本来就没有可返回的凭证）。

### 4.2 两个测试用例起初**因为错误的原因**通过

- 「续读位置在探针与列举之间消失 ⇒ 同样不跳过排在它之后的候选」与
  「续读位置在探针与列举之间消失 ⇒ 续读结果与一次搜完一致」：
  夹具里 `a.txt` 恰好只有 3 条命中，而 `max_matches: 3` —— 见证条目与游标
  都落在了 `b.txt` 上，于是删掉 / 藏起 `a.txt` 与这两条用例毫无关系。
  发现方式是**把 `walk.ts` 的竞态兜底改成 `return false` 之后，两条用例仍然通过**。
  修法：`a.txt` 改成 5 条命中，并加一条**装置前提**的用例把第二页钉成
  `['a.txt:4','a.txt:5','b.txt:1']`。
- 「真实 junction 不被跟随」：断言是 `命中里没有 junction 前缀的路径` —— 零命中的
  结果也能满足它。它**真的**在一次机器负载较高的全量运行里通过了（那次运行里
  6 条真实护栏用例全部返回空结果，见 §4.3）。修法是加一条正向的装置前提：
  `data.matches.length > 0`，失败消息里带上 `incomplete_reason`。

**两条都做了「反向验证」**：把兜底改坏之后用例必须失败。本文件末尾的两次
负向验证是**本次重新执行**的，不是上一轮的引用。

### 4.3 `clock` 的基准取在进程启动时刻 ⇒ 全量运行下 6 条真实护栏用例全部返回空结果

`tests/windows/files-search.test.ts` 首次全量运行时 6 条里 5 条失败、结果全空。
根因不在实现：`clock: () => NOW + performance.now()` 量的是**进程**启动以来的
时间，而 `SEARCH_TIME_BUDGET_MS` 说的是「一次搜索最多花多久」。并行跑测试文件时
`before` 钩子可能已经花掉 7–9 秒，于是 3 秒的预算在第一次判断时就已经过期 ——
**而空结果看起来像「搜索坏了」，不像「测试写错了」**。

修法：把基准取在 `depsFor()` 被调用的那一刻（每次搜索调用一次），
并在文件头把这个陷阱写清楚（`now` 与 `clock` 是两个刻度不同的量，
一个说「现在几点」、一个说「过了多久」）。修改后连续三次全量运行均为
767/767。

## 5. 脱敏

本文件的夹具里所有凭证都是**形状合规的假值**（`ghp_` + 40 位、`AKIA` + 16 位、
PEM 正文、`password = "…"`），不是真实凭证，也不来自任何真实系统。

- 采集脚本**不打印任何凭证值**：输出里只有布尔、计数、长度、规则名
  （`[REDACTED:keyword-secret-value]` 是规则标识，不是值）与假值本身被
  **断言缺席**的那些片段名。
- `泄露片段=[]` 这一列是运行时的实际比对结果：脚本对
  `JSON.stringify(结果)` 逐个查找 `ghp_` / `PRIVATE KEY` / `MIIEowIBAAKCAQEA` /
  `AKIABBBBBBBBBBBBBBBB` / `hunter2hunter2`，找到任何一个就把该条判为 FAIL
  并把片段打出来 —— 也就是说，**这份日志之所以干净，是因为它在运行时不干净就会自己报警**。
- 沙箱与 junction 目标都在 `%TEMP%` 下的独立临时目录里，运行结束后删除。
