## 0. 这一轮的证据是在什么装置上采的

四条步骤的原文：

> 1. 应用前验证全部既有目标与快照；所有旧/新 blob 持久化完成后才能写入工作区。
> 2. 对每个文件记录 intent、观察身份、已写/已刷盘/已验证状态；数据库提交与文件刷盘之间保留可恢复断点。
> 3. 普通失败在仍持有安全句柄时有界恢复；恢复失败进入 RECOVERY_REQUIRED。
> 4. 完成回执记录逐文件实际状态与 aggregate 状态，不把部分完成当全成功。

三条验收标准的原文：

> 故障注入覆盖每个日志边界以及第一、中间、最后一个文件。
> 快照持久化失败时目标文件零写入。
> 批量失败不会调用 Git reset/checkout/stash/clean。

| 段 | 装置 | 为什么非这样不可 |
| --- | --- | --- |
| §0 | 真护栏后端的**自述** + `PRAGMA table_info(journal_entries)` | 「零迁移」这句话要用真库验，不能读源码得出 |
| §1 ② | 在**第一次写入调用**的那一刻去磁盘上找全部旧/新快照 | 步骤 1 说的是**次序**，而次序只能在一个时刻上量 |
| §1 ③ | 逐条目四个阶段 + 全局 `seq` 严格递增 | 「可恢复断点」的可核对形式是「账上的顺序」 |
| §2 | 真盘上失败在**中间**那个文件，逐个文件比对字节 | 验收标准点名要「第一、中间、最后一个文件」 |
| §3 甲 | 让**收回本身**也被拒 | 「恢复失败 ⇒ RECOVERY_REQUIRED」只有在收回失败时才被走到 |
| §3 乙 | 把已登记的快照对象从盘上删掉 | 「快照持久化失败 ⇒ 零写入」的构造 |
| §4 | 在 `intent` 与 `verified` 两个边界上把进程停住 | 十个边界里最能说明问题的两个（其余八个见 §9 的 NOT_RUN） |
| §5 | 合成的日志行喂给折叠函数 | 见 §5.1：真盘上造不出「写成了、又没轮到、且没失败」 |
| §6 | 一句**带着工作区根**的护栏原话穿过三条出口 | 这一格量的是本轮修掉的那个洞 |
| §7 | 真 `git` 仓库**当工作区**，跑一次失败的批量 | 动态负实验；静态判据与它合起来才算数 |

### 0.1 §5 为什么可以喂合成的日志行

折叠函数 `aggregateOf` 的输入是 `readItemEvents` 会返回的**那种行**，不是某次执行本身。
真盘上要稳定造出「条目一号写成了、条目二号没轮到、而循环**不是**因为失败才停下」很别扭 ——
本工程的循环在第一个失败处就停（`apply.ts` 的阶段 C），因此「没轮到」在真盘上**总是**伴随一次失败。

于是这一节直接把 `ItemEvent[]` 造出来喂进去。**这不削弱断言**：
§5 问的是「折叠会不会把部分完成说成全成功」，而那是一个纯函数上的问题；
真有执行的那一半（一次成功、一次中间失败、一次收回失败）在 §1、§2、§3 甲 各有一格。

## 1. 正向 —— 三个文件真的写成，逐条目日志四步齐全

```
PASS ① 交回 applied（不是 no_change、不是 refused） — kind=applied
PASS ② 步骤 1：**第一次写入调用**的那一刻，全部条目的旧/新快照都已经在磁盘上 — 第一次写的是 src/a.txt；判据是每个条目的 old_blob_id / new_blob_id 都能在对象目录里找到
PASS ③ 步骤 2：src/a.txt 的四个阶段逐一落库且顺序正确 — item_intent → item_written → item_flushed → item_verified
PASS ③ 汇总：三个条目都走完四步
PASS ③ 日志序号严格递增且不重复（恢复流程靠顺序表达「先意图、后结果」） — seq=0,1,2,…,11
PASS ④ 三个文件的磁盘字节都等于各自已批准的 target_sha256
PASS ⑤ 步骤 4：`applied` 的报告附带逐条目小结（不是一句「全部成功」） — 全部 3 个条目已按计划写入并核验。逐条目：已写入并核验 3
PASS ⑥ 适配器止步于 APPLYING —— 终局由协调器的收尾落 — change.state=APPLYING
PASS ⑦ 折叠结果是 applied — applied
```

**② 是步骤 1 唯一可核对的形态。** 「所有旧/新 blob 持久化完成后才能写入工作区」是一个关于
**次序**的断言，而次序只能在一个**时刻**上量：`onFirstWrite` 钩子挂在护栏边界上，
它回调的那一刻在任何字节落盘之前，钩子里去对象目录把每个条目的 `old_blob_id` 与
`new_blob_id` 都 `existsSync` 一遍。少一个就 FAIL。

五个条目共 10 个 blob，其中任何一个没落盘，这一格都会红 —— 而只要它绿，
「先持久化、后写入」这句话在这一组构造下就是**被反证过**的，不是被相信的。

**⑥ 与 ⑦ 合起来才完整。** 适配器止步于 `APPLYING`（它不自己改判终局），
而折叠给出的 `applied` 是**账本的结论**。两个数字分开报，是因为它们出自两处：
前者是状态机那一侧，后者是日志那一侧 —— 一个实现完全可能两者不一致。

## 2. 故障在中间那个文件 —— 有界恢复把字节写回基线

```
PASS ① 报告是 rolled_back（不是 applied、不是「部分成功」） — kind=rolled_back
PASS ② 报告逐条目：1 个已回到基线、2 个未改动 — ……（逐条目：已回到基线 1；未改动 2）。
PASS ③ 一号文件**逐字节**回到执行之前（真盘哈希比对）
PASS ④ 二号文件从未被碰过
PASS ⑤ 三号文件从未被轮到
PASS ⑥ 一号的日志终局是 restored（写成了、又收回来了） — item_intent → item_written → item_flushed → item_verified → item_restored
PASS ⑦ 二号的日志终局是 untouched（护栏没越过破坏性区域） — item_intent → item_untouched
PASS ⑧ 「没轮到」被单独补记 —— 与「动过了但没记」在账上分得开 — item_untouched
PASS ⑨ 折叠结果是 rolled_back — rolled_back
PASS ⑩ 三个条目**都有终局** —— 缺一条，折叠就会说「说不清」 — 账上有结论的条目数 3
```

③④⑤ 是**三个不同的事实**，任何两个都不能推第三个：

- ③ 说「写下去的字节收回来了」（真盘哈希比对，不是看返回值）；
- ④ 说「失败的那个**一个字节都没动**」（护栏没带 `touched`，另外独立回读也证实了）；
- ⑤ 说「后面的**连一次护栏调用都没有发生过**」，因此账上那条 `untouched` 是**补记**的
  （`noteNotAttempted`）—— 它记的是「循环在它之前就停了」，而不是「我们去看过它」。

⑩ 是 §2 与 §5 的接缝：只要有一个条目**没有**终局，折叠就会退回 `unfinished`，
而 `unfinished` 会要求人工核验**一批从来没被碰过的文件**。补记那一步正是为此存在。

## 3. 甲：收回失败 ⇒ 待恢复；乙：快照没了 ⇒ 零写入

### 3.1 甲 —— 普通失败在仍持有安全句柄时有界恢复，恢复失败进入 RECOVERY_REQUIRED

```
PASS ① 抛出 RECOVERY_REQUIRED（不是交回一份 rolled_back 报告） — RECOVERY_REQUIRED
PASS ② 病因是「写到一半失败」，且指明了是哪个路径 — {"reason":"WRITE_FAILED_MIDWAY","change_id":"chg_0027",…,"path":"src/b.txt","write_mode":"edit_text",…}
PASS ③ 一号文件上确实**留着**本次执行的字节 —— 这是「没能收回」的磁盘证据 — 磁盘 e424b0779e83f77a… vs 基线 5deda86e6e67ba21…
PASS ④ 二号文件原样
PASS ⑤ 一号的日志终局是 restore_failed（不是 restored） — item_intent → item_written → item_flushed → item_verified → item_restore_failed
PASS ⑥ 折叠结果是 unfinished —— 「说不清」而不是「收回来了」 — unfinished
```

③ 是这一节的**核心**：它证明「没能收回」不是一句措辞，而是磁盘上真的留着一份
与基线不同的字节。一个把 `restore_failed` 当成 `restored` 记的实现，
在这一格上会同时交出 `rolled_back` 与「工作区回到执行之前的样子」—— 而磁盘不是那样。

**注意 ① 与 §2 ① 是相反的两格，而它们的区别只在收回成不成功**：
§2 里收回成功了 ⇒ `rolled_back`（干净的报告）；这里收回失败了 ⇒ 抛。
抛出而不是返回报告，是因为返回报告等于**宣称自己知道磁盘的状态**，
而 `unfinished` 恰恰是「不知道」。

### 3.2 乙 —— 快照持久化失败时目标文件零写入

```
PASS ① 删除动作本身生效了（先证明这个实验不是空跑）
PASS ② 报告是 refused — kind=refused
PASS ③ 拒绝理由说的是快照取不到，而不是别的 — 拒绝执行 1 个条目，未写入任何字节。「src/b.txt」：取不到本条目的目标快照：快照对象缺失，拒绝继续（极可能是状态库与磁盘不一致）：objects/42/42f054…
PASS ④ 验收：目标文件**零写入**（a）
PASS ⑤ 验收：目标文件**零写入**（b）
PASS ⑥ 一个字节都没写，就没记执行意图（状态还是 VALIDATING） — change.state=VALIDATING
PASS ⑦ 账上一条条目级日志都没有 — 0 条
```

⑥⑦ 是「零写入」这句断言的**另一半**：只查磁盘上文件没变是不够的 ——
一个先记了执行意图、再发现快照缺失的实现，磁盘上同样什么都没变，
但它把账推到了 `APPLYING`，于是**下一个读账的人**会以为「字节可能已经在盘上了」。
**磁盘干净与账本干净是两件事，这一节两件都断言。**

### 3.3 一处发现：这一格拦在**阶段 A**，不是 A2

本节的标题原本写作「快照在阶段 A 通过之后、阶段 A2 之前消失」。**实测不是。**
把已登记的快照对象从盘上删掉，拒绝发生在**阶段 A 的核查**里
（`vet` 逐个条目取目标快照时就发现对象缺失），比阶段 A2 那条「持久化边界」更早。

这不是缺陷，是**更便宜也更早**的失败点：A 阶段本来就该去取那份快照。因此：

- 验收标准要的「快照持久化失败 ⇒ 目标文件零写入」**已经满足**（本节的七条断言）；
- 而「恰好停在 A 与 A2 之间」这个**更窄**的构造，在真盘上要再开一个注入点才造得出来，
  因此它归单元测试的 H 组（见 §9）。

这段写在这里而不是悄悄改个标题，是因为**证据里最容易被做掉的一件事，
就是把没做到的构造说成做到了**。

## 4. 日志边界 —— 停在半路的进程，账上与盘上各说了什么

### 4.1 甲：停在 `verified` ⇒ 盘上已是目标字节，账上只有意图

```
PASS ① 注入确实生效（异常带着那句话） — 注入：在 item_verified 这个边界上进程停住
PASS ② 盘上**已经是批准过的那份内容** —— 这是最危险的一格
PASS ③ 账上只有 intent：三条回执日志在同一个事务里，第三条抛了，前两条一起回滚 — item_intent
PASS ④ 折叠结果是 unfinished（宁可说不知道，绝不说写成了） — unfinished
PASS ⑤ 报告里的逐条目小结把这一条标成「状态不明」 — **状态不明（账上只有意图）** 1。需要人看的条目：「src/a.txt」：准备写入这个条目。
```

**这一格是整个任务里最值得读的一格。** 它同时展示了两件事：

1. **盘上已经是批准过的那份内容** —— 用户看到的是「文件已经改了」；
2. **账上只有一条 `intent`** —— 而 `intent` 的含义是「我打算写」，不是「我写了」。

因此「按这本账折出来的结论」是 `unfinished`（§4.1 ④），交给人的那句话说的是
「**状态不明（账上只有意图）**」（④ ⑤），而**不是**「没写成功」。
这是刻意的：`unfinished` 会要求人工看一眼，而「没写成功」会让人以为不用看。

③ 里那句「前两条一起回滚」是**设计**，不是实现细节：三条回执日志
（`written` / `flushed` / `verified`）写在**同一个** `deps.repos.transaction(...)` 里，
因此中途抛异常时它们要么全在、要么全不在。代价是「盘上写了、账上不知道」这一格**存在**；
换来的是**不存在**「账上写了、盘上没写」那一格 —— 后者会让恢复流程去回滚一份
根本不存在的改动。两害相权，选前者。

### 4.2 乙：停在 `intent` ⇒ 盘上零改动

```
PASS ① 盘上逐字节还是执行之前那一份
PASS ② 账上一条日志都没有（这条日志就是它自己，它没落上）
PASS ③ 折叠结果是 unfinished — unfinished
```

**「账记不上就不许写」在这里是可核对的**：`intent` 那条日志自己写在
一个隐式事务里，且在**任何护栏调用之前**。它没落上 ⇒ 循环没走到写入那一步 ⇒ 盘上必然没动。
一个把这句顺序颠倒过来的实现，在这一格上会留下「有字节、没记录」的现场。

## 5. 步骤 4 的反方向 —— 部分完成绝不被折叠成全成功

```
PASS ① 逐条目：一个是 written、一个是 untouched — written,untouched
PASS ② 折叠结果是 unfinished —— 部分完成绝不被当成全成功 — unfinished
PASS ③ 反方向也成立：单条目全部 written 才是 applied — applied
PASS ④ 账本少一个条目就不算完（`expectedItems` 是硬判据） — unfinished
PASS ⑤ 报告会把「没轮到的那个」记成未改动，而不是沉默地漏掉 — 已写入并核验 1；未改动 1
```

**② 是本任务第二句验收标准的正题**，而 ③ 是它的对照：同一个折叠函数，
单条目全写成时**必须**给 `applied` —— 否则「不给 applied」这件事本身没有意义
（一个永远返回 `unfinished` 的实现也能通过 ②）。

④ 量的是 `expectedItems` 那个参数：折叠知道该有几个条目，账上少一个就是少一个，
**不会**因为「已有的那些都挺好」而放行。

## 6. 一处真实存在过的脱敏漏洞（已修，并已验证修得住）

### 6.1 洞是怎么发现的

护栏的消息是在**它自己的坐标系**里写的 —— `WinfsGuard.ps1` 的 `Open-Guarded`
把 `$Path`（绝对路径）拼进消息。这句话从 `classifyFailure` 出来之后走三条路：

| # | 出口 | 原本安不安全 |
| --- | --- | --- |
| 1 | 条目级日志 | **安全** —— `appendItemEvent` 在落库前脱敏 |
| 2 | 报告 | **安全** —— 给人看，且出口处还有一道 `sanitize` |
| 3 | **抛出去的 `RECOVERY_REQUIRED`** | **漏** —— 协调器接住它，把 `error.message` 原样写进一条**改动级**日志行 |

第 3 条路上那一行**不经过** `appendItemEvent`，因此**不脱敏**。于是工作区根
会跟着一个异常走进执行日志 —— 而执行日志是要给人看、要留档、要跨会话读的东西。

### 6.2 修法：在**造出那句话的地方**脱敏

`apply.ts` 里有三处拼装护栏原话（`classifyFailure` 的 `guardLine`、
`attemptRestore` 的两条），三处都在源头套上 `redactRoot`。

**为什么不修在出口上**：出口是从代码里长出来的。今天有三个，明天接一个新汇报面
就是四个 —— 而修在源头时，**每多一个出口都自动是安全的**。这条规则比这一次的修补更重要，
因此它写在 `apply.ts` 那段注释里。

### 6.3 验证：先证明测试**咬得住**，再证明它绿

只看绿的断言不能说明什么 —— 一个永远为真的断言也是绿的。因此做了一次**反证**：
把 `guardLine` 那处改回原样、重跑，单元测试 J1 与 J2 **双双变红**，
并把泄漏的那一行原样打了出来：

```
…护栏拒绝（PERMISSION_DENIED，Win32 5）：拒绝访问：C:\lwb-027\repo\src\a.ts。…
```

然后把修改放回去、重跑，两例恢复绿。**这一步是这个补丁唯一有价值的部分** ——
没有它，无法区分「修好了」与「本来就没漏」。

### 6.4 取证脚本里的量法

```
PASS ⓪ 先确认这个标记确实落在工作区根之下（否则本节验的是「根外的路径也没被脱敏」）
PASS ① 这次执行确实留下了日志行 — 3 行
PASS ② 那条护栏原话真的进了账本（否则本节验的是空气） — 护栏拒绝（IO_ERROR，Win32 5）：取证注入：写 <工作区根>\src\a.txt 时被拒。护栏报告已进入破坏性区域。
PASS ③ 没有任何一行日志带着那个绝对路径 — （没有泄漏）
PASS ④ 抛出去的那句话同样干净 —— 协调器会把它的 message 原样写进**改动级**日志行
PASS ⑤ 脱敏发生了，而不是「路径本来就没进去」：那句原话里现在站着占位符
PASS ⑥ 病因一字未动：脱的是根，不是消息的其余部分
PASS ⑦ 账本全文不含本机绝对路径
```

② 与 ⑤ 是这一节的**对照物**，缺了任何一条，其余几条都可能只是在验空气：
② 证明那句带路径的话**真的**进了账本，⑤ 证明占位符**真的**站到了它原来的位置上。

### 6.5 脱敏的**边界**，写清楚它保护什么、不保护什么

`redactRoot` 换掉的只有工作区根**这一个字符串**。因此它的保护范围是
「**根下**的绝对路径」。这不是保守的近似，而是**正好够用**：

- 护栏只会去碰工作区根下的路径，因此它消息里的绝对路径**必是**根下的；
- 根**之外**的路径它压根不会提到 —— 真提到的时候（本机别处的临时目录等），
  这一条不负责，也不该假装负责。

**第一次跑这一节时它是红的**，原因是注入用的那个路径被我放在了工作区根**之外**
（`…\redaction-marker\x.txt` 与工作区根平级）。那是**夹具的错，不是脱敏的错** ——
一处根外的路径本来就不该被这条规则换掉。修法是把标记放进工作区里，
并加一条 ⓪ 先把这件事本身断言掉。这条记在这里，因为它正是 §6.5 那句话的经验来源。

## 7. 验收 —— 批量失败不会调用 Git reset/checkout/stash/clean

### 7.1 静态判据：执行包里连 `child_process` 都进不来

```
PASS ① 静态：执行包里没有任何进程调用（连字符串 `git` 都没有） — 4 个文件 × 6 个模式，零命中
PASS ② 静态：仓库既有的导入护栏仍然拦着 `child_process` — ✅ FsGuard 导入检查通过（已检查 164 个文件，未发现绕过）。
```

`packages/executor/` 在 `scripts/check-fsguard-imports.mjs` 的**业务前缀**清单里，
因此「不调用 git」在本仓库是一条**编译期**性质而不是一句约定：
在那个目录里 `import 'node:child_process'` 会让 `check:imports` 直接失败。

### 7.2 动态负实验：在**真的 git 仓库**里跑一次失败的批量

实验起点刻意布置成「有东西可丢」：一个真 git 仓库、一处未提交的改动（`src/dirty.txt`）、
栈里压着一条（`src/stashed.txt`）。**失败的批量就发生在这个仓库上** ——
它真的往 `src/a.txt` 写了目标字节，又在回滚里把基线字节写了回去。

```
PASS ③ 实验起点是有内容的：栈里有一条、工作区有一处未提交 — stash 1 条；status=["?? src/dirty.txt"]
PASS ④ 那次批量确实失败了，并且确实回滚了 — kind=rolled_back
PASS ⑤  而一号文件回到了工作区原先的那一份（哈希与执行之前逐字节相同）
PASS ⑤′ 而且这次回滚是**有内容**的：批准的那份与基线本就不同，不能靠「什么都没写」蒙混过关
PASS ⑤″ Git 自己也这么说：工作区这份文件的 blob 哈希 == 已提交的那一个
PASS ⑥ 动态：`HEAD` 前后一致（没有 reset、没有 checkout）
PASS ⑦ 动态：`git stash list` 前后一致（没有 stash 进出） — 1 条 → 1 条
PASS ⑧ 动态：`git status --porcelain` 前后一致（没有 clean、没有 checkout）
PASS ⑨ 动态：`git show-ref` 前后一致（没有任何一个 ref 被移动过）
PASS ⑩ 动态：reflog 前后一致 — 2 条
PASS ⑪ 那个仓库里没有任何一次新的提交
```

③⑤′⑤″ 是**三条防线，防的是同一件事：让这几格变成空转**。

- ③ 防「起点本来就没东西可丢」—— 那样 ⑥–⑩ 的「前后一致」全是废话；
- ⑤′ 防「那次批量其实什么都没写」—— 那样「回滚了」这句话没有内容；
- ⑤″ 绕开我自己拼字节时的换行差异：`git hash-object`（会过 filter）与
  `git rev-parse HEAD:<path>`（仓库里那一个 blob）相等，是 **Git 自己**说
  「工作区这一份就是已提交的那一份」。

**⑤″ 是被一次失败换来的。** 第一版这一格用的是
`sha256(磁盘字节) === sha256(Buffer.from(git show HEAD:src/a.txt, 'utf8'))`，它 **FAIL 了** ——
不是因为文件没回去，而是因为 Git 在 `add` 时按 `core.autocrlf` 把 CRLF 存成了 LF，
于是「仓库里的字节」与「工作区里的字节」本来就不相等。
**是判据错了，不是实现错了**；换成让 Git 用**它自己的**哈希来比对之后，这一格才是它该有的样子。

### 7.3 这两半的证明力，各管一段

> **NOTE（逐字摘录）：** 它们证明的是「在这次失败批量的前前后后，那个仓库的 git 状态没有被改动」。
> 它**不**能单独证明执行器从没调用过 git —— 那一条由 ① 与 ② 的静态判据负责
> （`packages/executor` 里连 `child_process` 都 import 不进来，导入护栏会在 CI 上拦下）。
> 两条合起来才是这根验收标准；单看任何一条都不够。

动态那一半有个**天生**的弱点：它只能证明「没留下痕迹」，而一个调用过
`git stash` 又恰好把它恢复原状的实现同样能通过。静态那一半没有这个弱点，
但它只覆盖 `packages/executor/` 这四个文件。**两半合起来**才闭合。

### 8.2 本任务改了 LWB-027 / LWB-028 的 11 处断言（这一节是给读者的交代）

`touched` 取代 `actual_state` 作为「动过没有」的判据，是一次**语义修正**。
它让三处行为的形态变了，而那三处的旧断言写在既有证据脚本里：

| 旧行为 | 新行为 | 为什么新的对 |
| --- | --- | --- |
| 只读目标 ⇒ 抛 `RECOVERY_REQUIRED` | 只读目标 ⇒ `rolled_back` | 连句柄都没开到，`touched` 缺席是「一个字节没动」的**证明**，不是未知 |
| `CREATE_NEW` 撞名 ⇒ 抛 `RECOVERY_REQUIRED` | ⇒ `rolled_back` | 同上；LWB-028 的旧 NOTE 早就把这一次核验记成**多余**的代价 |
| 详情字段 `crossed_truncate` / `object_created` | `guard_verdict` / `guard_touched` | 旧名只说得清「改写」那条路；创建那条路无截断线可越。新名对两条路是同一句话 |

**这几处是「重指断言」，不是「放宽断言」**：每一处都换成了**更具体**的判据
（从「抛了没有」换成「账上那条终局是哪个阶段」+「磁盘字节对不对」），
新增的断言数（LWB-028 从 61 → 64）也没有一条是宽松的。
`object_created` 那一格尤其值得记：新判据 `guard_touched` 是从**代码**里读出来的，
而旧判据依赖的那条「`actual_state` 缺席 = 现场未知」的推理**本身就是错的**。

**这一轮还发现 §5c 的注入夹具本身是自相矛盾的**：它补报一条
**不带 `touched`** 的失败，却在磁盘上留下了一个真的、45 字节的新对象 ——
也就是说那条注入说的是「我什么都没动」，而磁盘在反驳它。修法是给注入补上
`touched: true`（它模拟的本来就是「对象已经建出来了才发现出的问题」）。
**这条记在这里，因为它是「夹具可以撒谎、断言不该跟着撒谎」的一个实例。**
