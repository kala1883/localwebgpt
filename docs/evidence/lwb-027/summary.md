## 0. 这一轮的证据是在什么装置上采的

三条验收标准的原文说的分别是**两次拦截**与**一次回读**：

> VS Code 在检查前保存则冲突；检查后到写入结束的普通竞争保存被共享模式阻止。
> 回读哈希与已批准 new_hash 一致才报告该文件完成。
> 文档明确进程崩溃可能留下部分字节，须进入恢复，不宣称原子替换。

前两条的装置是**同一个**：真盘上的一个真文件，一边是我们的写入路径，另一边是「不受我们管辖的那一方」。

| 段 | 装置 | 为什么非这样不可 |
| --- | --- | --- |
| §0 | 真护栏后端的**自述** | `crash_atomic_replace=false` 是验收 3 里唯一可以被机器核对的那一半。能力标志若含糊其辞，文档里的散文就没有地基 |
| §1 | 真写入 → 真回读 → **另一次**护栏调用独立再读 | 「回读一致」如果是复用写入调用自己的读数，验的就是「它自己说它对」 |
| §2 | 真盘上由**外部**改写 / 删除重建 | 冲突判定的两种形态各有一个判据：内容哈希与**对象身份**。只有后者能拦住「内容碰巧相同」 |
| §3 | 护栏自己的 `holdHandle` + 另一个 `pwsh` 进程的普通保存 | 见下 |
| §4 | 只读目标 / **被内存映射**的目标 | 「句柄能力不足」不是一句设计声明，得在真机上造出来 |
| §5 | 中止点落在**阶段 A 之内** | 施工中由单元测试抓出的一处真实缺陷，见 §5.1 |

### 0.1 验收 1 后半的装置（必须说清楚它证明的是什么）

「我们的写入期间，别人的保存被挡住」严格说需要把 `Op-WriteFileGuarded` 的句柄生命周期摊开给外部看 ——
而它是一次请求内的开→写→刷→回读→关，**没有可以被别的进程插进去的窗口**。

因此 §3 用的是护栏自己的 `holdHandle`：它走的是**同一个** `Open-Guarded`、**同一组**标志

```
access = GENERIC_READ | GENERIC_WRITE        仅此二者
share  = FILE_SHARE_READ                     刻意**不含** FILE_SHARE_WRITE / FILE_SHARE_DELETE
```

只是把「写完就关」换成了「持有」。**它证明的是这组标志的性质**，不是 `Op-WriteFileGuarded` 内部的时序 ——
后者由同一处 `Open-Guarded` 调用保证（`native/winfs/WinfsGuard.ps1`）。

```
PASS ① 持有之前，普通保存是通的（否则「被挡」可能只是文件本来就写不了）
PASS ② 持有期间：普通竞争保存被拒
PASS ② 被拒的保存不得留下半个字节
PASS ④ 持有者一退出，普通保存立刻恢复 —— 挡住它的是句柄，不是权限
```

① 与 ④ 是这一节的**地基**：只证「被挡」的话，一个把文件设成只读、或者干脆把 ACL 改坏的实现也能通过。
两边都成立才说明挡住它的是**那个句柄的共享模式**。

### 0.2 施工中量到的间歇性：句柄会被 GC 收走

`holdHandle` 起初把句柄留在函数的**局部变量**里。`SafeFileHandle` 是终结器对象 ——
函数返回、变量不可达之后，GC 可以在任意时刻把它关掉，「持有」于是成了一件碰运气的事。
第一次连测 20 轮就撞上了：

```
（修改前的一次运行）20 轮：立即被挡 19 轮；500ms 之后仍被挡 19 轮
```

**这不是环境抖动，是一个真实的间歇性缺陷**：靠它做的用例有大约二十分之一的失败率，
而那种失败会以「偶发红」的样子出现在回归里，最容易被当成噪声忽略掉。
修法是让护栏把持有的句柄留在一个脚本作用域的列表里（`$script:LwbHeldHandles`），活到助手进程退出为止：

```
PASS ④ 稳定性：20/20 轮在持有后**立刻**被挡（不是碰运气） — 20/20
PASS ④ 稳定性：20/20 轮在 500ms 之后**仍然**被挡（句柄不是被立刻回收的） — 20/20
```

20/20 是**修过之后**的数，两次独立运行都是 20/20。修改后 `tests/windows/` 全部 **100 例**通过。

### 0.3 这个装置的边界（写下来，别把它读成一把锁）

修改之后指针仍然是**进程内**的：它承诺「在这个助手进程活着期间持有」。
护栏本身**没有**、也不该有「跨进程长期持有某个文件」的能力 —— 那不是本工程要做的事。
因此：

- 用例只应在**短窗口**内断言（本证据是 ≤500ms），不能把「持有」当成一把锁；
- 正式路径 `Op-WriteFileGuarded` 不用这个装置：它在同一个请求内完成开→写→刷→回读→显式关闭，
  「写入期间别人写不进来」由**那一段**的句柄生命周期保证。

## 1. 验收 2 —— 回读哈希与已批准的新哈希一致，才报告该文件完成

```
PASS 一次正常写入交回 applied（不是 no_change、不是 conflict） — kind=applied
PASS 验收 2：磁盘字节的 sha256 等于条目里已批准的 target_sha256 — 磁盘 9fa757bc64877b28… == 批准 9fa757bc64877b28…
PASS 字节长度与它引用的快照登记尺寸一致 — 31 字节
PASS BOM 与 CRLF 逐字节保真（不是「解码后一样」） — 31 字节，前三个 ef bb bf
PASS 适配器止步于 APPLYING —— 终局由协调器的收尾落，写入方不自己改判终局 — change.state=APPLYING
PASS 独立回读（另一次护栏调用）：哈希仍等于已批准的新哈希 — read.sha256=9fa757bc64877b28…
```

**「独立回读」那一格是刻意加的。** 写入调用**内部**本来就有一次回读（`readback_ok`），
但拿它来证「回读一致」是循环论证：一份恒返回 `readback_ok=true` 的实现能让那条断言在任何情况下通过。
多花一次护栏调用、从**另一条路径**读一遍，问的才是「写完之后别人去看，看到的是不是那一份」。

夹具的目标字节刻意做成**带 BOM 的 UTF-8 + CRLF**：只比「解码后的字符串相等」的实现，
在这上面会写出少三个字节、换行全变的内容，而哈希对不上。

```
PASS 护栏回执：readback_ok 与 flushed 同时为真，且 after_sha256 等于写下去的那一份 — readback_ok=true flushed=true
PASS 护栏回执：身份在写入前后是**同一个对象**（file_id 未变，改名/替换会变） — file_id=002500000009c4df
```

这两行把「完成」这个词摊开成护栏回执上的四个字段：`target_sha256`（护栏真的收到了这一份字节）、
`readback_ok`、`flushed`、以及 `identity_before.file_id == identity_after.file_id`。
**适配器的判据比验收标准更紧一点**：任一字段不满足就按待恢复处理，而不只是比哈希。
代价是**可能把一次实际成功的写入判成待恢复**（`flushed=false` 时内容通常已经在页缓存里、只是没能刷到盘）。
仍然这么判，因为「字节可能还在内存里」正是崩溃后会产生部分字节的那种状态，
而一份说「已完成」的执行日志配一次可能没落盘的写入，比一次多余的人工核验糟得多。

## 2. 验收 1 前半 —— 检查前保存则冲突

两种「VS Code 保存了」，各由一个不同的判据拦住：

```
PASS 甲：原地改写被报成 conflict（不是 applied、不是 refused） — kind=conflict
PASS 甲的判据是**内容哈希**：磁盘既不是基线也不是目标 — 「notes.txt」：磁盘内容已不是被批准的基线：条目基线 9b57c5cb55b666d9…
PASS 甲：我们未写入任何字节，改的人的字节原样留着 — 24 字节
PASS 甲：没有任何写入请求发出，修改集停在 VALIDATING（冲突在校验阶段就定案） — change.state=VALIDATING
```

```
PASS 乙：删除重建被报成 conflict —— 批准的是**那一个对象**，不是那个位置 — 条目基线文件 ID 007b00000009cc06，磁盘实际 007c00000009cc06
PASS 乙：新对象的内容原样留着（被拒的写入不留半个字节）
```

**甲与乙的差别只在「换没换对象」**，而这一点是「只比哈希」与「比对象身份」两种实现**唯一**分得开的地方：
内容不同时两者都会拦；只有内容碰巧相同时，身份是唯一的判据。

乙这一格在真盘上是可造的：编辑器「原子保存」的典型做法就是写临时文件再替换 ——
路径字符串一模一样，`file_id` 却变了。判据来自 `GetFileInformationByHandle` 的
`(dwVolumeSerialNumber, nFileIndexHigh/Low)`，护栏在**打开句柄时**就比对（`Assert-HandleMatches`），
不是靠路径前缀（I05/I03）。

**「一个字节都没写」在两格都由磁盘内容反证**，不只是相信返回值：改的人的字节原样留着。

## 3. 步骤 3 —— 句柄能力不足返回错误，不降级普通文件 API

这一节要在真机上**造出**两种能力不足，而不是在文档里声明它们会被处理。

> **2026-09-26 · LWB-029 之后这一节重跑过。** 下面这些行是**重跑后**的逐字摘录。
> 甲与乙的结论块在 LWB-029 里被重新指向，理由见本节末尾的 §3.2 —— 那是**语义修正**，
> 不是把断言改绿。

```
PASS 甲：只读目标 ⇒ 交回 rolled_back（已证明未动过），不是静默跳过、也不是 conflict — kind=rolled_back
PASS 甲：理由里记着护栏码 PERMISSION_DENIED 与 Win32 5 — 条目「notes.txt」写入失败：护栏拒绝（PERMISSION_DENIED，Win32 5）：拒绝访问：<工作区根>\notes.txt……本次执行在这个文件上没有留下字节。
PASS 甲：账上那条终局是 `untouched`（打开就失败了，一个字节没动） — item_intent → item_untouched
PASS 甲：磁盘内容原样
```

甲是「**打开**就失败」那一类：一个字节都没动，因此**护栏没带 `touched`**。
判据「没带 `touched`」在 LWB-029 里被定为**权威**的「未越过破坏性区域」，
于是这一格交回一份**干净的报告**（`rolled_back`）而不是抛异常。

它**仍然不退回 `conflict`** —— 磁盘上那个对象与计划并不矛盾（它就是要改的那一个），
把它报成「磁盘状态与计划不符」是假话。`rolled_back` 说的是另一件事，也是真话：
**工作区此刻与执行之前一样**。

乙的构造手段是 Windows 的一条**真实**约束：**已被映射到某个进程地址空间的文件不能截断**
（`SetEndOfFile` → `ERROR_USER_MAPPED_FILE`）。第二个 `pwsh` 进程把目标只读映射起来，写入就恰好停在那条线上：

```
PASS 乙：写入被映射的文件 ⇒ 抛，且护栏那一行读成 TOUCHED（越过了截断线） — code=RECOVERY_REQUIRED verdict=TOUCHED touched=true
PASS 乙：护栏码 IO_ERROR、Win32 1224（ERROR_USER_MAPPED_FILE） — winfs_code=IO_ERROR win32=1224
PASS 乙：账本里记着**现场**（尺寸、摘要），供恢复流程定位 — observed_sha256=… 磁盘 6 字节
PASS 乙：磁盘内容**原样**（截断失败早于任何字节改动） — "hello\n"
```

**乙这一格存在的意义是让 `actual_state` 成为一段走得到的代码。** 否则它就是靠假后端「验」过去的分支 ——
而走不到的检查比没有检查更糟，它让人以为那句话有人验过。

**甲与乙配对的方式在 LWB-029 里变得更锋利**：两格都失败在「打开/截断」这一步，
唯一不同的是护栏**有没有越过那条线**，而两格的处置因此相反（甲交报告、乙抛）。
旧判据（「`actual_state` 在不在」）在这两格上给出的是同一个答案「未知」，
新判据（`touched`）才把它们分开 —— 这正是 §3.2 记的那次修正。

```
PASS 丙：记过执行意图的修改集不能再被同一个写入方重提（重来是恢复流程的事） — code=RECOVERY_REQUIRED reason=INTENT_RECORD_FAILED
PASS 丙：那次重提同样一个字节都没写（磁盘仍是 hello）
PASS 丁：映射释放后同一个文件写成功（乙是一次时刻判定，不是把文件判死） — readback_ok=true
PASS 戊：形状不对的 expected_sha256 被报成 INVALID_ARGUMENT，不进入文件操作
```

丙是采集过程中**修正了我自己的一个错误预期**：我原本以为「映射释放后再提交一次就成功」，
实际是 `INTENT_RECORD_FAILED` —— 乙那次已经把执行意图记进了账（`VALIDATING → APPLYING`），
而那一格的含义是「字节可能已经在盘上了」。写入方自己重来等于替恢复流程改判终局，**拒绝是正确方向**。
「映射释放后写得动」这件事改由丁在**护栏层面**证明（同一个文件、同一条路径）。丙与丁合起来才是完整的一句话。

### 3.1 `TOUCHED`（旧名 `crossed_truncate`）的诚实读法

> `guard_verdict = TOUCHED` 是**保守**的：它说的是「已经走到截断之后，剩下的不由我们说了算」，
> 不是「字节一定被改过」。本格的 `observed_sha256` 恰好等于基线哈希，正是因为那次截断根本没成功。
> 恢复流程必须按前者理解它 —— 拿它当「一定坏了」会误报，拿它当「一定没事」会漏掉真正写坏的那一半。

这条写下来是因为它很容易被误读成更强的结论。恢复流程（LWB-030）要拿它做依据，读错方向的代价是两个反方向的错。

### 3.2 这一节的两个字段在 LWB-029 里改了名（诚实交代）

| 旧 | 新 | 为什么 |
| --- | --- | --- |
| `crossed_truncate: boolean` | `guard_verdict: 'TOUCHED' \| 'NOT_TOUCHED'` + `guard_touched: boolean` | 旧名只说得清「**改写**」那条路 —— 它问的是「越过截断线了吗」。而**创建**那条路根本没有截断线可越：它的问题是「对象已经造出来了」。旧名在创建那条路上没有意义，于是一个字段对两条路说不同的话 |
| `already_written: number` | （并入上两者） | 同源：它也只对改写那条路成立 |
| `object_created: boolean` | `guard_touched` | 同上。**而旧判据背后的推理本身就是错的**：它把「护栏没给 `actual_state`」读成「现场未知」，可 `actual_state` 的缺席常常只是「护栏没走到那一步」—— 那是**确切知道没动过**，不是未知 |

**这次改名不是为了整齐，是为了让判据对上事实。** 后果之一在 §3 的甲那一格：
它从「抛异常、要人工核验」变成了「交回一份干净的报告」——
因为旧推理在那一格上付的是一次**多余**的核验费，而磁盘上明明什么都没发生。

LWB-027 里因此有 5 处断言被**重新指向**（换成更具体的判据），LWB-028 里 6 处。
两处证据的 `summary.md` 都随这次修正更新过，改动逐条记在
`docs/evidence/lwb-029/summary.md` 的 §8.2。

## 4. 验收 3 —— 「不宣称原子替换」

验收 3 是一句**文档**要求。它可以被机器核对的那一半是能力标志：

```
PASS 能力自述：不宣称崩溃原子替换（验收 3 的可机器核对那一半） — crash_atomic_replace=false
PASS 能力自述：独占句柄、刷盘、文件身份、硬链接计数这四项真的存在 — exclusive=true flush=true identity=true hardlink=true
```

另一半是散文，写在这里：

**进程崩溃可能留下部分字节。** 一次写入是「打开 → 截断 → 写 → 刷盘 → 回读」五步，
而崩溃可以落在其中任何两步之间。截断之后、写完之前崩溃，文件就是**第三态**：
既不是旧内容也不是新内容，长度可能为 0、可能是新内容的前半截。
本工程**不**通过覆盖来「修好」它，也不宣称这是一次原子替换 —— 它进入恢复流程，
由人在能证明的地方继续（LWB-030）。

**`crash_atomic_replace=false` 与 `cross_file_transaction=false` 是恒为 false 的常量**
（`native/winfs/src/ops.ts` 的 `WinfsCapability`，注释写着「不得含糊其辞」）。
一个多文件修改集也不是一次事务：第 2 个文件失败时，第 1 个文件**已经在盘上了** ——
这正是适配器在阶段 C 一律抛、并把 `already_written` 记进详情的原因。

## 5. 负向回归


### 5.1 §5a 是施工中修掉的一处真实缺陷

`recordIntent`（「我这就开始写了」）原本无条件地跑在阶段 A 之后、阶段 C 之前，
而**中止只在阶段 C 的循环开头才被看见**。于是：一次在阶段 A 之内被取消、一个字节都没写的执行，
会在账上留下 `APPLYING` —— 而那一格的含义正是「字节可能已经在盘上了」。
后果是一次**没有对象的人工核验**：记录说磁盘状态不明，磁盘其实一个字没动。

修法是在 `recordIntent` 之前补一次 `throwIfAborted`。代价是一行，
换来的是**记录与事实一致**。§5a 就是这一格的回归：
中止点由 Proxy 精确地落在阶段 A 的**探针**那一次调用上，而不是落在阶段 A 与阶段 C 之间。

**5b 交回的是 `refused` 而不是抛**，这一点也是采集时修正的错误预期（我原本写成期待抛出）。
阶段 A 就定案的拒绝不该惊动恢复流程：`refused` 的含义是「现在不行，什么都没变」，
把它升格成「需要人来」会让每一次拒绝都变成一次人工核验。

（上面那条「后记」说的是同一件事的另一面：正因为这一格的判据是
「阶段 A 的拒绝不惊动恢复流程」而不是「`create_text` 被拒」，
LWB-028 把创建实现出来之后，这一格只需要换一个拒绝来源就能继续成立。
**判据写在行为上，而不是写在某个具体形态上**，代价就是换来源时得有人
把它指出来 —— 记在这里。）

### 5.2 §5d：写入路径上的硬拒绝兜底在这里是 NOT_RUN

`native-adapter.ts` 里那次 `classifyFile(canonical)` 是**兜底**：正常路径上，修改集由受控读取
签发的票据准备而来，因此「准备出来一个指向 `.env` 的修改」在准备阶段就到不了这里。
要在这份证据里走到它，得让条目里的路径与磁盘上的句柄规范拼写不一致 ——
在真 NTFS 上只能靠符号链接/硬链接构造，而造链接需要管理员或开发者模式，
**本工程不得要求管理员权限**（`docs/` 的硬约束）。该分支由
`tests/unit/executor-native-adapter.test.ts` 的 **B6** 覆盖（假盘的 `openable_as` 就是为表达
「同一个对象有两个名字」而设的）。

## 6. 脱敏

判据刻意做成**两半**，只报后一半是没有意义的：

> **2026-09-26 · LWB-029 之后这一节重跑过，并新增了一格。** 下文是重跑后的逐字摘录。
> 新增的那一格（**抛出去的那句话**）来自 LWB-029 发现的一处真实脱敏漏洞，见下文。

```
PASS 护栏**原始**消息里确实带着本机绝对路径（脱敏不是空操作） — 拒绝访问：C:\Users\…\Temp\lwb-027-20428\readonly-6\notes.txt
PASS 适配器交出的那一份里**没有**本机绝对路径，根路径被替换成 <工作区根> — 条目「notes.txt」写入失败：护栏拒绝（PERMISSION_DENIED，Win32 5）：拒绝访问：<工作区根>\notes.txt……本次执行在这个文件上没有留下字节。
PASS 脱的是根，不是病因：那句话的其余部分还在 — 同上（`PERMISSION_DENIED` 与 `Win32 5` 原文都在）
PASS 抛出去的那句话与它的详情同样干净（这条出口最要紧：改动级日志行不脱敏）
PASS 而它的病因还在（干净不等于被擦成一句空话） — ……护栏拒绝（IO_ERROR，Win32 1224）：SetEndOfFile(截断) 失败……
PASS 全部失败详情里都没有本机绝对路径，也没有临时目录名
```

先证明**原始**护栏消息里真的有路径，才说明 `<工作区根>` 那一步不是空操作。
`native-adapter.ts` 的 `sanitize()` 把 `scope.root_path` 替换成 `<工作区根>`，失败详情因此可以原样交给模型。

### 6.1 新增那一格：抛出去的话也要干净（LWB-029 修掉的一个真洞）

这一节原本只量「报告」这条出口。**那条出口一直是安全的**，而这不说明别的出口也安全：
护栏的原话还会跟着一个**抛出去**的 `RECOVERY_REQUIRED` 走，
而协调器接住它之后，把 `error.message` **原样**写进一条**改动级**日志行 —— 那一行不经过
`appendItemEvent` 的脱敏。**工作区根就是这样进执行日志的。**

修法是在**造出那句话的地方**（`apply.ts` 的三处拼装点）脱敏，而不是在出口上：
出口是从代码里长出来的，修在源头时每多一个出口都自动是安全的。
LWB-029 用「先改回去、看测试是否变红」证明了这条修补**咬得住**，
细节与反证的输出记在 `docs/evidence/lwb-029/summary.md` 的 §6。

对照物选的是 §3 的**甲**（只读目标）而不是乙：甲那句话里**真的**有路径。
乙（被映射的文件）那句 `SetEndOfFile(截断) 失败` 本来就不带路径，因此它在下面只断言**否定面**。

`raw.log` 里那一行**故意**带着路径 —— 它是这一格的对照物。该文件不入库（`*.log` 在 `.gitignore` 中）。
本任务不访问真实工作区（G0/G2 未通过）、**不发网络请求**、**不涉及任何凭据**，
唯一的真实副作用发生在 `%TEMP%` 下 `mkdtemp` 出来的临时工作区上，`finally` 中清理。
