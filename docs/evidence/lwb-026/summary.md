## 0. 这一轮的证据是在什么装置上采的

三条验收标准的原文说的都是**关于时间的事**：

> 同一工作区不会并发应用两个修改集。
> 不同连接的任务也共享物理工作区执行约束。
> 旧执行器未退出时不会因心跳超时启动新写执行器。

因此装置必须是「真的有两个执行器」，而且第二个执行器的身份必须**真的是另一个进程**：

| 段 | 装置 | 为什么非这样不可 |
| --- | --- | --- |
| §0 | 真 SQLite **磁盘文件** + 真探针（含一只刚退出的金丝雀进程） | 内存库跨不了进程；探针必须先被证明在两个方向上都诚实，否则后面每一句「持有者还活着」都可能是「探针恒返回非 null」的副作用 |
| §1 | 真 `ExecutionCoordinator` 在**另一个进程**里跑完认领 → 写盘 → 收尾 | 步骤 2 要证的是「事务不跨过等待」。只有让写盘人**真的卡在写盘阶段**，父进程那次写入才落在事务之外 |
| §2 §3 | 写手进程**自己 spawn 自己**（`--worker writing` / `hold` / `stall` / `try`），各开一条独立连接 | 执行器的身份是 `(pid, started_at)`。同一个进程里开两个连接，pid 相同 —— 那样测出来的「互斥」在探针那一格上是空的 |

```
PASS 状态库是磁盘文件（跨进程的必要条件） — 229376 字节
PASS SQLite 模式为 WAL 且忙等有界 — journal_mode=wal busy_timeout=5000
PASS 探针双向诚实：活着的进程报存在，刚退出的进程报不存在 — identify(2676)=存在 identify(5864)=不存在
```

**唯一的假件是写盘人**，而且它是**故意**假的。真实写入落在 `native/winfs/`（LWB-027），
而本任务要回答的问题里没有一条需要它。反过来，一个假的写盘人让「持有者死在写盘途中」
「写盘期间父进程仍能写库」这类事件可以在几秒内构造出来 —— 在真盘上它们要么等十分钟，要么碰运气。

**假件仍然遵守真写盘人的约定**：它在动字节之前先记下执行意图（`VALIDATING → APPLYING`，§8.2 步骤 5），
报告只交 `applied` / `no_change` / `conflict` 三选一，被 abort 之后抛而不是交回一份迟到的「成功」。
这几条约定是**契约**，不遵守的实现在单元测试的 D3 里被专门检查。

## 1. 步骤 2 —— 认领是短事务，等待发生在事务之外

任务书原文：**「用短事务认领，不得在事务中做文件写入或外部等待」**。
这句话有两个方向，本节与 §2 各证一个。

第 1 节把写手卡在写盘阶段（`write_ms=2500`）**两秒半**，然后在这段时间里从父进程往同一个库文件写入：

```
PASS 真协调器认领并进入写盘阶段（写盘人由假件代替，真写入属 LWB-027） — operation=op_5d133d56718940a78997903d63f1afbc  token=1
PASS 外界能看见「正在写」这个中间态（不是等到收尾才一次性可见） — change=APPLYING operation=APPLYING
PASS 写盘人正在工作的那几秒里，父进程写库仍然成功且不卡（事务没有跨过等待） — 耗时 14ms（写盘人还要持续 2500ms）
PASS 父进程写库时写盘人仍在运行 —— 两件事真的重叠，不是先后发生 — 写手进程尚未退出
```

**判据是两件事一起成立**，而不是「写库成功了」：耗时要小（14 ms，而 `busy_timeout` 是 5000 ms ——
一个被攥住的长事务会表现为 5 秒卡顿或 `SQLITE_BUSY`），**且写手进程此刻还没退出**。
只断前者的实现可以靠「先让写手写完再写库」通过，那恰好是这条要求要禁止的东西。

`APPLYING` 这个中间态**外界能看到**也是同一条要求的一部分。如果实现把状态流转攒到收尾时一次写，
本节的两个断言都会失败，而失败的形态是「父进程写库时要等 2.5 秒」—— 那正是「事务跨过了等待」。

第 1 节的最后一格把**一次性许可**钉在槽判定**之前**：

```
PASS 负向：已消费的批准不能再启动第二次执行（一次性许可挡在槽判定之前） — reason=GATE_REFUSED gate_reason=APPROVAL_CONSUMED
```

两层都要有。只靠许可的话，一条被重复使用的许可就绕过了互斥；只靠槽的话，
同一块地上的两次执行会共享一份批准 —— 而那一份批准上写着「操作者看过这些字节并同意了」。

## 2. 验收 1 与验收 2 —— 互斥是**按物理身份**的

两个修改集属于**两个连接**（`conn_ev_a` / `conn_ev_b`），指向**同一块物理工作区**（`vol_ev_main` / `root_ev_main`）。
写手 A 占住它，写手 B 随即尝试认领另一个修改集：

```
PASS 两个修改集属于两个**不同连接**、同一块物理工作区 — conn_ev_a / conn_ev_b
PASS 槽按物理身份落库，持有者 pid 是**另一个真实进程** — slot.holder_pid=39452 写手 pid=39452 父进程 pid=2676
PASS 心跳把 expires_at 往后推了（租约在续，不是在倒计时等着被接管） — 2026-09-26T04:24:37.613Z → 2026-09-26T04:24:38.832Z
PASS 验收 1：第二个修改集被拒绝，而不是排队等待 — kind=refused reason=SLOT_REFUSED
PASS 拒绝的原因是「租约有效」—— 不是「查不清」也不是「持有者已死」 — slot_reason=LEASE_VALID
PASS 一次拒绝**一寸都没动**：状态、批准、槽逐项相同
PASS 被拒绝的那个修改集的批准仍未被消费 — approval.state=ACTIVE
PASS 槽仍指着写手 A 的操作，栅栏令牌没有增加 — operation=op_4c8074be5a1d4c7a8c49cbcb4ea1f9d6 token=1
```

**「一寸都没动」是一次三项比对**（`changes` 状态、`operations` 状态、`approvals` 里那条仍然可用的批准、
以及槽的五个字段）。只断「状态没变」会让「状态没变但批准被吃掉」通过 ——
而那种实现的产品后果是：操作者点了一次批准，什么也没发生，第二次再点就再也没有批准可用了。

心跳那一格读的是**两次真行**，不是 `heartbeat()` 的返回值。一个恒返回成功的 `heartbeat`
会让「租约在续」这句话在任何实现下都成立。

### 2.1 验收 2 的正面证明

「另一块地没有槽行」证明不了任何事 —— 那只是说还没有人用过它。因此本节让第三个写手进程
去认领**另一块物理身份**上的一个新修改集，它必须**拿到许可**：

```
PASS 验收 2：T1 被占着的时候，**另一块物理身份上仍能开工**（不是一把全局锁） — stage=claimed operation=op_4a7487d0f8f647509fd5c2f4f5d9ec94
PASS 另一块地上的残留槽行是被覆盖的：令牌 1 → 2，只增不减 — fencing_token=2
PASS 占地的是另一个执行器，而不是把写手 A 的槽改了个名 — T3.executor=exe_try_34220
```

这一格同时证了第二条性质。那块地上残留着第 1 节留下的槽行（上一次执行已经 `APPLIED`），
而认领拿到的令牌是 **2** 而不是 1：终态残留是被**覆盖**的，不是被删掉重来。
删掉再占会把令牌重置成 1，而「令牌只增不减」正是接管判定的依据。

## 3. 验收 3 —— 租约过期不等于可以接管

这一节是**唯一**需要进程探针的一节，而它的构造方式是让那两个数字分开：

写手 B 用 `lease_ms=2500` 认领，然后**故意不续约**，进程活着。这正是「休眠 / 断点 / CPU 饥饿」
在生产里的样子。等到租约真的过期（读真行拿 `expires_at`，不猜时间）再让第四个写手尝试认领：

```
PASS 写手 B 的租约确实过期了（时钟已越过 expires_at） — expires_at=2026-09-26T04:24:37.366Z 现在=2026-09-26T04:24:37.625Z
PASS 写手 B **仍然活着** —— 这是本节的唯一变量 — identify(34680) ≠ null（真进程，真的还在）
PASS 验收 3：租约过期 + 持有者活着 ⇒ **拒绝**，不是接管 — kind=refused slot_reason=HELD_BY_LIVE_EXECUTOR
PASS 拒绝的同时**没有**阻断这块地（阻断意味着要人来，而这里只需要等） — blocked_at=null
PASS 上一个操作**没有**被标成待恢复（字节下落未被写成「不确定」） — 前一操作=VALIDATING 前一修改集=VALIDATING
PASS 这一次拒绝同样一寸未动（状态、批准、槽逐项相同）
```

「不会启动新写执行器」的判据是**三件事同时成立**：新写手被拒绝、地没有被阻断、
上一个操作**没有**被标成待恢复。单独任何一条都不够 —— 一个「一律拒绝」的实现能过第一条，
一个「一律阻断」的实现能过第一条和第三条，而后者会把每一次心跳抖动都升级成一次人工介入。

### 3.1 唯一变量对照

紧接着杀掉写手 B，让同一个请求、同一块地再来一次。**只换了持有者进程在不在**：

```
PASS 对照：同一个请求、同一块地，只把持有者换成「真的退出了」⇒ 变成**阻断** — kind=blocked reason=PREVIOUS_WRITE_OUTCOME_UNKNOWN
PASS 阻断时把上一个操作标成待恢复，并如实报告标了谁 — previous_operation_id=op_3b3e5ff94b504ee1a437554181cc44b0
PASS 上一个操作与它的修改集都停在待恢复（不是「已应用」也不是「失败」） — op=RECOVERY_REQUIRED change=RECOVERY_REQUIRED
PASS 地被阻断，但**栅栏令牌没有增加**（阻断不是一次接管） — blocked_at=2026-09-26T04:24:38.605Z token=1
PASS 被阻断的修改集 c4 仍是 QUEUED，退回队列而不是被吃掉 — c4.operation=QUEUED
```

把这两次并排放，是因为只证一半的话两种相反的坏实现都能通过。
而两边的差别只有一处：`identify(pid)` 是 `null` 还是不是。

**持有者死掉不等于字节没写。** 它可能刚好死在写完一半的位置，而那时文件是第三态 ——
既不是旧内容也不是新内容。因此这里不接管，而是把地阻断、把上一操作标成待恢复，
等恢复流程（LWB-030）在能证明的地方继续。

## 4. 负向回归

```
PASS 负向：被阻断的工作区再试一次仍是阻断，不会被重试解开 — kind=already_blocked
PASS 负向：重试**没有**覆盖首次的阻断原因与时间 — reason=PREVIOUS_WRITE_OUTCOME_UNKNOWN
PASS 负向：对未被阻断的地调用解除阻断会被拒绝 — reason=NOT_BLOCKED
PASS 负向：补排队搬运已批准的那个（崩溃后补上「批准与排队是原子的」这半句） — 搬运数=1 state=QUEUED
PASS 负向：从未批准的那个**一格未动** —— 补排队不产生决定 — state=PENDING_APPROVAL 操作行=null 批准行数=0
PASS 负向：字节下落未定案时不许解除阻断（解除的前提是前驱操作已终结） — reason=PREVIOUS_NOT_TERMINAL
PASS 负向：被拒绝之后那块地仍然是阻断的（拒绝不改变任何东西） — blocked_at=2026-09-26T04:24:38.605Z token=1
```

三条值得单独说：

- **「被阻断的地不会被重试解开」**是这一整套设计的目的。一个会被重试解开的阻断，
  等于一个带超时的锁，而带超时的锁正是本模块要防的那个东西。
- **`enqueueApproved` 用两个候选并排验。** 只验证「搬了一个」会让「两个都搬」通过；
  只验证「留下一个」会让「一个都不搬」通过。补排队**只搬运已经由人做出的决定**，
  它存在的意义是让「批准与排队是原子的」这句话在崩溃之后仍然成立。
- **`clearBlockade` 在字节下落未定时拒绝**（见下）。

### 4.1 采集到的真实结论：解除阻断的成功路径在 V1 里走不到

```
NOTE 解除阻断的**成功**路径 — V1 里走不到：任何一次阻断都会把前驱操作标成 RECOVERY_REQUIRED，而它要等恢复流程（LWB-030）才能终结。在此之前 clearBlockade 一律拒绝 —— 这是 fail-closed 的方向，不是缺陷。成功路径与「清标志不是删行、令牌原地保留」由 tests/unit/executor-coordinator.test.ts 的 F2/F3 覆盖。
```

这条是采集过程中发现的，不是设计时就知道的。`RECOVERY_REQUIRED` 刻意**不在**
`TERMINAL_CHANGE_STATES` 里（`packages/contracts/src/change.ts:318`）：终态的定义是
「不可再回到可执行状态」，而待恢复的操作恰恰要回到 `APPLIED` 或 `ROLLED_BACK`。
于是每一次真实阻断都会留下一个「尚未终结」的前驱，而 `clearBlockade` 要求前驱已终结 ——
**在 LWB-030 落地之前，没有任何一条真实路径能让一块地被解除阻断。**

方向是对的（fail-closed：字节下落没定案就不许换人写），但它有两个后果需要写下来：

1. 本仓库里 `clearBlockade` 的**成功**分支今天只有单元测试在走（F2 手工把前驱推到 `APPLIED`）。
   这是「未被生产路径覆盖的代码」，记在偏离项 101。
2. 运维意义上的「工作区卡死」在 V1 里是**可以发生且无法在界面内恢复**的。
   它需要 LWB-030。在此之前，被阻断的工作区只能靠不进这条路来避免。

## 5. 脱敏

证据里出现的事实必须能原样交给模型。因此拒绝与阻断的详情只能带**标识**，不能带用户机器上的目录名：

```
PASS 脱敏：拒绝详情里没有本机绝对路径 — {"slot_reason":"LEASE_VALID","held_by_operation":"op_4c8074be5a1d4c7a8c49cbcb4ea1f9d6","volume_id":"vol_ev_main","root_file_id":"root_ev_main"}
PASS 脱敏：写手报告的事实里不含本机路径，只有物理身份标识 — 10 行；命中路径的行数=0；命中临时目录的行数=0
```

第二条扫的是**写手进程报上来的全部 10 行原文**（不是抽样），判据有两条且都可失败：
出现 `X:\` 形状的路径，或者出现临时库文件名（`lwb-026-`）。

本任务不涉及凭据，因此没有「凭据不入日志」这一格的取证对象。这一条属于 LWB-002 的隧道凭据，
登记在 `docs/evidence/platform-capability.md`。

**本任务不访问真实工作区**（G0/G2 未通过），**不发网络请求**，**不启动任何非 node 进程**。
唯一的真实副作用发生在 `os.tmpdir()` 下 `mkdtemp` 出来的临时库文件上，
`finally` 中 `rm -rf` 兜底清理，且**在关闭数据库之后**执行（库还开着时删不掉）。

### 8.1 采集过程中修掉的那处缺陷

`#finalize` 原本对所有终局都用同一组来源状态：

```ts
from: EXECUTION_STATES,   // ['QUEUED','VALIDATING','APPLYING']
to: 'APPLIED',
```

而 `refuseTransition`（`packages/changes/src/state-machine.ts:226`）要求**每一个**声明的来源状态
都有那条边 —— `VALIDATING → APPLIED` 不是边。于是这一句在**声明上**就是非法的，
它抛 `CHANGE_STATE_INVALID`，而抛出点在字节**已经写完**之后：修改集卡在 `VALIDATING`，
操作卡在 `VALIDATING`，而文件已经改了。这正是本模块最该避免的那种状态 ——
记账与磁盘不一致，且**记账那一侧看起来像「还没开始写」**。

修法是让来源状态**由报告推出来**，而不是保守地放宽：

```ts
applied           ⇒ ['APPLYING']                       // 报告自己说「已经写完」
conflict/no_change ⇒ ['VALIDATING']                    // 这两件事在**校验阶段**就定了
没有报告（待恢复） ⇒ 三者皆可
```

再加一段只在报告说 `applied` 而记账仍停在 `VALIDATING` 时补跳的兜底（`stepIntoApplying`）——
它**只**在两行**同时**停在 `VALIDATING` 时才动手，因为「一个到了 `APPLYING`、另一个还在 `VALIDATING`」
意味着记账已经坏了，那种情形下让状态流转响，比在这里把它抹平诚实。

单元测试的 D6 专门锁这一格：让写盘人**违反契约**（不记执行意图就交回 `applied`），
协调器仍必须落到 `APPLIED` 而不是抛。
