## 1. 验收标准逐条

### 验收标准 1 · 禁止文件不会通过搜索片段或 Git diff 旁路返回

```
PASS 不该被拒的路径没有被拒（规则是逐段精确匹配，不是子串包含） — 放行 4 条
PASS 每一条硬拒绝路径都被判定为 hard_deny（含 .env.example，方案 §4.3 不做自动豁免） — 14 条全部命中
PASS 每个出站面 × 每条硬拒绝路径都被闸门自己拒掉（上层漏检也拦得住） — 8 面 × 14 路径 = 112 次全部拒绝
PASS 同一张凭证上：干净路径正常出站，禁止路径被拒
PASS 判定时与出站重判时用的是同一份规则表对象（不存在两个版本的策略）
PASS 动作与出站面的映射是穷尽的双向覆盖 — 13 个动作 → 8 个出站面
PASS 每个出站面都有明确的秘密处置，且只有两种取值（没有"不处置"这个选项）
NOT_RUN 搜索（LWB-015）与 Git 差异（LWB-016）的真实调用点也走这道闸门
```

**这条标准真正要防的是什么。** 它字面上说的是"搜索与 Git diff 这两条路不能漏"，
但它背后的风险是普适的：**每多一个出站的地方，就多一次"记得调用过滤器"的机会**。
读取、搜索、Git 差异、历史快照、错误详情、审计导出 —— 方案点名了六个面，本实现
连同目录列举与变更回执一共八个。少调一次过滤，策略就少生效一次，而**没有任何测试
会失败**：漏调的那次不报错，它只是安静地把内容发出去了。

因此这里做的不是「过滤器」，是**闸门**：`emitContent()` 是内容离开本机的唯一出口，
而它在出口处**自己重新判定那条路径**，不采信调用方"这个文件我查过了"的说法。
证据里的 112 次拒绝就是这么造出来的 —— 凭证是对**工作区根**铸的（相当于上层压根
没按文件过滤），路径直接送进闸门，闸门自己拒掉。

**同一张凭证上干净路径放行、禁止路径被拒**这一条是上面那段话的可判定形式：
它排除了"这张凭证本来就什么都送不出去"这个解释。

**规则表按对象（`===`）从判定传到出站**，因此不存在「判定时用新规则、出站时用旧规则」
这种时间差 —— 两份表若是两个副本，中间那个差异就是一条旁路。

**硬拒绝与搜索排除是两份独立的存储**（方案 §4.3），不是一个列表加个 `severity`：

| | 硬拒绝 | 搜索排除 |
| --- | --- | --- |
| 内容 | `.env`、私钥、SSH、凭证目录、`.git/config`、插件状态目录 | `node_modules`、`dist`、媒体、锁文件 |
| 性质 | **安全**边界 | **性能**取舍 |
| 谁能改 | 只有本地操作者，且只能**具名收窄**（见 §1.2） | 随项目随时调整 |

两者共用一个列表的话，就会出现「为了让搜索快一点，把某条规则调成排除」这种看起来
无害、实则把安全边界降级成性能开关的操作。分开之后，放宽搜索排除在**语法上**碰不到
硬拒绝集合 —— 这是"结构性不可能"，不是"记得别那么干"。

**逐段精确匹配，不做子串包含**：`.env` 不能连 `docs/env-notes.md` 一起拒掉。
拒得过多会促使人们去关规则，而**一条会被关掉的规则等于没有**。证据里"放行 4 条"
就是在钉这一点。

### 验收标准 2 · 模型输入无法修改策略或扩大资源根

```
PASS 请求对象的字段集是封闭的：没有绝对路径、没有资源根、没有"已批准"
     PolicyRequest = {action, connection, now, presented, workspace}
PASS ActionView 只有 action / path / approval 三项，且 path 是**相对**路径
PASS WorkspaceView 里的根身份是 volume_id/file_id（不透明标识），不是可写路径
PASS approved / user_id / principal_id / session_id / conversation_label / force 等字段对判定毫无影响
     注入 7 个字段，判定逐字节相同
PASS 模型单独调用 change_apply（有票据、无批准）得到 APPROVAL_REQUIRED
PASS 注入 approved:true 之后仍然 APPROVAL_REQUIRED（模型不能自己批准）
PASS 判定产出的对象被登记过；手搓的字面量换不到出站资格
PASS 五层检查全部留痕（没有短路） — 11 条失败，覆盖 5/5 层
PASS 主因按固定优先级取第一条（connection 最先）
PASS 正当的具名豁免被接受，且只收窄那一个名字
PASS 五类越界豁免全部被拒（含 I13 的「永远不可豁免」）
PASS 豁免不改变规则条数（既不新增也不删除，只加 except）
PASS 只读模式下 change_prepare 与 change_apply 都被拒（整条链路）
PASS 只读模式下读取仍可用（拒绝的是提议链路，不是整个工作区）
```

**「无法扩大资源根」在本层是类型层面成立的，不是靠检查。** `PolicyRequest` 里
根本没有绝对路径这种字段：`ActionView.path` 是工作区**相对**路径，工作区的根身份是
`root_volume_id` / `root_file_id` 两个不透明标识。判定层拿不到、也构造不出工作区外的
对象 —— 没有可扩大的入口，就不需要"记得检查有没有人想扩大"。

**「模型不能自行批准」同样是字段层面的。」** `ApprovalView` 里**没有**
`approved: boolean`，只有 `state`（来自 daemon 的批准状态库）、两个摘要与到期时间。
方案与 ADR 反复强调 `approved:true` / `user_id` / `session_id` / `conversation_label` /
`principal_id` 不能作为授权证据；最彻底的落实方式不是逐条检查它们，而是让这种字段
在本层**不存在** —— 一个从请求体里读到的布尔值，在这里没有任何途径变成
`state: 'ACTIVE'`。证据里向请求注入 7 个这样的字段（含 `force` / `skip_approval`），
判定结果**逐字节相同**。

**五层能力交集，而且不短路。** 连接授权、工作区模式、当前代次、文件规则、批准权限
五层**全部**跑，任何一层不通过即拒绝；全部失败项都保留（本地审计用），呈现给模型的
只有一条主因，按固定优先级挑出。不短路的三条理由：

1. 短路会把「为什么拒绝」变成「哪一层先拒绝」—— 拒绝理由因此取决于代码里的语句
   顺序，而不是安全事实。改一次顺序，同一个请求的拒绝码就变了。
2. 审计需要知道**全部**失败项。只记第一条的话，一个既越权又过期的请求在审计里
   看起来和单纯越权一模一样。
3. 短路会掩盖规则失效：第一层永远先失败，第二层的判定就永远不执行，它的 bug
   也就永远不暴露。

`generation` 排在 `file_rules` **之前**是有意的：代次变了意味着据以判定的那份策略
快照可能已经过期，此时报「命中了哪条文件规则」是拿旧地图指路。先报代次，模型重新
读取之后自然会撞上硬拒绝 —— 信息不丢，只是顺序更诚实。

**豁免只能收窄，不能新增或删除。** `.env.example` 这条规则一定会有人想开洞
（方案要求**默认**不豁免，但没说永远不豁免）。如果没有一处正当的开洞方式，人们就会
去改规则本身 —— 而那会顺带把 `.env` 也放出来。给一个只能收窄的口子，是让那条规则
活得久一点的办法。五类越界豁免全部被拒：指向不存在的规则、通配符、无意义的豁免、
带路径分隔符的名字，以及 **I13 的状态目录**。

`NON_EXEMPTABLE_RULE_IDS = ['HD-PLUGIN-STATE']` 把方案里「密钥、审批状态库、恢复快照
目录对模型**永远**不可挂载」的那个"永远"变成了可执行的含义：若它可以被本地配置豁免，
「永久不可挂载」就变成了「默认不可挂载，改一行配置即可」—— 性质完全不同。更根本的是，
那三个目录泄露的后果不是"某个项目的秘密泄露"，而是**整套授权机制失效**（审批状态库
决定了什么算获批），因此它不在可权衡的范围内。

**只读模式关闭的是整条提议链路**，不只是写入那一步：`change_prepare` 与
`change_apply` 都被拒，而读取仍然可用。只关写入那一步的实现会允许模型生成修改集、
等待批准，然后在最后一步永远失败 —— 那不是只读，那是浪费一次人工审批。

### 验收标准 3 · 明确记录秘密检测并非百分之百识别任意秘密

本条不是"通过/不通过"型的验收，是**记录**型的。因此证据脚本把它打印出来（规则清单
+ 边界逐条），而不是只打印一个 PASS。

```
规则清单（与代码同源，直接读出） — 15 条
      [certain] private-key-block / putty-private-key / aws-access-key-id / github-token
                slack-token / stripe-secret-key / google-api-key / npm-token / jwt
                azure-account-key / aws-secret-access-key / control-plane-token
      [likely]  keyword-secret-value / url-userinfo / http-auth-header

检不出来的情形（这是记录，不是缺陷清单）：
      检不出  无关键字的高熵随机串 — 形状与随机串无异；收录它等于让规则命中一切长十六进制串
      检不出  运行时拼接的凭据 — 拼出来的值不在文本里，本模块看不到运行时状态
      检不出  被 base64 包了一层的凭据 — 编码之后的形状与原规则完全不同
      检不出  自研令牌（无固定形状，名字里也没有关键字）
```

> **本次采集后追加的一条（LWB-012）**：`control-plane-token` 是在本任务收尾之后、
> 由 LWB-012 加进来的第 15 条。它与其余各条**性质不同**：其余各条保护的是
> **用户的**秘密，这一条保护的是**本程序自己的授权凭据**（启动令牌 / 会话 /
> CSRF / 一次性 nonce）。泄露它不等于泄露某份文件，而是等于把「批准」这件事
> 本身交出去 —— 持有者可以批准自己的写入。因此它被放进 `certain` 档：
> 形状即凭证，不存在「可能是占位符」的情形。
> 判定规则与签发端共用 `packages/contracts/src/control.ts` 里的一份定义，
> 因此不存在「生成端改了形状、筛查端还在认旧形状」的漂移空间。
> 上面的规则清单与本节其余数字均已按 15 条重新采集。

**这个模块不是「秘密识别器」，是「已知形状的凭证识别器」。** 没有关键字、没有固定
前缀的随机串检不出来；运行时拼接的凭据检不出来；被编码或切分的凭据多半检不出来；
私有格式与自研 token 检不出来。这不是"以后改进"的清单，是**能力边界**。

因此出站检查的定位是**纵深防御的一层**，不是唯一那层。真正拦住秘密的第一道是硬拒绝
规则（`.env` / 私钥 / 凭证目录）与用户自己不给工作区授权 —— 那一层看路径不看内容，
不受上列边界影响。证据里用同一个"检不出来"的随机串做了对照：它躺在 `.env` 里就会被
`POLICY_DENIED` 挡住。

**边界是写成断言的，不是写成注释的。** `tests/unit/egress.test.ts` 的「已知边界」一节
逐条**断言这些情形确实检不出来**（`findings.length === 0`）。注释会腐坏；断言会在
有人以为"再加一条规则就全覆盖了"时提醒他并不是。若哪天某条真被检出来了，用例会红，
那时该做的是把该条移出清单、写进正式规则、更新本节 —— 而不是删掉那条用例。
（本次采集时，最初写在清单里的两条"检不出来"其实**是**检得出来的，见 §4。）

**反向的边界同样记录在案：把不是秘密的东西盖掉。**

```
PASS 已知的过度脱敏：关键字 + 长标识符会被当成值盖掉 — "const apiKey = [REDACTED:keyword-secret-value];"
NOTE 代价 — 该文件因此拿不到可编辑票据，用户看到的是"这个文件不能改"
PASS 被切成多行的凭据：前半段被盖掉，后半段原样送出（**残余**，记录在案）
PASS 该次读取拿不到可编辑票据
PASS 脱敏不留任何前后缀（对原值逐字符滑窗，6 字符片段一律不出现） — 4 个样本无残留
```

- `keyword-secret-value` 的要求只是「关键字 = 一个 ≥12 字符的连续记号」，因此
  `const apiKey = getFromVault();` 也会被脱敏。方向是安全的（多盖不放行），
  代价是这一行看起来含秘密，于是整份文件失去可编辑票据。
- **被切成多行的凭据只盖住一半**：形状规则要求 `ghp_` 之后至少 36 位，切断后两边都
  不满足；关键字规则只认得「关键字 = 值」那一段，于是盖掉前半段，**后半段原样送出**。
  这一条单独写成用例（而不是混进"检不出"清单），是因为它最容易被误认为已经处理好
  了：输出里出现了 `[REDACTED:...]`，看起来这件事已经完事。任意切分的凭据无法靠
  形状识别，这是真正的边界。

**脱敏的铁律：替换文本里不得出现被替换内容的任何前缀或后缀。** 常见的错误做法是
`sk_live_****abcd`（保留前 8 位 + 后 4 位）—— 那不是脱敏，是**部分泄露**，而且留下的
部分往往正好是用于识别账户的那部分。本实现替换成固定标记 `[REDACTED:<规则 id>]`：
零个原始字符。证据用逐字符滑窗（原值的任何 6 字符片段都不出现在输出里）来钉这一点，
而不是靠"肉眼看着没问题"。

**脱敏结果不得获得可编辑读取票据**，而且这条**跟着凭证走**：

```
PASS 凭证被污染后，**先前**签发的干净票据也作废（票据有效性跟着凭证走）
PASS 硬拒绝路径抛 PolicyDeniedError，且 details 里带得出规则 id（不含正文、不含绝对路径）
```

一次读取可能分多次出站（分页、多个片段）：先出去的干净片段拿到了票据，随后出去的
片段命中秘密。只在**签发那一刻**查污染的话，那张早先的票据仍然有效，而它所属的文件
此时已经确认含秘密。因此票据记录它由哪张凭证签发，在**使用票据的那一刻**复查凭证的
污染状态 —— 把这条时差关掉。

## 2. 两条设计取舍（都是"少一个可选项"）

### 2.1 出站义务里**只有一项**

`EgressObligations` 只声明 `secret_mode: 'block' | 'redact'`。容易顺手写成开关、
但**刻意没有**写进去的三件事：`screen_secrets`（要不要做秘密筛查）、
`no_editable_ticket_when_redacted`、`metered`（要不要计入出站预算）。

它们不是可选项，因此不放进义务集合 —— **可选项会被关掉**。一个「本次不筛查秘密」的
合法取值，迟早会出现在某条为了性能或为了"别老是拦住我"的代码路径上；它一旦出现，
验收标准 1 就只是一句注释了。这三条硬编码在 `@lwb/egress` 里，没有开关。
`tests/unit/egress.test.ts` 有一条用例把义务集合的键集钉成 `['secret_mode']`。

留下的这一项是真的会变，而且两个取值都不泄露被命中的内容，区别只在「其余部分还能
不能看」：读取与目录列举脱敏后放行（用户要的是这份文件，把私钥那一行盖掉之后剩下的
部分仍然有用；整份拒掉只会逼人去关掉这个策略），其余六个面整块阻断。

两档的划分由**判定**给出，不是出站层自己猜；证据里断言每个出站面都有明确处置、
且取值只有这两种 —— 没有"不处置"这个选项。

### 2.2 `error_detail` 有预算例外，但有上限

如果预算耗尽连「预算耗尽」这条错误都发不出去，调用方看到的是连接断开或超时，而真正
的原因永远到不了 —— 那不是收紧，是让人无法诊断，于是一个可解释的限额变成了一个说不清
的故障。因此 `error_detail` 在预算耗尽时仍可出站，但**限 8 KiB**：没有上限的话它就
成了一条不受预算约束的无限通道，而"错误详情里能不能夹带正文"正是要防的事。

这个例外**不是**旁路，证据逐条钉住了：错误详情照样重判路径（`.env` 仍被拒）、照样做
秘密筛查（夹带令牌仍 `SECRET_DETECTED`）、超过 8 KiB 仍被拒，其它面没有这个例外。

## 3. 实测：出站预算为什么是滑动窗口

```
PASS 对照：固定小时桶在跨小时时又给出一整份额度（实际允许两倍）
PASS 本实现：滑动窗口在同一时刻仍然拒绝（不给双倍）
PASS 窗口长度实测落在 [59, 60] 分钟（用量在第 60 分钟滑出）
PASS 被拒绝的出站不记账（反复被拒不会耗光额度） — 10 次超额拒绝之后用量仍为 0
PASS 预算是每连接的，不是每工作区的
```

最省事的实现是记 `{hourStart, bytesThisHour}`，跨小时清零。它有**两倍**的漏洞：
12:59 用满一整小时的额度，13:00 立刻又有一整小时 —— 「每小时 32 MiB」实际允许在两分钟
内送走 64 MiB。证据脚本现场搭了一个这样的对照实现，量出了这个洞（12:59 记满、
13:00 又放行），并量出本实现在同一时刻仍然拒绝。

本实现用 60 个月份桶，用量取存活桶之和，内存 O(60)。**它的真实精度不夸大**：桶粒度是
一分钟，因此有效窗口在 **[59, 60] 分钟**之间浮动，最坏提前一分钟忘掉最早的用量；超出
上界约 `limit/60`（默认 32 MiB 时约 546 KiB），比固定小时桶的一倍小两个数量级。

**记账的两条铁律**：先检查、后记账、再出站（被拒绝的出站**不记账** —— 否则一个反复
被拒的请求会把额度耗光，而它什么都没送出去：既是错误的计量，也成了一个廉价拒绝服务
入口）；超额一次即整体拒绝，不做部分记账（"先送一半、剩下的下次"会让调用方以为拿到的
是完整结果，违反 I14）。

**预算是每连接的，不是每工作区的**：一个连接可以访问多个工作区，若按工作区记，多授权
一个工作区就顺带多拿一份额度 —— 扩大授权范围不该顺带扩大出站额度（那正是「扩大资源根」
的一种隐蔽形式）。

## 4. 采集期间修掉的三个真实缺陷

三条都是**实现已经写完、类型检查通过、而且"看起来对"**，由测试与证据脚本逼出来的。
列在这里，因为它们是本任务最有价值的部分。

### 4.1 秘密检测从来没有真正执行过（缺 `g` 标志）

`String.prototype.matchAll` 要求正则带 `g` 标志，否则抛 `TypeError`。当时的 14 条规则
**一条都没有** `g` —— 也就是说 `screenText()` 在第一次被调用时就会抛异常，从来没有
筛查过任何东西。（数字 14 是**当时**的规则条数，本节是那次采集的记录，不改写；
规则清单现已增至 15 条，见 §3。）

它不算"安静地放行"（会抛错），但会以「出站时抛一个与秘密无关的 TypeError」的形式
暴露，很容易被当成别的问题去查。**修法不只是补上标志**：在模块加载期加了自检，
缺标志就在**导入模块时**报出一条说明"筛查将完全失效"的错误 —— 加规则的人立刻知道
少了什么，而不是等到某次出站。

### 4.2 `url-userinfo` 把用户名脱敏了，口令原样送出（`value_group` 没被读过）

`SecretPattern.value_group` 被声明、被写进注释（"只替换捕获组 1；0 表示替换整个匹配"），
但代码里始终读的是 `match[1]`：**填 1 还是 2 结果一样**。而 `url-userinfo` 的第 2 组
才是口令，第 1 组是用户名。于是 `redis://default:sup3rs3cr3tpass@host` 被处理成
`redis://[REDACTED:url-userinfo]:sup3rs3cr3tpass@host` —— **看起来脱敏了，秘密还在**。
这是这类实现最危险的失败形态：输出里有 `[REDACTED]`，复核的人一眼扫过去不会再看。

修法不是"把 2 改成 1"，而是把位置来源换掉：正则一律带 `d` 标志，位置取自
`match.indices[value_group]`，取哪一组由 `value_group` 决定、位置由正则引擎给出。
原先的 `lastIndexOf` 反查还有第二个隐患 —— 捕获组的值恰好也在关键字里出现时
（`password: password123`）会定到错误的位置。`d` 与 `g` 一起纳入加载期自检。

### 4.3 早先签发的干净票据在凭证被污染后仍然有效

一次读取可能分多次出站。原先 `mintEditTicket` 只在签发那一刻检查污染，因此：干净片段
先出去、拿到票据 → 后续片段命中秘密、凭证被标记为已脱敏 → 那张早先的票据**仍然有效**。
修法是让票据记录签发它的凭证（`TICKET_OWNER` WeakMap），在 `assertEditTicket` 里
复查该凭证的污染状态 —— 票据的有效性跟着凭证走。

这条是在**设计测试用例时**发现的，不是运行时报错逼出来的：写"脱敏过的读取拿不到票据"
这条用例时，问了一句它反过来成不成立。

### 另外两处：写入的实现细节

- **PEM 规则必须连正文一起匹配。** 只匹配 `-----BEGIN … PRIVATE KEY-----` 那一行的话，
  脱敏会把标记换成 `[REDACTED]`，而后面那一大段 base64 私钥正文原样留在输出里 ——
  那不是脱敏，是把锁头涂黑、钥匙还挂在门上。结尾用 `|$` 兜住没有 END 标记的截断情形。
- **重叠命中取并集，不取"更长的那条"。** 同一段文本常被两条规则同时命中
  （`aws_secret_access_key = …` 既命中它自己的规则也命中通用的关键字规则）。合并时若
  丢掉被覆盖的那条，另一条多出来的尾巴就会留在文本里 —— 那正是脱敏最容易漏的一段。
  并集只会多盖，不会少盖；且合并后取**更严重的那一档**，否则一次关键字合并会把一个
  私钥从 `certain` 降级成 `likely`，本该阻断的变成只脱敏。

## 5. 与任务书的一处偏离：`change_apply` 要求 `propose` 而不是 `apply`

任务书未直接规定，但**冻结契约**（`packages/contracts/src/capabilities.ts`）把 `apply`
放进 `CONTROL_ONLY_CAPABILITIES`，并写明「MCP 适配器凭据不得包含其中任何一项」——
因此模型**永远拿不到** `apply`。若 `change_apply` 要求 `apply`，模型调用它只会得到
`NOT_AUTHORIZED`，而工具契约（`packages/contracts/src/tools.ts:276`）与 LWB-028 的验收
标准要求的是「模型单独调用应用工具只得到 `APPROVAL_REQUIRED`」。

两者这样调和：**能力决定"能不能发起"，批准决定"能不能落地"。**

| | 能力 | 行为 |
| --- | --- | --- |
| 模型 | `propose` | 可以提议，也可以**请求**应用；缺本地批准时得到 `APPROVAL_REQUIRED`（这是 `await_human`，不是越权） |
| 控制面 | `apply` | 控制台「批准并应用」入口持有的能力 |

也就是说，**写入的授权来源自始至终是本地操作者的批准**，不是某个能力位；能力位管的是
工具面。这与「模型绝不能自行批准」一致：放宽的只是"能发起请求"，没有放宽"能产生授权"。

**连接层另有一条独立检查**：模型侧凭据里出现任何控制面专属能力（`control` / `apply`）
即判该凭据配置本身无效，哪怕这次只读一个文件也不放行。证据里审计导出面的测试因此
用的是一条 `local_console` 连接 —— 顺带也就证到了「换个面不等于换一套规则」。

## 6. 步骤 3 的另一半：静态检查的覆盖是被**探针**证明的，不是被"检查通过"证明的

```
NOTE 基线 — ✅ FsGuard 导入检查通过（已检查 66 个文件，未发现绕过）
PASS 反向探针：在这两个包里种下违规 import 都会被检查器报错
     packages/policy/src/__probe_evidence.ts → 被检出
     packages/egress/src/__probe_evidence.ts → 被检出
PASS 探针文件已删除，仓库恢复干净（检查器回到基线结果）
```

`scripts/check-fsguard-imports.mjs` 的规则 1 条件是 `isBusiness && !isAllowed`，
因此**两个清单都不在**的包既不被允许、也不被检查，而检查器照常打印"未发现绕过"
（PROGRESS.md 偏离项 9）。也就是说，「检查通过」这句话证明不了覆盖 —— 一个漏出清单的
包和一个正常受检的包，输出完全一样。

唯一能区分二者的办法是**反向探针**：往包里种一个故意违规的文件（`import fs from
'node:fs'`），确认检查器报错，再删掉。本次对 `packages/policy/` 与 `packages/egress/`
两个包各做了一次，都检出了 `FSGUARD_BYPASS`。文件数从 58 增到 66，正好等于本次新增的
8 个文件。

探针写在证据脚本内部，用 `try/finally` 保证即使中途失败也会删除，并**在最后断言
探针文件确实不存在、检查器回到基线结果** —— 一个会留下垃圾文件的探针本身就是缺陷。
