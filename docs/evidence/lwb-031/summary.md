`change_apply` 同样仍未接入工具面，因此**今天撤销这条路只能由测试与取证脚本驱动**。

**这一轮里最要紧的一句话：撤销是一条新的修改集，不是把旧的抹掉。**
源记录在提议前后、执行前后**逐行逐列**不变（§7.2 / §7.4），磁盘却真的回到了基线（§7.5）；
撤回一次改写靠的是**按当前字节重算出来的逆提案**（§1.7），而不是把旧快照抄回去；
而「上次应用之后是什么」这个问题，答案只有一个来源 —— **执行日志**（§5）。

## 0. 这一轮的证据是在什么装置上采的

三条步骤的原文：

> 1. 将旧修改的逆操作生成新的修改集，仍需独立批准。
> 2. 撤销既有文件修改要求当前内容/身份仍符合上次应用后的预期，或明确生成冲突。
> 3. 撤销新增文件视为删除：默认不自动删除，V1 输出本地恢复方案；V1.1 删除能力通过后再启用批准删除。

三条验收标准的原文：

> (a) 后续人工修改不会被回滚覆盖。
> (b) 旧修改回执不可被篡改成“未发生”。
> (c) 撤销不改变 Git 暂存区，也不执行 reset --hard。

交付物原文：`packages/changes/revert.ts`。

| 段 | 装置 | 为什么非这样不可 |
| --- | --- | --- |
| §0 | **先让执行器真的跑完一次修改**（真 NTFS + 真护栏 + 真 SQLite 磁盘文件 + 真 `createNativeApplier`），再谈撤销 | 撤销的前提是「上一次真的应用过」；夹具要是假的，后面每一条「回到基线」都无从谈起 |
| §1 | 一条无人碰过的改写，端到端撤销回基线，前后比**字节** | 步骤 1 说的是「逆操作生成**新的**修改集」；「新」要能被看见（新 id / 新摘要 / 新窗口 / 停在待批准） |
| §2 | 三种冲突各在**真文件**上造一次（第三内容 / 删掉 / 删除重建） | 「身份仍符合上次应用后的预期」里的**身份**是真对象身份（NTFS 文件索引），编一个填进去这一格就永远为假 |
| §3 | 撤销之后比**新建文件的指纹**（大小 + 最后写入时刻 + 内容哈希） | 「不自动删除」的可核对形式是「三样都没变」，而不是「内容没变」 |
| §4 | 撤销之前**真的**用手改一次文件 | 验收 (a) 要的是一份**不属于本次修改**的现场，构造不出来就没有这一条 |
| §5 | 往**真操作**的日志里追加真行，把每一格造出来 | 「回执不完备」在正常路径上造不出来 —— 真执行写出来的日志清一色以 `item_verified` 收尾 |
| §6 | 源修改集的三条边界（不存在 / 别人的连接 / 另一个工作区） | 步骤 1 说「旧的修改」，而「旧的」的前提是它得**是你的** |
| §7 | 提议前后 + 执行前后，把**修改集、条目、操作、逐条目回执、执行日志**五组关系逐行逐列取指纹 | 验收 (b) 说的「篡改」不只是改一个字段，还包括**抹掉重来**；只比状态会让「状态没变但记录被换掉」通过 |
| §8 | 真 git 仓库里跑完整流程，比 `.git/index` 字节与暂存区输出 | 验收 (c) 里「不改变暂存区」的判据是**索引文件的字节**，不是 `git status` 的一行文字 |

**装置自述（§0 逐字）：**

```
PASS §0.1 原生护栏后端可用 — PowerShell 7 + .NET P/Invoke（本机无编译型工具链时仍可调用真实 Win32 API）
PASS §0.2 源修改集是被**执行器真的跑完**的（状态 APPLIED） — [{"id":"op_5705682967d148ee8f78c9c84ef3fe80","state":"APPLIED"}]
PASS §0.3 盘上确实变成了目标内容
```

> **§0.3 那一句要是失败，后面每一条「撤销成功」都无从谈起** —— 它先证明夹具真的改过盘。
> 因此撤销的每一条结论都排在一个**真的应用过**的修改集后面，而不是排在一个人造的状态值后面。

## 1. 步骤 1：逆操作生成**新的**修改集，仍需独立批准

```
PASS §1.1 一条无人碰过的改写 ⇒ REVERTIBLE — {"item_id":"ci_id_s1-2_5","seq":0,"op":"edit_text","path":"src/a.txt","observed_path":"src/a.txt","verdict":"REVERTIBLE","reason":null,"expected_sha256":"4e768a3d…","observed_sha256":"4e768a3d…","detail":"src/a.txt 的对象身份与内容都还是本次修改留下的那一份，可以生成逆操作（还原为基线 6fa7f1cf…）。"}
PASS §1.2 撤销提议是一条**新**修改集（新 id）
PASS §1.3 新修改集的摘要与源不同
PASS §1.4 新修改集停在 PENDING_APPROVAL —— 没人批准就不动 — PENDING_APPROVAL
PASS §1.5 新修改集有自己的新窗口（不是沿用源的那一个）
PASS §1.6 逆提案是一整条 replace_text，不是「把旧快照抄回去」的一句话
PASS §1.7 逆提案的基线是**当前**盘上那一份（不是旧快照） — 提案锚在 4e768a3d…；盘上是 4e768a3d…
PASS §1.7b 而它写下去的那份内容，与旧快照的**基线**逐字节相同（§1.9 在真盘上验这一条）
PASS §1.8 批准并执行之后到达 APPLIED — APPLIED
PASS §1.9 端到端：文件内容逐字节回到基线
PASS §1.10 端到端：源修改集仍是 APPLIED —— 撤销不改它的状态
```

**「新的修改集」是四条性质，不是一句话。** §1.2 ~ §1.5 分别钉住新 id、新摘要、
停在 `PENDING_APPROVAL`、以及**自己那条新的有效期窗口**。
最后一条是结构性的，不是口味：`CHANGE_TRANSITIONS` 里 `APPLIED: []` 是空数组，
而 `EXPIRABLE_STATES` = `Object.keys(CHANGE_TRANSITIONS).filter(s => CHANGE_TRANSITIONS[s].includes('EXPIRED'))`
算出来是 `[PENDING_APPROVAL, APPROVED, QUEUED]` —— **`APPLIED` 不在里面**。
撤销因此**不可能**沿用原计划的有效期，它只能作为一条新修改集拥有自己的那一段。

这条推理依赖的是**另一张表**，因此 `revert.ts` 把它变成了一次**现算**
（`assertExpiryInapplicable`）：撤销在绑定校验里**摘掉** `CHANGE_EXPIRED` 这一条理由
（`APPLIED` 到不了 `EXPIRED`，那一列对它没有作用点），而摘掉的代价是每次调用问一次
`EXPIRABLE_STATES.includes('APPLIED')` —— 一旦有人给 `APPLIED` 加了一条到 `EXPIRED` 的边，
撤销会**立刻停摆**并说明原因，而不是继续安静地忽略一条已经生效的期限。
只摘这一条：代次、策略版本、契约版本、工作区与连接状态那几条照旧生效 ——
它们说的是「这次撤销所依据的授权事实还在不在」，与时间无关。

**逆提案锚在「当前」而不是「快照」。** §1.7 与 §1.7b 是一对：提案的 `base_sha256` 等于盘上此刻的字节，
而它写下去的**目标**内容逐字节等于旧快照里的**基线**（§1.9 在真盘上端到端验完）。
两句话合起来的含义是：撤销是**按当前文件重算**出来的一次改写，不是一次「把历史字节灌回去」。
这也正是它对**行**有效的唯一理由 —— 引擎要拿当前内容去逐行匹配，才能保证 `old_lines` 真的在那里。
§1.6 顺着这一点确认产物是一整条 `replace_text`，而不是一句「恢复旧版本」的指令。

## 2. 步骤 2：当前内容 / 身份必须仍符合上次应用后的预期，否则**明确冲突**

```
PASS §2.1 第三种内容（人又改了） ⇒ 判定 CONFLICT — CONFLICT / THIRD_CONTENT
PASS §2.1 第三种内容（人又改了） ⇒ 理由 THIRD_CONTENT — THIRD_CONTENT
PASS §2.1 第三种内容（人又改了） ⇒ 没有生成任何逆提案
PASS §2.1 第三种内容（人又改了） ⇒ 提议阶段整体拒绝，且码是「重新读一次再来」这一类 — {"code":"FILE_VERSION_CONFLICT","reason":"THIRD_CONTENT","message":"不能撤销：1 个文件已经不是本次修改留下的那一份，撤销会覆盖它们；本次没有建立任何修改集。挡路的是：src/a.txt。"}
PASS §2.1 第三种内容（人又改了） ⇒ 冲突的现场**一个字节都没被碰**（提案阶段不写盘）
PASS §2.1 第三种内容（人又改了） ⇒ 源修改集没有被改动过（仍 APPLIED）
PASS §2.2 目标不在（被删掉） ⇒ 判定 CONFLICT — CONFLICT / OBJECT_MISSING
PASS §2.3 对象被替换（删除重建，内容一样） ⇒ 判定 CONFLICT — CONFLICT / REPLACED_OBJECT
PASS §2.3 对象被替换（删除重建，内容一样） ⇒ 冲突的现场**一个字节都没被碰**（提案阶段不写盘）
PASS §2.5 护栏报告「不可用」⇒ GUARD_UNAVAILABLE（不是「没写过」） — {"reason":"GUARD_UNAVAILABLE","verdict":"CONFLICT"}
PASS §2.5b 护栏读了但失败 ⇒ READ_FAILED，仍然是不测 — {"reason":"READ_FAILED","verdict":"CONFLICT"}
PASS §2.5c 两种失败都不生成提案（「不知道」不产生动作）
PASS §2.5d 护栏消息里的本机路径没有被带进计划文本
PASS §2.5e 反向探针：那句路径确实存在于替身消息里（否则上面一句是空的）
```

**冲突是「明确」的，因为它是逐条目判定出来的，而整条提议被整体拒绝。**
三种冲突各占一格，理由串（`THIRD_CONTENT` / `OBJECT_MISSING` / `REPLACED_OBJECT`）在错误对象里
逐条带出去。错误**码**是 `FILE_VERSION_CONFLICT` 而不是 `CHANGE_STATE_INVALID`：
这一格要模型做的是**重新读一次再来**，不是「这条路走不通」。
而「提议阶段一个字节都不写」是用**指纹**（大小 + 最后写入时刻 + 内容哈希）量的 —— §2.1 与 §2.3 各量一次。

**第三格（§2.3）是这一节里最容易被糊过去的一格。** 它是「删掉重建、内容一模一样」：
只比内容的话它会**通过**，撤回去也不会有任何人立刻发现。而它错了 ——
`file_id` 变了，那个文件已经不是我们改过的那个对象了。
真盘上能造出这一格，靠的是 NTFS 的文件索引（含序列号）：改名不变，删除重建会变。

**「不知道」与「没写过」是两回事（§2.5）。** 护栏不可用、护栏读了但失败，
两条路都落到 `CONFLICT`，理由串不同（`GUARD_UNAVAILABLE` / `READ_FAILED`），
**都不生成提案**。这一节还钉住了另一件事（§2.5d/§2.5e 是一对反向探针）：
护栏消息里带着目标的**绝对路径**（§2.5e 证明那句路径真的在替身消息里，
否则 §2.5d 那句话是空的），而它**没有**被带进计划文本 ——
这条是 LWB-029 那处脱敏漏洞留下的教训，在这里成了**一开始就写对**的东西。

## 3. 步骤 3：撤销新增文件视为删除 —— V1 **不自动删除**，只输出本地方案

```
PASS §3.1 装置自检：新建真的落盘了
PASS §3.2 新建条目 ⇒ LOCAL_DELETE_REQUIRED（不是 REVERTIBLE） — LOCAL_DELETE_REQUIRED
PASS §3.3 改写条目照常可撤销（已知做不到 ≠ 不知道） — null
PASS §3.4 新建条目**不**进提案
PASS §3.5 本地方案明确写着动作、路径与哈希 — "DELETE_CREATED_FILE"
PASS §3.6 本地方案自报「与创建时一致」
PASS §3.7 本地方案的话里没有本机绝对路径
PASS §3.8 提议结果自报「需要本地动作」 — 本次撤销有 1 个文件需要你在本地处理（V1 不支持自动删除文件）：…
PASS §3.8b 但可撤销的那一条**照常**生成了提案 — 已知做不到 ≠ 不知道；不该因为有一条要人动手就整件事停住
PASS §3.9 撤销执行完 — APPLIED
PASS §3.10 可撤销的那一条真的回到了基线
PASS §3.11 新建的文件**还在**（本服务不删除文件）
PASS §3.12 新建文件的指纹一个都没变
PASS §3.13 撤销模块里不出现 `writeFileGuarded`
PASS §3.13 撤销模块里不出现 `createFileGuarded`
PASS §3.13 撤销模块里不出现 `DeleteFile`
PASS §3.13 撤销模块里不出现 `removeFileGuarded`
PASS §3.14 反向探针：它确实调用了读取（否则上面几句是空的）
PASS §3.15 反向探针：它确实调用了探路径
```

**「不自动删除」在代码里是一条写不出来的路径，不是一句承诺。**
§3.13 的四条静态探针查的是 `revert.ts` 的**去注释源码文本**
（先剥掉 `/* … */` 与 `// …` 再找，否则文件头里那些**解释**这件事的句子会把探针自己绊倒）：
它不出现 `writeFileGuarded`、不出现 `createFileGuarded`、不出现 `DeleteFile`、不出现 `removeFileGuarded`。
而 §3.14 / §3.15 是它们的**反向探针** —— 同一个探法去找 `readFileGuarded` 与 `resolveTarget`，
必须**找得到**。没有这两句，§3.13 会在「探针写错了」或「文件被改名了」的时候照样全绿。

**本地方案里最要紧的一句是它**不**说什么。** §3.5 与 §3.6 让方案带着动作名
（`DELETE_CREATED_FILE`）、路径与哈希出去；§3.8 是它对操作者说的话（逐字在上面的日志里），
其中这一段是本任务的立场：

> 但新建没有基线身份可锚，本服务因此**不声称**它一定由本次修改创建 —— 方案 §8.3：不能猜测所有同名内容都属于插件。

新建条目**没有基线**（它原本不存在），所以「这个文件就是那次创建留下的」这件事
**没有任何东西可以锚定**。因此它不进提案、不出现在「可以撤销」的清单里，
只输出一条**给人看**的方案。§3.8b 是配套的一句：不能因为有一条要人动手，
就把整件事停住 —— 可撤销的那一条照常生成提案。

## 4. 验收 (a)：后续人工修改不会被回滚覆盖

```
PASS §4.1 人改过之后 ⇒ 冲突，不是 REVERTIBLE — CONFLICT
PASS §4.2 理由点明是「第三种内容」 — THIRD_CONTENT
PASS §4.3 提议被整体拒绝（不做部分撤销） — {"code":"FILE_VERSION_CONFLICT","reason":"THIRD_CONTENT",…}
PASS §4.4 人的那次编辑：**大小 + 写入时刻 + 内容**三个都没变
PASS §4.5 盘上就是人写的那份字节
PASS §4.6 拒绝的话里没有本机绝对路径
```

**「不会被覆盖」的可核对形式是「三样都没变」**（§4.4）—— 大小、最后写入时刻、内容哈希。
只比内容的话，一次「把同样的字节再写一遍」也会通过，而那次写入已经把用户的时间戳抹掉了。
§4.5 补一句「盘上就是人写的那份字节」：§4.4 说的是没被动过，§4.5 说的是**它现在是对的**。
两句一起才排除了「没被动过，因为它早就被改坏了」。

**不做部分撤销**（§4.3）：一个文件冲突，整条提议不建立。方案 §10.2 的「没有默认部分批准」
在撤销这一侧的同一条规则 —— 一个要人处理的现场不产生一条「剩下的先办了」的修改集。

## 5. 执行日志的折叠 —— 「**最后一条**说了算」

```
PASS §5.1 真执行的日志里，**该条目**以 `item_verified` 收尾 — item_intent → item_written → item_flushed → item_verified
PASS §5.2 真执行的日志里出现过 `item_intent`
PASS §5.2b 日志里存在操作级行（无 item_id），折叠必须按条目取而不是取整条的最后一行 — item_intent → item_written → item_flushed → item_verified → write_applied
PASS §5.3 追加 skipped 之后 ⇒ 拒绝撤销（那份内容不是本次执行留下的） — CONFLICT / EXECUTION_SKIPPED
PASS §5.4 码是重新读一次那一类，理由是 EXECUTION_SKIPPED
PASS §5.5 不认识的阶段名 ⇒ 冲突（不推断它写了什么） — CONFLICT
PASS §5.6 理由说清楚是「不认识这个阶段」 — src/a.txt：日志里出现了一个本版本不认识的阶段名（item_unheard_of）；不据此推断它写了什么。
```

**这一节回答的是整个任务的地基问题：「上次应用之后是什么」从哪里来。**
答案只有执行日志一个来源。`revert.ts` 的文件头把这一条写成了正文，因为这里有一个
**看起来更自然、实际是错的**答案 —— `operation_item_results` 那张表。
它只在 `@lwb/recovery` 的 `reconcile` 里被写过，而正常路径（跑完就收场）**根本不会写它**。
照它折叠的话，撤销会在**100% 的普通情况下**拿不到回执，然后报一个听起来很合理的
「回执不完备」。这个坑在实现阶段被识别出来，代码里因此走的是 `journal.list(operationId)`。

**§5.2b 是采集时发现的一处新事实。** 真操作的日志**不是**只有条目级行：
它最后还有一条 `write_applied`，`item_id` 是 `NULL`。
因此「取整条日志的最后一行」会取到一条**不属于任何条目**的行。
折叠必须**先按 `item_id` 过滤**，再在条目自己的那些行里取 `seq` 最大的那条。
这一条是 LWB-030 的真盘装置在日志里留下的，本任务因为要读同一份日志而撞上。

**`skipped` 需要自己的裁决（§5.3 / §5.4）。**
日志说「这个条目当初被跳过了」（执行时它**已经是**批准的那份内容），
而盘上现在是**目标内容**。这时候撤销**没有资格**动手 —— 那份内容不是本次执行留下的。
理由串因此是 `EXECUTION_SKIPPED` 而不是 `THIRD_CONTENT`：
两者对操作者说的是完全不同的话（一个是「有人改过」，一个是「这一条我们当初就没动」）。

**不认识的阶段名 ⇒ 冲突，不是「没写过」（§5.5 / §5.6）。**
`default:` 那一格返回的是 `unaccounted` / `RECEIPT_INCOMPLETE`。
产品后果是：将来 `@lwb/executor` 加了新的阶段名，撤销会**停下来**，
而不是把「我不认识」读成「什么也没发生」然后去覆盖一个文件。

### 5.7 反向探针：把折叠规则逐条改坏，看哪几条会红

记录在 `docs/PROGRESS.md` 的偏离项 124，装置本身是 `.lwb-local/probe-g.py`
（改坏 → 跑 `tests/windows --grep changes-revert` → 原样还原，任何一步不干净就直接抛）。

## 6. 步骤 1 的边界：源修改集的状态必须允许撤销

```
PASS §6.1 不存在的修改集 ⇒ NOT_FOUND，且不带任何细节 — {"code":"NOT_FOUND","reason":null,"message":"没有找到该修改集。"}
PASS §6.2 那句话里不含任何路径或标识 — 没有找到该修改集。
PASS §6.3 工作区对不上 ⇒ 拒绝 — {"code":"INVALID_ARGUMENT","reason":"CHANGE_WORKSPACE_MISMATCH","message":"这条修改集属于另一个工作区，不能在本工作区撤销。"}
PASS §6.4 别人的连接 ⇒ 与「不存在」不可区分 — {"code":"NOT_FOUND","reason":null,"message":"没有找到该修改集。"}
```

**`NOT_FOUND` 是单值的（§6.1 / §6.2 / §6.4）。**
「本机有没有这个 id」与「这个 id 是不是你的」必须给出**同一个**回答，
否则错误消息本身就成了一个探测器。§6.2 把话说死到「那句话里不含任何路径或标识」。
§6.3 是反面：工作区**对得上用户身份**的那一格可以明说（`CHANGE_WORKSPACE_MISMATCH`），
因为那条信息操作者本来就有。

`REVERTIBLE_CHANGE_STATES` 只有 `['APPLIED']` 一个值，它作为 `allowed_from`
传给 `revalidateExecutionBindings`：未应用成功的那些终态
（`FAILED_NO_CHANGE` / `CONFLICT` / `ROLLED_BACK` 等）因此得到
`CHANGE_STATE_INVALID` —— 一次**具名的拒绝**，而不是逐个墓碑态各写一条分支。
（§6 没有为这一格单独取证：它走的是同一条「绑定校验」代码，而 §10 的 `NOT_RUN`
写明了这一点 —— 逐个墓碑态各跑一遍证明的是同一行代码。）

## 7. 验收 (b)：旧修改的回执不可被篡改成「未发生」

```
PASS §7.1 装置自检：那份指纹里确实有内容（不是一个空串） — 3078 字节
PASS §7.2 提议阶段：源记录**逐行逐列**不变
PASS §7.3 撤销真的执行完了 — APPLIED
PASS §7.4 撤销**执行之后**，源记录仍然逐行逐列不变
PASS §7.5 而盘上确实回到了基线（所以「不变」不是因为什么都没发生）
PASS §7.6 源修改集仍是 APPLIED，摘要未被改写 — {"state":"APPLIED","digest":"5ba0e31d…"}
PASS §7.7 撤销之后库里是**两条**修改集（新的那条 + 源那条） — 2
PASS §7.8 源记录的 `digest` 改不动（触发器挡住）
PASS §7.8 源记录的 `workspace_id` 改不动（触发器挡住）
PASS §7.8 源记录的 `root_generation` 改不动（触发器挡住）
PASS §7.8 源记录的 `created_at` 改不动（触发器挡住）
PASS §7.8b `state` 不被 SQL 冻结（它必须能流转）—— 这条是**说明**，不是缺陷 — 状态的合法性由 `assertChangeTransition` 把守
PASS §7.8c 五条「从 APPLIED 回流」的流转全被代码拒绝
PASS §7.8d 反向探针：`PENDING_APPROVAL → APPROVED` 是合法的，不该被拒
PASS §7.9 源条目改不动
PASS §7.10 执行日志删不掉
PASS §7.11 操作记录删不掉
```

**「不可篡改」在这里是三件事，逐件取证。**
§7.2 / §7.4 是**逐行逐列**的指纹（五组查询、每组都是原始 `SELECT *`，不是查几个字段：
`changesets`、`change_items`、`operations`、`operation_item_results` ⋈ 操作、`journal_entries` ⋈ 操作）
—— 因为「篡改」不只是改一个值，还包括**抹掉重来**。
§7.8 ~ §7.11 是库层的第二道：内容列被 `changesets_content_immutable` 挡住、
条目被 `change_items_immutable` 挡住、日志与操作记录各自被 `*_no_delete` 挡住。
§7.7 是它的正面证据 —— 撤销之后库里是**两条**记录，不是一条：「抹掉旧的」这条路在数据结构上不存在。

**§7.8b 是一条被降级的断言，这段经过要写清楚。**
第一版的 §7.8 断言了 `UPDATE changesets SET state = …` 会被拒 —— **它是错的**。
`changesets_content_immutable` 有意**不**守 `state`：状态必须能流转，它的规则在
`assertChangeTransition` 里，不在触发器里。把「状态的合法性由触发器保证」当成结论写进证据，
是一句关于系统的**过度声称**。改法不是删掉这一条，而是把它拆成三句：
§7.8b 说清楚**为什么** `state` 不被冻结（这是**说明**，不是缺陷）、
§7.8c 直接验代码那一侧的守卫**真的会拒**（`assertChangeTransition(['APPLIED'], to)`
对五条回流全抛）、§7.8d 是它的**反向探针**（`PENDING_APPROVAL → APPROVED` 是合法的，
不该被拒 —— 没有这一句，一个「一律拒绝」的实现也能让 §7.8c 全绿）。
§7.8c 与 §7.8d 合起来才说明挡住了什么、又**没有**挡住什么。

## 8. 验收 (c)：撤销不改变 Git 暂存区，也不执行 `reset --hard`

```
PASS §8.0 装置自检：暂存区里确实有一个文件
PASS §8.1 提议阶段之后 .git/index 逐字节不变
PASS §8.2 提议阶段之后 git status 逐字不变
PASS §8.3 撤销执行完 — APPLIED
PASS §8.4 执行之后 .git/index 仍然逐字节不变
PASS §8.5 执行之后暂存区内容逐字不变
PASS §8.5b 而工作区那一行确实变了 —— 因为撤销真的把文件改回去了（这条是**说明**，不是缺陷） — 撤销前： M src/a.txt / A  staged.txt / ；撤销后：A  staged.txt /
PASS §8.6 HEAD 没动
PASS §8.7 没有 stash 被创建
PASS §8.8 暂存区里还是那一个文件
PASS §8.9 撤销模块里不出现 `reset --hard`
PASS §8.9 撤销模块里不出现 `git clean`
PASS §8.9 撤销模块里不出现 `git checkout`
PASS §8.9 撤销模块里不出现 `git stash`
PASS §8.9 撤销模块里不出现 `child_process`
PASS §8.10 `@lwb/changes` 不依赖 git 读取器
PASS §8.11 `@lwb/changes` 不依赖执行器（依赖方向不允许）
```

**「不改变暂存区」的判据是索引文件的字节（§8.1 / §8.4），不是 `git status` 的一行文字。**
§8.2 / §8.5 是它的第二重：暂存区那一侧的**输出**逐字不变。§8.6 ~ §8.8 各自补一格
（HEAD、stash、暂存区条目数）。四条一起才排除了「暂存区恰好没变，因为别的事情把它抵消了」。

**§8.5b 是一条被降级的断言，同 §7.8b。**
第一版的 §8.5 断言了整条 `git status` 输出不变 —— **那也是错的**：撤销**真的重写了工作区的文件**，
` M src/a.txt` 那一行**本来就应该**消失。把「工作区没变」写成保证，是一句
关于系统的过度声称（而且方向相反：它掩盖了这次撤销确实生效了这一事实）。
改成：§8.3 / §8.4 / §8.5 只断言**暂存区**那一侧（索引字节 + 暂存区输出），
另立 §8.5b 把工作区**确实变了**这件事当成**说明**记下来，两条输出逐字对照。
验收 (c) 说的是「不改变 Git **暂存区**」—— 工作区正是它要改的那部分。

**§8.9 的五条静态探针查的是源码文本**：`revert.ts` 里不出现 `reset --hard` / `git clean` /
`git checkout` / `git stash` / `child_process`。第五个不是顺手加的：
没有它，前四个都可以靠「拼一个字符串再传进 shell」绕过去。
§8.10 与 §8.11 是依赖方向上的两条：`@lwb/changes` 的清单里没有 git 读取器、也没有 `@lwb/executor`
（`revert.ts` 因此只能自己写一份阶段名词表，见 §12）。

## 11. 这一轮里发现并改掉的几处

0. **`operation_item_results` 是错的回执来源**（`revert.ts` 的设计阶段 —— **真实缺陷**）。
   它只在 `@lwb/recovery` 的 `reconcile` 分支里被写，正常执行路径**不会写它**。
   照它折叠意味着撤销在**普通的、成功应用过的**修改集上拿不到任何回执，
   然后把每一格都判成「回执不完备」—— 一个看起来完全合理的错误。
   真值来源是执行日志（§5）。这一条改变的是整个模块的地基，不是一处分支。

1. **`skipped` 需要自己的裁决**（**真实缺陷**）。
   「执行时这个路径上**已经**是批准的内容，因此执行器跳过了它」与「有人事后改成了第三种内容」
   是两件不同的事，对操作者说的话也不同。原先两者都塌成 `THIRD_CONTENT`。
   拆出 `EXECUTION_SKIPPED` 之后，理由串说的是**我们的执行没碰过它**这一事实（§5.3）。

2. **日志里有操作级行，折叠必须按条目取**（**不是缺陷**，是一处此前没被记下来的事实，采集时撞出来）。
   真操作的日志以 `write_applied` 收尾，而那条的 `item_id` 是 `NULL`。
   「取整条日志的最后一行」会取到一条不属于任何条目的行。
   代码**本来就**按条目折叠（`dispositionOf` 先 `if (row.item_id !== itemId) continue;`），
   因此这一条改的不是代码而是**见证**：证据脚本 §5.2b 把这件事实断言出来 ——
   它取的是**真操作**的日志，逐条打印出 `item_intent → item_written → item_flushed →
   item_verified → write_applied`，并断言**整条**日志里存在一个 `write_` 开头的阶段名
   （`all.some(stage => stage.startsWith('write_'))`），
   而 §5.1 的断言取的是**过滤之后**的那一串、以 `item_verified` 收尾。
   两句并排读才说明白：整条日志的最后一行**不是**这个条目的最后一行。

3. **两处证据断言是过度声称**（`scripts/evidence/lwb-031.ts`，**采集时发现**）。
   §7.8 断言 `state` 被 SQL 冻结（**它是允许流转的**），§8.5 断言整条 `git status` 不变
   （**工作区本来就应该变**）。两处都不是代码缺陷，而是证据在替系统许下它没有许的承诺。
   改法是「拆成准确断言 + 一条说明 + 一条反向探针」（§7.8b/c/d、§8.5b），
   而不是删掉它们 —— 删掉之后，那两处**真正**的保证就失去了见证。

4. **G1 的第一版在为错误的理由通过**（`tests/windows/changes-revert.test.ts`，**反向探针发现**）。
   见 §5.7 末段：夹具让第二种防线（当场观测）在正确实现与变异实现下得出同一个结论。
   一条「能过、但过不出区别」的守卫测试比没有它更糟 —— 它让折叠规则看起来被守住了。

**第 0、1 处改的是代码**（两处都在 `revert.ts` 的设计阶段被拦下，都是**真实缺陷**）。
**第 2 处改的是见证** —— 代码本来就是对的，但「日志里有不属于任何条目的行」这件事
在此之前没有任何东西写着，于是它只对到今天为止。
**第 3、4 处改的是证据与测试**，两处都不是代码缺陷，而是**装置本身在为错误的理由通过**：
一处是断言替系统许下它没有许的承诺，一处是夹具分不出对错。
第 4 处之所以被发现，靠的是把折叠规则**故意改坏**再跑一遍
（`.lwb-local/probe-g.py`，四条变异全部咬住）—— 没有那一步，这条会一直绿着。
**全套测试的计数从 1485 变成 1515（+30，正是本任务新增的那个真盘文件）。**

## 12. 装置本身的一处诚实说明

`revert.ts` 里有一份**自己的**阶段名词表（`REVERT_JOURNAL_STAGES`，
值分别是 `item_intent` / `item_skipped` / `item_untouched` / `item_written` / `item_flushed` /
`item_verified` / `item_failed` / `item_restored` / `item_restore_skipped` / `item_restore_failed`），
而它的权威定义在 `@lwb/executor` 的 `ITEM_STAGE` 里。**两份字面量同时存在**，
而依赖方向不允许 `@lwb/changes` import `@lwb/executor`（§8.11 把它钉死），
因此这份重复**不可能**被编译器消掉。

它由 `tests/windows/changes-revert.test.ts` 的 **A5** 把守，而那个守卫是**逐键**比对，不是比集合：
集合相等是不够的 —— 把 `verified` 与 `failed` 的值对调，两边仍然是同一个集合，
而含义正好反过来。因此 A5 断言三件事：(1) 每个键的值逐一相等；
(2) `ITEM_STAGE` 的每个键都必须出现在 `REVERT_JOURNAL_STAGES` 里，且键数相等；
(3) 每个值都必须属于 `ALL_ITEM_STAGES`，且互不重复。
**A5 自己还有一条反向探针（G5）**：它把同一套检查在内存里重实现一遍，
确认它能咬住三种改坏方式（缺一个键、对调两个值、打错一个值）——
没有这一句，「守卫每次都通过」与「守卫根本没在检查」是同一件事。

**第二处，关于一条本文件没有报 `PASS` 的守卫。**
`revert.ts` 里有一句 `assertExpiryInapplicable()`：它现算
`EXPIRABLE_STATES.includes('APPLIED')`，为真就抛 `INTERNAL_ERROR` / `EXPIRY_NOW_APPLICABLE`。
它守的是 §1 那条关于「另一张表」的推理。**它在本文件里没有任何一条 `PASS`**，
因为它在今天的仓库里**走不到**（`APPLIED` 确实不在 `EXPIRABLE_STATES` 里），
而本文件没有为它造一个人工的真值去触发它 —— 那会是一次「把常量改成别的值再看它抛不抛」
的测试，验的是断言自己而不是这条推理。写在这里是为了说明：
**这一句没有证据，一行也没有**；它的价值在于将来那张表被改时它会响，而不在于今天被验过。
（`tests/windows/changes-revert.test.ts` 也没有覆盖它 —— 这条守卫今天只由「代码里写着」这件事本身支撑。）

一个没人能走到、却在证据里报 `PASS` 的分支，比没有这一条更糟。
