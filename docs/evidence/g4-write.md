## 1. 门禁原文，以及它今天缺的到底是什么

`docs/LWB_COMPLETE_PLAN.md` §12 的分期表：

```
| P4 写入与恢复 | 026–034 | 原生直写、不覆盖创建、幂等、故障恢复、撤销、停用 | G4：竞争与故障测试通过 |
```

**G4 的原文与 G2 的形状完全不同，这一点必须先说清楚。**

| | G2 的原文 | G3 的原文 | G4 的原文 |
| --- | --- | --- | --- |
| 文字 | 真实网页读取**且**内容出站可追踪 | 批准前工作区字节零变化 | 竞争与故障测试通过 |
| 提到网页 | **有** | 没有 | 没有 |
| 形态 | 一句关于**环境**的话 | 一句关于**性质**的话 | 一句关于**证据**的话 |

G2 的判定干脆，是因为它的原文里就写着「真实网页」四个字。G3 的判定靠的是
任务书对同一阶段的同一件事另有要求。**G4 两者都不是**：它说的是「测试通过」——
一句不可能由代码单独满足的话，因为**「通过」需要一个判定人**。

于是「未通过」在这里的理由与 G2/G3 不同，按分量排序：

1. **没有人被授权说这句话。** 「测试通过」是一条**判定**，不是一个可观测的性质。
   本仓库至今没有验收负责人（ADR-001 §6 空缺），因此这一格只能被写成
   「证据汇总与结论陈述」，任何一份写着「G4 通过」的文件都会是一次**无授权的签署**。
2. **P4 的分期还没跑完。** 门禁原文点名的是 `026–034`，而 **LWB-034（安全暂停与紧急停用）
   尚未交付**。它给这套装置引入的是**新的故障面**（暂停中、紧急停用中、两条控制路径
   与执行并发），因此今天这一组「竞争与故障测试」是一份**会过期的**证据：LWB-034 落地
   之后必须重取。把一份自己知道会过期的证据签成通过，等于把一个待办事项签成了结论。
3. **步骤 2 要求的七种故障里，有两种本机造不出确定的那一格**（磁盘满、刷盘错误），
   另有一种只做到了它的确定等价物（落在一次 `WriteFile` 之内的进程死亡）。
   三条都如实记在 `scripts/evidence/lwb-033.ts` §11，**不**用别的东西顶替。
4. **上游全悬着**：G0 未通过、G1 无判定记录、G2 未通过、G3 未通过（§4）。

### 1.1 一处**被记录下来的少数读法**

按本仓库处理边界争议的既有做法（`g2-read.md` §1.2 的偏离项 61、`g3-proposal.md` §1.1），
这里如实记下另一种读法：

> **读法 B：** G4 的原文只有「竞争与故障测试通过」七个字，没有一个字提到真实环境、
> 真实网页或真实工作区。这一组测试已经在本机真 NTFS 上跑过（LWB-033，110 PASS / 0 FAIL），
> 三条验收标准逐条有证据（§2.3）。因此 G4 应判**通过**，待办项只剩「指定验收负责人并签署」。

**本文件不采纳读法 B**，理由就是上面第 2 条：门禁原文点名的任务区间是 `026–034`，
而 LWB-034 还没交付 —— 这不是「谁被授权说这句话」的缺口，是**这一组测试本身还没写全**。
但读法 B 不是荒谬的：它成立的唯一前提是「LWB-034 不改变这组测试的覆盖面」，
而那个前提恰好是错的（暂停与紧急停用是一套新的控制面，见 LWB-032 §8 的对照）。
把它写在这里，是为了让将来翻这份文件的人看到：**这个分歧是被看见之后才搁置的，
不是被忽略掉的。**

## 2. 已证的部分：竞争与故障

两份独立的证据线，装置不同、注入的东西也不同。

### 2.1 竞争（任务书步骤 1，五格）

`tests/windows/concurrency/`，**17 例 / 3 套**（`node scripts/run-tests.mjs tests/windows/concurrency`），
加上 `scripts/evidence/lwb-033.ts` §1 ~ §6 里同样的五格，全部在真 NTFS + 真 `WinfsGuard.ps1` 上：

| 格 | 注入了什么 | 判据 |
| --- | --- | --- |
| 并行保存 | 第三方在阶段 A 之后覆盖目标（走 `writeFile`，编辑器保存那条路） | 盘上是第三方那一份，终局不是 `APPLIED` |
| 同内容换身份 | 字节一样、对象换了（`rm` + `writeFile`） | 护栏在句柄内比的是 `file_id`，不是哈希 |
| 目录交换 | 目标**之上**那一级被换成同名新目录 | 旧对象被挪走，写入没有落到新目录里的同名文件 |
| 目标创建竞争 | `CREATE_NEW` 之下同名文件已被别人建出来 | 不覆盖、不追加、护栏交回 `FILE_EXISTS` 一类拒绝 |
| 文件占用 | 真 `CreateFileW`（护栏自己的 `holdHandle`：`GENERIC_WRITE` + `FILE_SHARE_READ`）占住目标 | 阶段 A 的**两问**（身份探针与取内容）都被挡住，挡住它们的是**同一个**内核错误（`FILE_BUSY` / Win32 32） |
| 权限变化 | ACL 改成只读（`chmod 0o444`） | `PERMISSION_DENIED` / Win32 5，盘上仍是基线 |

后两格各自带一条受控对照：**基线逐字节相同**的另一个夹具、同样的注入位置、只是不注入，
必须写成 `APPLIED`（§6.5 / §6.9）。少了它，一条「被内核挡住」的结论可能只是
「这个夹具本来就写不成」。

### 2.2 故障（任务书步骤 2 的七格，五格已验、两格 NOT_RUN）

| 要求的故障 | 本机的落点 | 它凭什么是证据 |
| --- | --- | --- |
| 原生辅助进程退出 | LWB-033 §7 | 助手**真死**（`[Environment]::Exit(43)`），调用方拿到的失败来自 `#onGone` 合成的**真**进程退出（退出码在消息里），不是装置手写的一句话 |
| 短写 | LWB-033 §7 | 真 `SetEndOfFile` + 真 `WriteFile(半份)`：盘上是**真的半截**（长度 = 目标一半、字节逐位等于目标前半段） |
| 数据库忙 | LWB-033 §8 | 真文件库 + **第二个连接**的真 `BEGIN IMMEDIATE`；判据是「另一个连接此刻写不进去」这次**失败**，而不是装置的自述 |
| 服务退出 | LWB-033 §10.3（`tests/fault-injection/daemon-death.test.ts`） | **真 SIGKILL** 一个真执行者：两个停机点各一次（动笔之前 / 动笔之后），然后跑**真**启动恢复 |
| 断网 | LWB-033 §9 | 逆向：证明执行段**没有网络调用点**（36 个源码文件 + 传递闭包 + 反向探针），因此这一格没有运行时故障面 |
| 磁盘满 | **NOT_RUN** | 本机造不出可控的满卷（§11 记了理由与替代判据） |
| 刷盘错误 | **NOT_RUN** | 需要可注入失败的存储栈（管理员 + 过滤器驱动） |

**为什么这一半不空洞。** 上面每一格的判据都落在**字节、对象身份、逐条目日志与护栏调用次数**上，
而报告与状态库里的措辞只是线索。三处值得单独点名：

- **每一格都有对照组。** 「没写成」的旁边总是有一条**同样装置、同样注入位置、只是不注入**的运行
  必须写成（§6.1/§6.2 之外的反向探针、§8.11、`daemon-death` 的第三条）。少了它，
  一个「这套装置本来就写不成」的世界会让所有断言一起变绿。
- **注入自带落地自查。** `crashInWrite` 在助手竟然正常返回时抛；`killGuardHelpers` 等到
  进程表里查不到为止；`daemon-death` 等到子进程报出停机点才动手，且要求它的退出信号**是** `SIGKILL`。
- **反复执行。** 同一个故障跑三轮（§8.13 ~ §8.15），逐项比对盘、账、工作区目录 ——
  判据不是「三轮都没报 APPLIED」，而是「第 2、3 轮和第一轮长得一模一样」。累积出来的东西
  单轮看不出来，三轮看得出来。

### 2.3 三条验收标准逐条对照

| 验收原文 | 证据 |
| --- | --- |
| 未授权文件保持不变；无并发覆盖、重复追加和错误的 `APPLIED` | 每一个 rig 带两个看门文件（工作区内一个修改集从未提起过的兄弟文件 + 工作区外一个文件），每次运行前后取三项指纹逐项比对 —— 这是装置的**固定构件**，不是某条用例的断言；「错误的 `APPLIED`」由每一格的终局 + 反向探针合起来钉住 |
| 第三种状态不会自动覆盖 | §3：第三方在窗口里写下第三个版本 ⇒ 判定为 `THIRD_CONTENT` ⇒ `MANUAL`，恢复**不自动定案**，要本地恢复授权才动字节 |
| G4 未通过时 `direct_write` 永远不对真实目录启用 | `apps/daemon/src/gates.ts`：`direct_write_enabled = platform_ready && native_guard_verified && g4_concurrency_fault_passed`；`BRIDGE_GATES` 是全 `false` 的常量（注释写明「这是一处需要人去改的常量，这是刻意的」）；16 格门禁取值穷举见 `tests/unit/gate-combinations.test.ts`（6 例）。本任务的**全部**取证都在 `os.tmpdir()` 下，真实工作区一个字节都没被碰过 |

### 3.1 这一轮里发现并改掉的三处

**两处是产品里的真实缺陷**，共同点是「库这一层看不见」：单元测试全绿，
而出问题的那条路径只有把真护栏、真进程、真盘用起来之后才会走到。

1. **一句自相矛盾的回滚报告**（`packages/executor/src/apply.ts`）。
   `rolled_back` 允许带着 `untouched` 的条目（基线哈希不符、对象已经换人 —— 而这两种成因
   本身就意味着**盘上已经不是执行之前的样子了**）。原来的措辞一律说「工作区回到执行之前的样子」，
   于是同一份报告里会同时出现「独立回读看到的是…与基线不同」与「工作区回到执行之前的样子」——
   后一句把前一句刚说过的事说没了。现在按 `untouchedCount` 分成两句话。
   一份自相矛盾的报告比一句含糊的话糟得多：它把「别人改过盘」这件事从报告里说没了，
   而那正是操作者此刻最需要知道的事。
2. **把一个未知印成了已知**（`packages/executor/src/native-adapter.ts` + `recovery/service.ts`）。
   护栏失败原来被压成两句二选一：「已进入破坏性区域」/「未进入破坏性区域」。
   而 `NATIVE_GUARD_UNAVAILABLE` —— 客户端合成的「没连上护栏」——
   **一个字节的下落都没说**，它当时被印成了「已进入破坏性区域」。判据现在是三句
   （`TOUCHED` / `NOT_TOUCHED` / `UNKNOWN`，`guardVerdict`），第三句说的是
   「这个回答可能根本没到过护栏，因此它进没进破坏性区域没有被报告过」——
   它不描述磁盘，它描述**我们手上有什么证据**。三处报告 + 一处恢复日志同时改用这一句。

**一处是装置本身。**

3. **「助手还在不在」的探测器每次把自己数进去**（`tests/fault-injection/fault-rig.ts` 的
   `guardHelperPids`）。查询自己也是这个 node 进程的 pwsh 子进程，而它的命令行里就写着
   `WinfsGuard.ps1` 那半句过滤器 —— 于是每一次调用都比实际多一个 PID。
   杀伤面不止于多一个数：「助手还在不在」正是这一组用例里唯一用来证明**故障真的落地了**
   的观察。这个缺陷是 `scripts/evidence/lwb-033.ts` §7.1 撞出来的（它断言进程表里恰好一个助手，
   拿到了两个），修法是在过滤器里加 `$_.ProcessId -ne $PID`。
   三处均记在 `docs/PROGRESS.md` 的偏离项 **132–134**。
