## 0. 这一轮的证据是在什么装置上采的

三条验收标准的原文：

> 检查不存在后被别人创建的文件不会被覆盖。
> 新文件部分写入/进程退出能被识别为恢复事项。
> 不隐式创建父目录、修改 ACL 或设置执行权限。

| 段 | 装置 | 为什么非这样不可 |
| --- | --- | --- |
| §0 | 真护栏后端的**自述** | `supports_create_new=true` 是整条路的地基；`crash_atomic_replace=false` 与 `cross_file_transaction=false` 必须同时为假，否则「创建是原子的」这句话会被含糊过去 |
| §1 | 真创建 → 真回读 → **另一次**护栏调用独立再读 | 「回读一致」如果复用创建调用自己的回执，验的是「它自己说它对」 |
| §2 甲 | 三种**占位**形态：精确同名 / 大小写别名 / 一个目录 | 「绝不覆盖」要有可失败的判据；别名与目录是「只比字符串」的实现分得开的地方 |
| §2 乙 | 绕过适配器**直接**调护栏 | 适配器不去覆盖，不等于护栏不去覆盖。这一格量的是 `CREATE_NEW` 自己 |
| §2 丙 | 抢跑发生在**适配器探完之后、护栏被调用之前** | 那正是第一条验收标准问的那一段窗口 |
| §3 | 缺一级父目录 / 父路径上是一个文件 | 「不隐式建目录」要在磁盘上**反证**：拒绝之后那一级目录依然不存在 |
| §4 | 与同目录下普通方式建的文件逐项比对 ACL 与属性 | 「不动 ACL、不设执行权限」的可核对形式 |
| §5 | 中止落在阶段 A 之内 / 计划自身不符 / 创建**之后**失败 | 三种失败要走三个不同的出口，见 §5.2 与 §5.3 |

### 0.1 §4 的判据为什么是「与对照组逐项相同」

「不设置执行权限」在 NTFS 上**没有对应位** —— 那里只有只读/隐藏/系统/存档四个属性，
权限全在 ACL 里。因此这一条不能写成「检查某个位」，只能写成：

- 新对象的安全描述符**逐项等于**同目录下用普通方式建的那一个（属主 + 每一条 ACE 的主体/权限/允许拒绝/是否继承）；
- 它**不携带任何非继承的 ACE** —— 护栏若调用过 `SetSecurityInfo`，只能在这里留下痕迹；
- 工作区根的 ACL 与一个刚刚 `mkdir` 出来的目录相同（创建前后护栏都没动过它）。

若护栏设置过执行权限，它只能体现为 ACL 上多出（或改变）一条 ACE，而那会让这两份摘要不再相同。
**① 的对照组不可省**：只证「新文件的 ACL 看起来正常」的话，一个把 ACL 设成某个固定值的实现也能通过。

## 1. 正向 —— 新文件真的建出来，字节等于已批准的那一份

```
PASS ① 提交之前，那个名字在磁盘上不存在 —— 由护栏自己说的（不是脚本猜的） — 目录内容 []
PASS ② 创建交回 applied（不是 no_change、不是 conflict、不是 refused） — kind=applied
PASS 验收 2 前半：磁盘字节的 sha256 等于条目里已批准的 target_sha256 — 磁盘 116f0db9f46a7971… == 批准 116f0db9f46a7971…
PASS 字节长度与它引用的快照登记尺寸一致 — 35 字节
PASS BOM 与 CRLF 逐字节保真（不是「解码后一样」） — 35 字节，前三个 ef bb bf
PASS 父目录里只多了那一个条目，没有别的产物（临时文件、备份、锁） — ["created.txt"]
PASS 适配器止步于 APPLYING —— 终局由协调器的收尾落，写入方不自己改判终局 — change.state=APPLYING
PASS 独立回读（另一次护栏调用）：哈希仍等于已批准的那一份 — read.sha256=116f0db9f46a7971…
```

① 问的是「这个名字**刚才**空着吗」，由护栏回答而不是脚本猜。这一格的措辞必须带上「刚才」：
阶段 A 的探测**不是**权威判定，权威判定在 `CREATE_NEW` 里（见 §2 丙）。

「父目录里只多了那一个条目」这一句防的是**实现细节泄漏到磁盘上**：临时文件、`.bak`、锁文件
在一个只比哈希的判据下都能通过。目录内容是被反证的，不是被相信的。

夹具的目标字节刻意做成**带 BOM 的 UTF-8 + CRLF**：只比「解码后的字符串相等」的实现，
在这上面会写出少三个字节、换行全变的内容，而哈希对不上。

```
PASS 护栏**原始**响应里有 absolute_path，且它是本机绝对路径 — C:\Users\mj\AppData\Local\Temp\lwb-028-2…
PASS 护栏回执：readback_ok 与 flushed 同时为真，写入字节数等于交出去的字节数 — readback_ok=true flushed=true written=22
PASS 护栏回执：target_sha256 == after_sha256（护栏收到的 == 回读到的） — target=2bb0c951b06c… after=2bb0c951b06c…
PASS 护栏回执：新对象的 link_count 是 1（没有顺手造出一个硬链接） — link_count=1 file_id=006b00000009ccc3
PASS 后端的回执里没有 absolute_path（后端按白名单拼装，不整包透传） — 回执字段=["ok","relative_path","canonical_relative_path","identity_after","after_sha256","target_sha256","readback_ok","flushed","bytes_written"]
PASS 适配器交回的报告里没有任何路径字段（只有 kind） — ["kind"]
```

`create_text` 的回执**刻意与改写同形**（`target_sha256` / `readback_ok` / `flushed` /
`bytes_written` 四个字段一个不少）：验收标准在两条路上是同一句话，回执少一个字段，
调用方那一侧的判据就会退化成「没看到就当通过」。

`target_sha256` 在创建这条路上格外要紧：它**没有基线可对**，因此
「护栏收到的到底是不是我们批准的那份字节」是唯一一处把「批准的内容」与「写下去的内容」
连起来的检查。它在 `createComplaint` 里是**第一条**判据。

**`absolute_path` 那两行是脱敏的第一道**：护栏的原始响应里有它（它是绝对路径坐标系里干活的），
而后端的回执是**按白名单逐字段拼起来**的（`native/winfs/src/powershell-backend.ts` 的
`createFileGuarded`），因此这个字段根本走不到调用方。第二道是进报告时的 `sanitize`，见 §6。

## 2. 验收 1 —— 检查不存在后被别人创建的文件不会被覆盖

### 2.1 甲：三种占位形态，创建调用**一次都没发出**

```
PASS 甲之一：名字被占着 ⇒ conflict（不是 applied、不是 refused） — kind=conflict
PASS 甲之一：理由说的是「已经被占用」且点名**绝不覆盖**
PASS 甲之一：**创建调用一次都没发出**（这才是「绝不覆盖」的可核对形式） — create=0 write=0 resolve=1
PASS 甲之一：别人的字节原样
PASS 甲之一：修改集停在 VALIDATING（一个字节都没写）
```

```
PASS 甲之二：条目写 Case.txt 而盘上是 case.txt ⇒ 同样 conflict（大小写不是不同的名字）
PASS 甲之二：说明里给的是**磁盘上的拼写**，而不是条目里写的那个 — ……磁盘上的 case.txt 已经被占用……
PASS 甲之二：目录里仍然只有那一个对象（没有多出一个「新」的）
```

```
PASS 甲之三：目标位置是一个目录 ⇒ conflict，且被当作「那里已经有东西了」
PASS 甲之三：那个目录还在，没被换成文件
```

`create=0` 是这一组里**唯一**falsifiable 的那一条：只比「返回值是 conflict」的实现，
完全可以在报告 conflict 之前先发一次创建再收拾残局 —— 而收拾残局的意思就是覆盖。
计数器插在护栏边界上（Proxy 转发到**真**后端，方法与私有字段都落在正确的实例上）。

甲之二问的是**谁的名字算数**：条目里写 `Case.txt`、盘上是 `case.txt`，NTFS 认为同一个名字。
说明里给的是**磁盘上的拼写**（护栏句柄上的规范路径），不是条目里的字符串 ——
这不是措辞洁癖：给条目拼写会让人去找一个磁盘上并不存在的名字。

### 2.2 乙：护栏自己那一层

适配器不去覆盖，不等于护栏不去覆盖。这一格绕过适配器直接调 `createFileGuarded`：

```
PASS 乙：真 CREATE_NEW 撞上已有文件 ⇒ FILE_VERSION_CONFLICT，且**没有** actual_state — code=FILE_VERSION_CONFLICT actual_state=undefined
PASS 乙：护栏码是真实的 Win32 80（ERROR_FILE_EXISTS；同一张映射表里的 183 归到同一个码） — win32=80
PASS 乙：别人的字节仍然原样
```

**`actual_state` 不在，是这一格里最有信息量的一件事。** 它的含义在两条路上不同：
改写是「已越过截断线」，创建是「对象已经被创建出来了」。因此 `CREATE_NEW` 失败
⇒ 失败抛在句柄被赋值之前 ⇒ **不带** `actual_state` ⇒ 调用方据此知道「**一个对象都没被创建**」。
反过来说，凡是进到创建那段 `catch` 里的失败，都发生在创建**之后**，都要带现场。

**Win32 码实测是 80，不是 183。** 本机（Windows 11 Home China 10.0.26200）上
`CreateFileW` + `CREATE_NEW` 撞上已存在的目标返回 `ERROR_FILE_EXISTS`（80）；
183（`ERROR_ALREADY_EXISTS`）是同一张映射表里的兄弟码，两者都归 `FILE_VERSION_CONFLICT`
（`native/winfs/WinfsGuard.ps1` 的 `Convert-Win32Error`）。**可核对的是映射后的码**
（`FILE_VERSION_CONFLICT`），80/183 是实现细节 —— 这条记在这里，免得下一个人
拿 183 去写一条在本机永远不成立的断言。

### 2.3 丙：检查之后、创建之前被别人抢先

窗口的入口是 `createFileGuarded` 这一层：适配器探完磁盘、记过执行意图、走进阶段 C
之后**才**调它。抢跑者在这个钩子里写下去，位置正好落在第一条验收标准问的那一段里。

> **2026-09-26 · LWB-029 之后这一节重跑过，结论翻了案。** 下文是重跑后的逐字摘录，
> 翻案的理由与它为什么翻得对写在下面的 §2.4。**验收标准本身一个字没动**：
> 「检查不存在后被别人创建的文件不会被覆盖」在这一格里仍然成立，而且判据更硬了。

```
PASS 丙：抢跑 ⇒ 交回 rolled_back（已证明未动过，不再报成待恢复） — kind=rolled_back
PASS 丙：理由带着护栏码与 Win32 码，并明说本次执行没留下字节 — 条目「created.txt」写入失败：护栏拒绝（FILE_VERSION_CONFLICT，Win32 80）：文件已存在，CREATE_NEW 拒绝覆盖：<工作区根>\created.txt。……本次执行在这个文件上没有留下字节。
PASS 丙：账上那条终局是 `untouched`（**未动过**），不是「动过、收回来了」 — item_intent → item_untouched
PASS 丙：**抢跑者的字节一个都没被碰**（覆盖这条路真的不存在） — 25 字节「抢跑者写下的内容」
PASS 丙：修改集停在 APPLYING，**没有**被改判成 CONFLICT —— 那张转移表没动过 — change.state=APPLYING
```

**这一格证明的是「覆盖不可能发生」，而不是「我们检测到了抢先」。** 差别在于：
一个「先检查、发现不存在、再用普通覆盖写」的实现在这一格同样能报错（它甚至可能报得更早），
但它已经在磁盘上留下了自己的字节；而这里抢跑者的 25 个字节一个都没被碰。
真护栏调用仍然发生（不是被跳过的），失败来自 `CREATE_NEW` 本身 —— 判定与创建是同一次系统调用，
因此从「刚才不存在」到「真的创建」之间**没有**可以插进去的间隙。

### 2.4 丙这一格为什么从「抛」变成了「交报告」

旧行为是抛 `RECOVERY_REQUIRED`，依据是一个**错误的推理**：
「护栏没给 `actual_state` ⇒ 现场未知 ⇒ 不敢下结论」。而一次 `CREATE_NEW` 撞名失败
**永远**不带 `actual_state` —— 它失败在句柄被赋值之前。于是这一格**总是**付一次人工核验的代价，
哪怕磁盘上明明白白什么都没发生。本文件旧版的 NOTE 自己就把那次核验记成「**多余的**」。

LWB-029 把判据换成护栏的 `touched` 那一行：
**「没带 `touched`」= 「没越过破坏性区域」**，那是一条**证明**，不是未知。
于是这一格交回 `rolled_back`，理由里带着护栏码与 Win32 码，
账上那条终局是 `untouched`。代价连同它的特例一起消失了。

**而「不为这一格改状态机那张图」这条约束没有被放弃** ——
`change.state` 仍然停在 `APPLYING`，上面第 5 条断言的就是这件事：
`APPLYING → CONFLICT` 这条边**依然不存在**，因为那条边会让
「记过执行意图的执行可以报『磁盘上没有这次执行改动的字节』」变成合法，
而那句话在别的情形下就是假的。

`object_created` 这个字段名随之并入 `guard_touched`（理由见
`docs/evidence/lwb-029/summary.md` 的 §8.2）：旧名只说得清「改写」那条路，
创建那条路无截断线可越。

## 3. 验收 3 前半 —— 不隐式创建父目录

```
PASS 甲：父目录不存在 ⇒ conflict（不是 refused —— 这是磁盘那一侧的事实） — kind=conflict
PASS 甲：理由点的是**哪一级**目录，并明说不隐式创建 — ……「src/deep/new.txt」：父目录 src/deep 不存在（护栏码 NOT_FOUND）。本工程**不隐式创建父目录**……
PASS 甲：那一级目录在磁盘上**依然不存在**（拒绝没有退化成一次 mkdir） — []
PASS 甲：一个 create 都没发出，修改集停在 VALIDATING — create=0 change.state=VALIDATING
```

```
PASS 乙：父路径上是一个文件 ⇒ conflict，理由说的是「不是一个目录」 — ……父路径 src 在磁盘上不是一个目录……
PASS 乙：那个文件没被删掉、也没被改名（拒绝不是「先腾地方」）
```

**「依然不存在」是这一节的地基。** 只报「父目录不存在 ⇒ 拒绝」是不够的：
一个先 `mkdir -p` 再创建的实现也能通过那条断言，而它的副作用是把工作区里多出一串目录。
第三行查的是磁盘，不是返回值。

父路径上是一个**文件**那一格（乙）要分开说：它和甲不是同一件事。
甲是「那一级还不存在」，乙是「那一级存在但形态不对」。乙的构造里那个文件
**既没被删也没被改名** —— 「拒绝不是先腾地方」这句话在这条路上才有人验。

「父目录同样固定并验证」的另一半在护栏那一侧：阶段 C 的 `Open-GuardedChain`
逐级打开中间目录、每一级都 `Assert-HandleMatches`（规范拼写 + 非重解析点）。
本节的探测是**早失败**，不是安全边界 —— 这个区别写在 `vetCreate` 的注释里。

## 4. 验收 3 后半 —— 不动 ACL、不设执行权限

```
PASS ① 前置：文件确实建出来了 — kind=applied
PASS ① 新建文件的 ACL 与同目录下普通方式建的文件**逐项相同** — 创建 14 行 / 对照 14 行
PASS ① 新建文件没有任何**非继承**的 ACE（护栏没调用过任何 SetSecurityInfo） — 非继承 ACE=0
PASS ① 新建文件的属性与对照文件相同（没有额外的只读/隐藏/系统位） — 创建 Archive / 对照 Archive
PASS ② 工作区根的 ACL 与一个刚刚 mkdir 出来的目录相同（护栏没动过它） — 非继承 ACE=0
```

判据的形状与理由写在 §0.1。这里补一条**否定性**说明：

**这一节证明不了「ACL 一定不会被改」这种普遍命题**，它证明的是「在这一组构造下，
新对象的安全描述符与普通方式建的对象逐项相同」。差别在于覆盖面：ACL 的维度很多
（继承标志、ACE 顺序、完整性级别、属主与组的解析），逐项比对我这一台机器上的默认继承结果
不等于穷尽。真正让这条判据有意义的是它的**方向**：护栏**只**用 `CreateFileW` 创建对象、
不调用任何 `SetSecurityInfo`，因此 ACL 只能来自父目录的继承 —— 而那正是对照组量到的东西。

## 5. 负向回归

```
PASS 5a：中止落在阶段 A 之内 ⇒ 抛（协调器据此判待恢复） — code=RECOVERY_REQUIRED
PASS 5a：**没有**记下执行意图，也**没有**把文件建出来 — change.state=VALIDATING 磁盘上存在=false
PASS 5b：计划自身前后不一致 ⇒ refused（阶段 A 就定案，不惊动恢复流程）
PASS 5b：拒绝的理由说的是**哪一条**对不上，而不是一句笼统的「不支持」 — ……声明 utf-8 / bom=false / crlf，实际 utf-8-bom / bom=true / crlf。
PASS 5b：被拒的计划**没有**在磁盘上留下任何东西 — change.state=VALIDATING create=0
PASS 5c：创建之后失败 ⇒ RECOVERY_REQUIRED，且护栏那一行读成 TOUCHED（与 §2 丙 恰好相反的那一格） — verdict=TOUCHED touched=true
PASS 5c：详情里的现场是真的 —— 观测到的哈希与尺寸等于独立读取量到的那一份
PASS 5c：文案分得清这两种失败（「这个对象是本次执行创建出来的」而不是「没有留下字节」）
PASS 5c：账上把创造出来的那个对象单独记成 restore_skipped（不删用户文件，因此不许说「收回」） — item_intent → item_failed → item_restore_skipped
PASS 5c：那次创建是真的 —— 字节确实在盘上（现场不是编出来的） — 45 字节
```

### 5.1 §5a 与 §5b 与 LWB-027 是同一格的创建版

5a（中止落在阶段 A 之内）与 5b（计划自身不符 ⇒ `refused` 且不碰盘）在 LWB-027 里已经
各有一格，这里重做一遍不是复制：**创建那条路上这两格的后果不同** ——
一次被取消的创建如果记了执行意图，账上就是「字节可能已经在盘上了」，而磁盘上
**连一个对象都不存在**（改写那边至少还有一个半改的文件）。5a 因此把
「磁盘上存在=false」和状态一起断言。

### 5.2 §5c 是一格**注入**的失败，说清楚哪一半是真的

真盘上无法在「创建成功」与「刷盘完成」之间**按需打断**这一步：
`Op-CreateFileGuarded` 是一次请求内的创建→写→刷→回读，外部插不进那一段；
而「写满卷」之类的办法只能造出写入失败，不能让它**恰好**停在刷盘之前（见 §8 的 NOT_RUN）。

因此 §5c 用一层 Proxy 在**真护栏成功之后**补报一次失败。**真与假分清楚：**

| 项 | 真 / 假 |
| --- | --- |
| 对象确实被创建、字节确实在盘上 | **真**（真 `CREATE_NEW`，脚本最后一行反证了磁盘内容） |
| `observed_sha256` 那条现场 | **真**（由另一次独立 `readFileGuarded` 量出来，不是编的常数） |
| 那次「失败」本身 | **注入**（真盘上打断不了，合成一个 `Win32 0 / IO_ERROR` + `touched: true`） |

它证明的是「**适配器如实转交现场、并按 `guard_touched=true` 分类**」——
那是本任务能背的那一半。护栏那一半（`touched` **只**在创建成功之后才挂上去）
由 §2 乙 从**反面**量过：`CREATE_NEW` 失败时它确实不在。

这一格的文案也断言了**否定面**：消息里**不**含「没有留下字节」。
两种失败的区别就是恢复流程要做的判断，文案把它们混成一句会让那一步没有依据。

**`touched: true` 这个字段在 LWB-029 之后是这一格的命门，说明白为什么。**
这条注入补报的是一句「我什么都没动」，而磁盘上留着一个真的、45 字节的新对象 ——
**两者互相矛盾，而矛盾的是注入。** 在旧判据下这个矛盾被「`actual_state` 在场即视为现场未知」
糊了过去；换成 `touched` 之后它立刻显形：**不带 `touched` 的失败 = 没动过**，
于是一条这样的注入会走「证明未动过」那一支，而它旁边就摆着一个刚建出来的文件。
修法是给注入补上 `touched: true`（它模拟的本来就是「对象已经建出来了才发现出的问题」）。
**这条记在这里，因为它是「夹具可以撒谎、断言不该跟着撒谎」的一个实例。**

### 5.3 这一轮施工中被抓出来的两处自身缺陷（都记在 `docs/PROGRESS.md`）

1. **单元测试的假磁盘里，抢跑者是「追加」而不是「替换」那一格。** 一个名字在磁盘上
   只能对应一个对象，而追加会让 `find` 先撞上原来那条「不存在」的记录，
   于是「抢先建了同名文件」这件事在假盘上**根本没有发生** —— 用例因此一度是绿的假绿。
   修法是在 `beforeCreate` 里按名字 `findIndex` 后**就地替换**。
2. **占用说明的模板少了一个字。** 带路径那一支原本拼成「磁盘上的 `src/new.ts`已被占用」，
   读起来像路径的一部分。改成两句完整的话（「目标位置已经被占用」/「磁盘上的 X 已经被占用」）。
   修的是**源码**而不是断言：断言当时是对的，是模板读着不对。

## 6. 脱敏

判据刻意做成**两半**，只报后一半是没有意义的：

> **2026-09-26 · LWB-029 之后这一节重跑过，并换了对照的出口。** 下文是重跑后的逐字摘录。

```
PASS 护栏**原始**消息里确实带着本机绝对路径（脱敏不是空操作） — 文件已存在，CREATE_NEW 拒绝覆盖：C:\Users\…\Temp\lwb-028-…\redaction-raw…
PASS 丙：补上 `touched` 之后确实走了「抛」这条出口（否则本节量的是一个更松的出口） — code=RECOVERY_REQUIRED
PASS 适配器交出的那一份里**没有**本机绝对路径，根路径被替换成 <工作区根> — 条目「created.txt」写入失败：护栏拒绝（FILE_VERSION_CONFLICT，Win32 80）：文件已存在，CREATE_NEW 拒绝覆盖：<工作区根>\created.txt……
PASS 同一句护栏话在两侧都还在（脱敏换掉的是路径，不是病因）
PASS 详情里的路径字段是**相对**路径（不是把绝对路径换个键名接着放） — path=created.txt
PASS 本次采集里所有失败详情都没有本机绝对路径，也没有临时目录名
```

**两侧说的是同一句护栏话。** 上半是护栏原始响应（`文件已存在，CREATE_NEW 拒绝覆盖：<绝对路径>`），
下半是同一句经由 `guardLine` 脱敏之后的形态。

这里有一个**方法上的坑**，记下来因为它很容易被踩第二次：脱敏的那一半必须让失败发生在
**阶段 C**。阶段 A 的冲突说明是适配器自己用**相对拼写**写的，根本不经过脱敏函数 ——
拿它去证明「脱敏有效」是拿一个没有路径的字符串去比一个没有路径的字符串，那一条永远为真。
因此 §6 走的是 §2 丙 的那个装置（目标在阶段 A 看着是空的，抢跑发生在检查之后、创建之前），
而不是「让目标一开始就被占着」。

**LWB-029 之后还多了一层讲究。** §2 丙 那一格现在**不抛**了（见 §2.4），
而报告那条出口本来就有 `sanitize` —— 拿它证明脱敏有效太轻松。这一节要问的是
**最难的那条出口**：抛出去的那句话，协调器会把它的 `message` 原样写进**改动级**日志行，
而那一行不经过条目级的脱敏（**LWB-029 发现的那个真洞就在这里**，见
`docs/evidence/lwb-029/summary.md` 的 §6）。因此这一节给真护栏那条拒绝补上 `touched: true`，
让它走「动过、但创建出来的对象收不回来」那一支 —— **消息一个字没改**，
它仍然是 `WinfsGuard.ps1` 造出来的那一句，带着真的本机绝对路径。
第 2 行断言的就是「这次确实走到了那条出口上」，没有它，本节可能只是在量一个更松的出口。

第三行问的是**病因还在不在**：`sanitize` / `redactRoot` 只替换根路径，不动别的 ——
一个「把所有像路径的东西都擦掉」的过滤器会顺手擦掉真正的病因，
而这份文字的唯一用途就是告诉人病因。

`raw.log` 里那几行**故意**带着路径 —— 它们是这一格的对照物。该文件不入库（`*.log` 在 `.gitignore` 中）。
本任务不访问真实工作区（G0/G2 未通过）、**不发网络请求**、**不涉及任何凭据**，
唯一的真实副作用发生在 `%TEMP%` 下 `mkdtemp` 出来的临时工作区上，`finally` 中清理。
