## 1. 什么时候会用到它

守护进程启动时会扫一遍**上一个进程留下的未终结操作**（`QUEUED` / `VALIDATING` /
`APPLYING`），并把它们标成「待恢复」。启动日志里出现下面任意一句，就翻到对应的小节：

| 日志里的话 | 意思 | 去 |
| --- | --- | --- |
| `未终结操作 N 个` 且 `自动定案 N 个` | 全部收敛完了，不需要你做什么 | §2 |
| `留待人工 N 个` | 有现场**不是**插件留下的。**不要覆盖它** | §3 |
| `判定不成 N 个` | 连「现在是什么」都没看清（护栏或快照不可用） | §4 |
| `写能力仍关闭：N 个工作区…` | 那些工作区的写能力关着，这是**设计如此** | §5 |
| `启动日志有 N 行因含凭证被拦下` | 那是一处缺陷，请报告 | §6 |

---

## 2. 自动收敛了什么（不需要你动手）

三种情形**一个字节都不写**就能定案，因此它们自动完成：

| 现场 | 定案 | 为什么它是安全的 |
| --- | --- | --- |
| 每个条目都已经在**批准的目标内容**上 | `APPLIED`（`recovered=true`） | 无事可做。写一遍只是把同样的字节再写一次 |
| 每个条目都还在**基线**上 | `ROLLED_BACK` | 无事可做。一次都没写下去 |
| 新建的文件**还不存在** | 该条目算「原状」 | 要建的东西没建出来 |

三种都**只改账、不动盘**。定案来自**重新观测一次**，不是来自日志里的自述——
因此回执上写的是「核验到目标状态」，不是「我们写成功了」。**内容等于目标
并不总能证明是谁写的**（方案 §8.4），所以恢复回执不声称归属，也不声称时间。

> 一个工作区上有多个操作时，逐个定案。定案完的那一个会自动解除它对写槽的阻断
> （前提：导致阻断的那个操作已经终结）。

## 3. 留待人工：现场是第三种内容

**判据：** 文件存在、读得到，但内容**既不是基线也不是目标**。或者：内容对得上，
而**对象不是被批准的那一个**（被删除后重建、改名后再建 —— 也就是「身份变化」）。

**插件不会碰它。** 这不是保守，是方案 §8.4 的原文：

> 当前是第三种内容 → 保留当前文件，进入人工恢复，**不自动覆盖**。

那很可能是**你自己在崩溃之后继续写的**，而一次自动「恢复」会把你刚写的东西抹掉。

### 你要做的

1. 打开执行日志（`recovery_manual_required` 那一条）——它指名了第一个有问题的条目。
   逐条目清单在恢复记录里：**状态是 `UNKNOWN`，错误码是 `THIRD_CONTENT` 或
   身份不明的原因**（`REPLACED_OBJECT` / `OBJECT_MISSING` / `CREATED_IDENTITY_UNPROVEN` …）。
2. 决定这一条**该往哪边走**：
   - 如果你要的就是你手上这一份 → **把改动集当成作废**，什么也不用做。恢复流程
     不会再碰这个文件；下次启动扫描会重新判定，而它仍然是第三种内容，仍然留待人工。
     （它不会自己变成「已应用」——那是诚实的：谁写的没人知道。）
   - 如果你要的是**方案原本批准的目标内容** → 由**你自己**编辑成目标内容，或者
     用 `git diff` 之类的手段对照。**不要**指望插件替你写上去：那等于重放一次旧批准，
     而 §8.4 明令禁止。
   - 如果你要的是**回到改动之前** → 见 §7（收回已经写下去的那些）。
3. 处理完之后，**重启守护进程**（或等下一次启动扫描）。它会重新判定：如果现在
   全部条目都在同一侧了，这一条就会自动定案，工作区的写能力随之放开。

> **不会有事的一个保证：** 只要还有第三种内容或身份不明，`repair` 这条路径就
> 是**拒绝**的（`HAS_UNRESOLVED_ITEMS`），连恢复授权都签发不出来。你不可能
> 在「还有别的现场要处理」的时候误触发一次收场。

## 4. 判定不成：连「现在是什么」都没看清

**判据：** 护栏不可用（`NATIVE_GUARD_UNAVAILABLE`、护栏进程起不来）、读被截断、
快照取不到。**这不是「没动过」，也不是「动过」**——它是一条事实的缺席。

**插件什么都不做：** 状态原样留着，磁盘一个字节都没碰。

### 你要做的

1. **先重跑一次。** 护栏不可用常常是暂时的（PowerShell 起不来、被安全软件拦住）。
   重启守护进程，看启动恢复那一段的数字变了没有。
2. 还是判不成的话，查**为什么护栏不可用**：这条路径上唯一的原生后端是
   `PowerShellWinfsBackend`（见 `docs/compatibility.md`）。用
   `node --import tsx scripts/evidence/lwb-027.ts` 这类取证脚本单独试一次护栏。
3. 快照取不到（`取不到基线快照` / `快照对象缺失`）说明**状态库与磁盘不一致**：
   状态库里登记着一个快照，而那个对象不在快照库里了。**不要**手工补一个文件进去
   （一个内容不对的快照比没有快照更危险）。这是一次需要人工核验的故障：
   - 哪些条目受影响：恢复记录里的 `UNKNOWN` 那几条，错误码含「快照」；
   - 现场**没有被改动**，因此你手上的文件仍然是你手上的那一份。

> **不能当成新安装。** 一个打不开或对不上的状态库会让守护进程**拒绝启动**，
> 而不是清空历史重新开始（见 §6）。历史还在，这是刻意的。

## 5. 写能力关着：`recovery_required` 为真

一个工作区的写能力在两种情况下关着：

1. 它上面有操作停在**待恢复**（盘上有说不清的字节）；
2. 它的**写执行槽被阻断**（那块地不许新的执行器进来）。

这不是故障，是「有事要你处理」。处理完 §3 / §4 之后，重启一次就会放开。

**为什么关着而不是只发个警告：** 让一个新的执行器进到一块「上一个执行器的字节
下落不明」的地上，会让两份改动叠在一起，而那时连「现在是什么」都不再有单一答案。

禁用连接**不影响**你查看恢复记录 —— 记录全部来自状态库，读它不需要任何能力开关。
这是刻意的：一个「停用连接之后连记录都看不了」的恢复流程，会把人逼到
「先把连接启用起来」这条路上，而启用连接比看记录危险得多。

## 6. 状态库或快照库不完整

守护进程**默认暂停**，而且**不会**把它当成一次新安装：

| 现场 | 行为 |
| --- | --- |
| 库文件有用户表但没有迁移记录 | 拒绝打开（不认领别人的库） |
| 库文件比本版本**新** | 拒绝打开（不拿旧代码去写新结构） |
| 已应用迁移的校验和与代码里的不符 | 拒绝打开 |
| `PRAGMA` 值（WAL / `synchronous=FULL` / 外键）对不上 | 拒绝打开，报 `STORAGE_UNAVAILABLE` |
| 库文件坏了（不是 SQLite） | 拒绝打开 |

**任何一条都不会删掉或改写那个文件。** 历史留在原处，等人工处理。

### 你要做的

1. 把那个库文件**复制一份**留底（在动手之前）。
2. 用 SQLite 工具单独打开它看一眼能不能读（`sqlite3 <库文件> '.tables'`）。
3. 能读 → 说明是守护进程这一侧的判断，报告它。
4. 读不了 → 从备份恢复；**没有备份就不要重建**。重建意味着放弃全部未决恢复数据，
   而方案 §9.3 要求「未终结/恢复引用不清理」。

## 7. 收回已经写下去的那些（唯一的恢复写入）

这是整个流程里**唯一**会写用户文件的动作，因此它需要一次**本地恢复授权**。

### 前提（全部满足才做得了）

- 这个操作处在**待恢复**；
- 收场判据成立：没有第三种内容、没有身份不明，且**确实有东西要收**
  （全在基线上的话是 `NOTHING_TO_ROLL_BACK`，根本不需要授权）；
- 要收回的条目里**没有新建的文件**。本工程不删文件，护栏也没有删除操作；
  一个多余的文件是可逆的，因此宁可要求人工处理它（`CREATED_OBJECT_NOT_REMOVED`）。

### 它做什么

把**已经写到目标内容**的那些条目写回**基线字节**，一条一条来，
每写一条就独立回读一次证实它回到了基线。反向顺序与正向写入相反（最后写的先收回）。

### 它**不会**做什么

- **不会**把基线补写成目标。这个模块里不存在那条路：唯一被授权执行的动作叫
  `ROLLBACK_TO_BASELINE`（`packages/recovery/src/plan.ts` 的 `repairOf` 只产出这一个）。
- **不会**碰已经在基线上的条目（没有东西要写回去）。
- **不会**覆盖别人的改动：写回的前置条件是「对象身份 **且** 内容哈希同时成立」，
  由护栏在自己的句柄里核。

### 授权为什么是「绑死在这一次现场上」的

授权里存着一个**计划摘要**：每条观测到的对象身份、内容哈希、磁盘拼写，加上
操作绑定的卷与根。签发之后如果有人动过盘，摘要就对不上，**消费会被数据库拒绝**——
在**一次写入发生之前**就被拒绝，而不是写到一半才发现。

- 有效期 **10 分钟**（与本地批准同一个数字，`LIMITS.APPROVAL_TTL_MS`）。
- **一次性**：用过即作废。
- 判定不通过时**不消费**：一次「环境还没准备好」的尝试不该白白烧掉你的授权。
- 摘要重算两次逐字节相同，而**换一句给人读的措辞不会让它失效**——它绑的是
  可观测量，不是文案。

### 写到一半失败了怎么办

**停下，不重试。** 留下一条 `recovery_repair_failed` 日志说明写到哪一条。
现场比进来时更复杂了，因此它会停在**待恢复**等一次新的判定 ——
**回到 §1 重跑一次启动扫描**，不要手工把状态推下去。

---

## 8. 无论何时都不许做的事

- **不许**用 `git reset --hard` / `git clean` / `git checkout` / `git stash` 实现回滚。
- **不许**手工把 `operations` / `changesets` 的状态改写成一个「看起来收场了」的值。
  定案只能来自一次重新观测。
- **不许**删掉恢复记录或未决数据来「让日志干净点」（方案 §9.3）。
- **不许**为了解开一个待恢复的操作而把 `recovery_required` 硬改成假。
- **不许**把恢复授权当成一个可以提前签发、慢慢使用的东西：它是给**此刻**的现场签的。
- **不许**让模型侧看到或调用这条路径上的任何东西（`authorize` / `repair` / `sweepStartup`）。

## 9. 回退这次交付本身

LWB-030 的回退约束（任务书原文）：

> 关闭相关能力开关；保留执行日志与未决恢复数据；不得通过覆盖用户文件实现代码回滚。

落在操作上是三件事：

1. 关掉工作区的写能力开关（这本来就是默认：全部能力开关默认 `OFF`）；
2. **不要**删掉 `recovery_authorizations`、`operation_item_results`、`journal_entries`
   里任何一行 —— 它们是下次排查的唯一依据；
3. 停用恢复扫描时，**不要**用「把状态改成终局」或「把文件覆盖回基线」来收尾。
   停下就是停下。
