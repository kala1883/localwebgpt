# ADR-004：用逐工作区授权替代隐藏的全局写入门禁

状态：已决定（2026-09-28）

## 背景

旧实现把 G0、平台兼容性、原生护栏与 G4 的签署状态合并成全局开关；签署状态任一为 false，所有工作区工具就一并不可用。控制台还把每个修改集的本机批准设为写入前置条件。这使用户无法从 UI 直接判断“哪个目录、哪些工具已授权”，也让已在真 NTFS 上运行的受保护写入实现无法使用。

## 决定

1. 外部平台验收字段继续在诊断中如实展示，但不作为全局运行权限开关；它们不会自动授予工作区。
2. 本机控制台保存的逐连接、逐工作区 grant 是唯一产品级目录权限：`read` / `list` / `search` / `git_read` 控制读取范围，`propose`（控制台显示为“文件修改”）授权该工作区文本创建、编辑与修改集应用。
3. 单文件 `file_create` / `file_edit` 在一个 MCP 调用中准备并直接经受保护执行器写入；多文件工作流使用 `change_prepare` → `change_apply`。两种写入均不再等待逐次人工批准。
4. 守卫、根身份与路径验证、秘密硬拒绝、冲突检测、快照、摘要、操作唯一性、审计、恢复与紧急暂停继续生效。模型没有 Shell、工作区外访问、Git 提交/推送或文件删除能力。
5. 持久化中的一次性批准行只作为现有执行队列的摘要绑定/去重记录，actor 标记为 `workspace-grant:<id>`，不得在 UI 或工具说明中描述为“用户逐次批准”。

## 结果

- 授予“文件修改”意味着该连接可在该工作区内自动创建/编辑文本文件；用户须只选择所需目录，撤销 grant 可阻断后续操作。
- 若本地操作者登记固定 NTFS 卷根（如 `C:\`），这就是一次明确的整卷授权：该卷内所有可访问路径都处于已选工具 grant 范围；它可覆盖已有的窄目录 grant。它不会在安装或启动时自动发生。
- 整卷范围仍硬拒绝凭证文件/目录（含 `.env`、浏览器凭证与 `LocalWorkspaceBridge` 私有状态树）；目标文件夹的 Windows ACL 仍由当前用户账户决定。
- G0/兼容性/账号写能力的真实网页验收仍是独立证据缺口；代码与 NTFS 测试通过不能冒充 ChatGPT 网页验收。
- 既有设计基线和历史证据中的旧门禁描述保留为历史记录；当前操作说明以本 ADR、README 与最新进度记录为准。

## 推翻条件

若 ChatGPT 平台无法提供稳定的连接认证，或真实网页测试发现逐工作区授权不能约束该连接，则必须暂停工作区工具，而不能回退到未经验证的身份假设。
