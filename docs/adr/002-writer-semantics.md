# ADR-002：写入语义与 Windows 文件系统护栏实现方式

- 状态：**已决定，附实测证据**
- 日期：2026-09-25
- 关联任务：LWB-003、LWB-010
- 关联不变量：I05、I06、I07、I08、I09、I10
- 证据：`docs/evidence/lwb-003/winfs-handle-evidence.json`、`docs/evidence/lwb-003/summary.md`
- 可复现命令：`node --import tsx native/winfs-spike/run.ts`

> 本文中的每一个数字都来自本机真实执行，不是估算或引用。
> 未构造成功的场景显式标注为「未验证」，**没有**被写成通过。

---

## 1. 背景

方案要求把「模型提出的修改」落到本地磁盘上的真实文件，同时要求：

- 路径安全必须由**逐级句柄与文件身份**证明，不能用字符串前缀判断（§5.3，I05）；
- 重解析点（Junction / 符号链接）必须拒绝（I06）；
- 写入前必须在同一句柄内重新校验基线（I07）；
- 不安全时拒绝，而不是降级（I08）；
- 不得宣称崩溃原子性或跨文件 ACID（I09）；
- 没有护栏就不写入（I10）。

---

## 2. 决策一：写入语义是 `guarded_inplace`，不是原子替换

### 执行步骤（实现在 `native/winfs/WinfsGuard.ps1` 的 `Op-WriteFileGuarded`）

1. 逐级打开祖先目录，每级检查重解析点并用 `GetFinalPathNameByHandleW` 比对内核认定的真实路径；
2. 以 `GENERIC_READ|GENERIC_WRITE` + `FILE_SHARE_READ`（**不含** `FILE_SHARE_WRITE`）打开目标文件；
3. 拒绝重解析点与硬链接数 > 1 的文件；
4. **在同一句柄内**读取当前字节，比对 `expected_sha256`；
5. `SetFilePointerEx(0)` + `SetEndOfFile` 截断；
6. `WriteFile` 写入新内容；
7. `FlushFileBuffers`；
8. 重新定位到 0 并回读，比对目标哈希；
9. 只有回读一致时才返回 `readback_ok: true` 的回执。

### 为什么不是「写临时文件 + `ReplaceFile`」

Windows 上确有 `ReplaceFileW` / `MoveFileEx(MOVEFILE_REPLACE_EXISTING)` 这类原子替换，
它能让读者要么看到旧内容要么看到新内容。V1 不采用，理由：

1. **原子替换会改变文件的身份**（新文件的 file index 与旧文件不同），
   而方案里「撤销」「冲突判定」「基线复核」都依赖文件身份连续性；
2. **原子替换丢弃原文件的 ACL、ADS、创建时间与其它元数据**（除非显式复制）；
3. 它只对**单文件**原子，跨文件的多个编辑依然不是 ACID（见 §4）；
4. 编辑器与同步工具对「文件被替换」的感知与「文件被改写」不同，
   会产生用户可见的行为差异（例如某些工具会重新索引整个文件）。

因此 V1 选择原地改写，并把「崩溃可能留下不完整文件」**如实写进限制**，
配合恢复流程处理，而不是假装它不会发生。

## 3. 实测证据（本机 Windows 11 26200 / NTFS / Node v22.20.0 / PowerShell 7.6.6）

### 3.1 路径安全（E1）

| 场景 | 结果 |
| --- | --- |
| 正常嵌套路径 `a/b/ok.txt` | 接受 |
| **Junction** `a/junc/ok.txt`（祖先段为重解析点） | 拒绝 `LINK_UNSUPPORTED` |
| 遍历 Junction 目录本身 | 拒绝 `LINK_UNSUPPORTED` |
| **目录符号链接** `a/sym/ok.txt` | 拒绝 `LINK_UNSUPPORTED` |
| **文件符号链接**（目标文件本身是重解析点） | 拒绝 `LINK_UNSUPPORTED` |
| `../outside.txt` | 拒绝 `PATH_UNSAFE` |
| `a/../../x` | 拒绝 `PATH_UNSAFE` |
| `a/b/ok.txt:stream`（ADS） | 拒绝 `PATH_UNSAFE` |
| `a/./b/ok.txt` | 拒绝 `PATH_UNSAFE` |
| `\a\b\ok.txt`（根相对路径） | 拒绝 `PATH_UNSAFE` |

**开发过程中真实踩到的坑（保留在此以免重犯）**：
`\a\b\ok.txt` 最初被**接受**了。原因是实现先按分隔符切分再丢弃空段，
于是开头的 `\` 被吃掉，根相对路径被静默当成相对路径。
这正是方案警告过的「表面路径与实际对象不一致」。
已修正为：以分隔符开头的路径必须先拒绝，再谈切分。

**残余风险（未消除，必须承认）**：
逐级检查与最终打开之间存在 TOCTOU 窗口——检查完某一级目录后，
该目录理论上可以在我们打开最终文件之前被替换为重解析点。
本实现用「打开最终句柄后用 `GetFinalPathNameByHandleW` 比对内核认定的真实路径」
把窗口收窄到最小，但**没有**彻底消除：真正无窗口的做法需要用
`NtCreateFile` 以父目录句柄为基准逐级相对打开，当前未实现。

### 3.2 文件身份（E2）

| 观察 | 结果 |
| --- | --- |
| 重命名后 `file_id` | **不变** |
| 硬链接与原文件 `file_id` | **相同** |
| 硬链接 `link_count` | 2 |
| 删除后重建同名、同内容文件 | `file_id` **改变**（内容哈希相同） |
| 经硬链接写入 | 拒绝 `LINK_UNSUPPORTED` |

**意义**：`file_id` 能区分「同一个对象的改名」与「内容相同但对象已被替换」。
这是「写入前重新校验基线」的判别依据，也是「同名 ≠ 同一对象」的证明。
硬链接会导致写入影响工作区外的另一个名字，因此被拒绝。

### 3.3 共享模式（E3）

| 场景 | 结果 |
| --- | --- |
| A：对方以 `FILE_SHARE_READ` 持读句柄，我方请求写 | **拒绝** `FILE_BUSY`（Win32 32），文件内容未改动 |
| B：我方以 `FILE_SHARE_READ` 持读句柄，对方尝试写 | **拒绝**（Win32 32） |
| C：对方以 `share=0` 独占持有，我方读取 | **拒绝** `FILE_BUSY`（Win32 32） |
| C（旁证）：对方独占时 Node 自己的 `open()` | 被拒绝 `EBUSY` |

**意义**：只要句柄的共享模式里**不含** `FILE_SHARE_WRITE`，
持有期间其它进程就无法取得写权限。这把「读取 → 校验基线 → 写入」
这个窗口从「尽力而为」变成「有内核保证的独占」。

**但必须同时承认**：以 `FILE_SHARE_READ|FILE_SHARE_WRITE` 打开的进程
依然可以在我们持有句柄期间写入。基线哈希复核是**必需的第二道防线**，
不是冗余。

**实施过程中被这条证据纠正的一个错误结论**：
最初版本的实验中，持有句柄的外部进程把 `0x80000000` 作为字面量传给 C# 的
`uint` 参数。PowerShell 会把它解析成 Int32 的**负数**并抛出 `MethodException`；
而默认的 `Continue` 偏好设置让脚本继续执行，于是「已持有句柄」的标记文件
照样被写了出来——**句柄其实从未打开**。
结果那一轮的并发结论全是错的（表现为「对方持有句柄却挡不住我们写入」）。
现已修正为：引用 C# 中声明为 `uint` 的常量、设置 `$ErrorActionPreference='Stop'`、
并在写标记前显式校验句柄非空。
这条经历本身就是「为什么必须做真实实验而不是推理」的例证。

### 3.4 同句柄写入（E4）

| 观察 | 结果 |
| --- | --- |
| 正常写入 | `readback_ok=true`，回读哈希等于目标哈希，磁盘内容正确 |
| 写入前后 `file_id` / `volume_id` | 不变（字节数 32 → 48） |
| 缩短写入（48 → 6 字节） | 磁盘字节数确为 6，**无残留尾巴** |
| 基线哈希不符 | 拒绝 `FILE_VERSION_CONFLICT`，**文件未被改动** |
| CRLF 保真 | 字节完全一致 |
| BOM 保真 | 前 3 字节仍为 `efbbbf`，字节完全一致 |

**意义**：写入端不猜测换行与编码，完全按调用方给出的原始字节写入。
截断是真实的（不会留下旧内容的尾巴）。

### 3.5 CREATE_NEW（E5）

| 观察 | 结果 |
| --- | --- |
| 首次创建 | 成功 |
| 对同一路径再次创建 | 拒绝 `FILE_VERSION_CONFLICT`（Win32 80），**原内容保留** |
| 父目录不存在 | 拒绝 `NOT_FOUND`，**未创建任何目录** |

**意义**：「检查不存在 → 别人抢先创建 → 我们写」这个竞态不会退化成静默覆盖。

### 3.6 崩溃语义（E6）——本 ADR 最重要的一节

| 场景 | 崩溃前 | 崩溃后 |
| --- | --- | --- |
| 截断后进程立即退出（退出码 42） | 3200 字节 | **0 字节，内容完全丢失** |
| 截断 + 只写一半后进程立即退出（退出码 43） | 3200 字节 | **1600 字节**，前缀与目标一致，完整哈希不符 |

**这就是 `guarded_inplace` 的真实残余风险，是本机实测而非推测。**

进程在「截断」与「写满」之间死亡，会留下：
- 0 字节的空文件（最坏情况，原内容完全丢失），或
- 一段与目标前缀一致、但长度不足的部分文件。

**V1 的应对**：这是**恢复流程**要解决的问题，不是写入流程能承诺解决的事情。
恢复流程负责：检测上次操作未正常结束 → 从快照（内容寻址 blob）取回原字节 →
校验 → 提示本地操作者确认后重建。
**不承诺**「写入是原子的」，也不在 UI 或工具返回值里暗示这一点。

## 4. 明确不提供的保证

- ❌ **崩溃原子替换**。见 §3.6 的实测数据。
- ❌ **多文件 ACID**。方案 §9 已说明；一个修改集里的多个文件是**逐个应用**的，
  中途失败会留下「部分文件已改、部分未改」的状态。
  当前实测覆盖率：0%（本任务未构造多文件中途失败的场景）。
- ❌ **跨卷或非 NTFS 支持**。文件身份依赖 NTFS 的 file index；
  在 FAT32/exFAT 上 `GetFileInformationByHandle` 的语义不同，本实现未验证。
- ❌ **阻止同账户的恶意进程**。共享模式只在协作式进程之间有效；
  任何能调用 `CreateFile` 的同账户进程都可以用 `FILE_SHARE_READ|FILE_SHARE_WRITE` 绕过它。
- ❌ **网络文件系统 / 重定向的 shell 文件夹**。未验证。
- ❌ **长路径（> 260 字符）**。本实现使用 Win32 路径语义且未加 `\\?\` 前缀，
  本机未验证长路径行为。

## 5. 决策二：护栏后端用 PowerShell + .NET P/Invoke（过渡），而非编译型原生模块

### 事实约束

本机 **没有** Rust 工具链、**没有** MSVC C++ 工具集、**没有** Windows SDK、
**没有** .NET SDK。Visual Studio 2022 的目录存在但为空。
因此方案原本设想的编译型原生模块（Rust 或 C++）**当前无法构建**。

### 实测延迟（同一台机器，同一份助手脚本）

| 模式 | 样本 | P50 | P95 | 最小 | 最大 |
| --- | --- | --- | --- | --- | --- |
| 每次调用新起 `pwsh` 进程 | 12 | 1124.97 ms | 1235.76 ms | 1070.02 ms | 1235.76 ms |
| **常驻进程 + JSON 行协议** | 300 | **1.37 ms** | **3.92 ms** | 0.99 ms | 15.62 ms |

方案 §13 对小文件读取的目标是 **P95 ≤ 500 ms**。

**结论**：冷启动模式比目标慢约 2.5 倍，不可用；
**常驻助手满足目标，且余量很大**（P95 约 4 ms，是目标上限的 1/125）。

### 决策

- **必须**使用常驻助手单例（`getWinfsBackend()`），进程内串行化请求。
  **不接受**每次调用新起进程的退化模式。
- 后端调用的是与编译型模块**完全相同**的 Win32 API
  （`CreateFileW` / `GetFileInformationByHandle` / `GetFinalPathNameByHandleW` /
  `ReadFile` / `WriteFile` / `SetFilePointerEx` / `SetEndOfFile` / `FlushFileBuffers`），
  因此安全语义相同，不是「近似实现」。
- spike 与生产后端**共用同一份** `native/winfs/WinfsGuard.ps1` 与
  `native/winfs/src/helper-client.ts`。
  如果证据来自一份、交付的是另一份，证据就没有意义。

### 何时**必须**替换为编译型原生模块

满足任意一条即应替换，而不是继续沿用：

1. 需要消除 §3.1 的 TOCTOU 窗口（以父目录句柄为基准的相对打开需要 `NtCreateFile`，
   PowerShell 中可用但会更脆弱）；
2. 目标环境无法预装 PowerShell 7（Windows PowerShell 5.1 的 `Add-Type` 使用旧版
   Roslyn，本实现未在 5.1 上验证）；
3. 单次调用 P95 需要低于约 1 ms；
4. 需要以非 Administrator 身份部署且无法保证 `pwsh` 在 PATH 中；
5. 安全评审要求护栏进程与 daemon 之间不使用文本协议通信。

### 附加风险（PowerShell 后端特有）

- **`Add-Type` 首次编译耗时约 1 秒**：助手启动慢，因此必须常驻；
  启动失败时由 `capability()` 返回 `available=false`，写入能力保持关闭。
- **文本协议**：请求/响应经 JSON 行协议传输，大文件以 base64 承载。
  2 MiB 上限下约 2.7 MiB 的 base64 负载，实测可接受，但明显劣于共享内存。
- **PowerShell 的字面量陷阱**：见 §3.3 的记录。所有常量必须从 C# 侧引用，
  禁止在脚本里直接写十六进制字面量。

## 7. 回退方式

本决策不涉及数据迁移，回退是纯代码层面的：

1. 删除 `native/winfs/` 与 `native/winfs-spike/`；
2. 删除 `docs/evidence/lwb-003/` 与本文；
3. 从 `packages/files/`、`packages/executor/` 中移除对 `@lwb/winfs` 的引用，
   并把 `direct_write_enabled` 保持为 `false`（它本来就是默认值）；
4. 移除 `tsconfig.json` 中的 `@lwb/winfs` 路径映射。

回退后系统退化为**只读**：读取路径若已依赖护栏，需一并停用，
而不是改用普通 `fs` 读取——那会违反 I05，属于用功能换取安全假象，不允许。
