## 1. 背景

V1 要回答的问题是：**让 ChatGPT 网页端读写本地代码，同时让「越权」在结构上不可能，
而不是靠提示词或模型自觉。** 因此范围的划定方式与功能列表相反——先划出**不做什么**，
因为每一项「顺手加上」的能力都会把上面那句话变成一句愿望。

---

## 2. V1 范围（做的部分）

| 维度 | V1 范围 | 出处 |
| --- | --- | --- |
| 平台 | Windows 本地 **NTFS**，单用户 | 方案 §1、§5.1 |
| 数据源 | **磁盘上已保存的**代码/文本文件 | 方案 §5.3 |
| Git | **只读**（状态、diff、按路径读旧/新内容） | 方案 §6.4 |
| 写入 | 已有文件的修改，**本地人工批准后**执行；在**已存在的父目录**内创建新文件 | 方案 §5.4、任务书 LWB-013–018 |
| 读取 | 读取、目录列举、限定范围内的字面量搜索 | 方案 §6 |
| 接入 | ChatGPT 网页 → 原生 MCP 工具 → Secure MCP Tunnel → tunnel-client → MCP 适配器 → 认证本地 IPC → Local Daemon → 受护栏的 Windows 文件系统 | 方案 §2 |
| 编码 | UTF-8 与 UTF-8 BOM；换行 LF / CRLF / 混合（**保留**，不静默归一化） | 方案 §5.3 |

**写入语义是 `guarded_inplace`**（就句柄内截断重写），不是原子替换。
决策与实测见 `docs/adr/002-writer-semantics.md`。

## 3. V1 **不做**的部分（排除项）

每一条都对应一个具体风险。排除项不是「暂时没做」，而是**V1 通过验收的前提**：
如果实现里出现了其中任何一项的隐含需求，验收即不通过。

### 3.1 硬排除（不得出现隐含需求）

| 排除项 | 为什么 | 若被引入会怎样 |
| --- | --- | --- |
| **任意 Shell 执行** | 一旦能执行命令，之前所有路径/权限校验都可以被绕过（`cmd /c copy` 不经过 FsGuard） | I01–I10 同时失效 |
| **自动 Git 提交 / 推送** | 会改写版本历史，而历史是用户回滚的最后一道保障 | 撤销不再可能 |
| **默认全盘访问** | 「先全开，以后收紧」在实践中不会收紧 | I02 失效 |
| **写入未保存的编辑器缓冲区** | 那些字节不在磁盘上，本程序看不到也管不到；伪称能读写它们会造成静默丢改动 | I14 失效 |
| **`git reset --hard` / `git clean` / `git checkout` / `git stash` 作为撤销手段** | 会销毁用户未提交的工作，且这正是「恶意仓库提示文本」最容易诱导执行的操作 | I12 失效 |
| **用模型传入的 `approved` / `user_id` / `session_id` / `conversation_label` 授权** | 这些都是**模型可写的字符串**，把它们当证据等于让模型自批准 | I02、I06 失效 |
| **插件自身状态目录、凭证目录、审批库、快照目录可被挂载** | 挂载即可读凭证，或直接改审批状态 | I13 失效 |
| **依赖字符串前缀判定路径安全** | Junction / 短名 / 大小写别名可绕过 | I03 失效 |
| **承诺崩溃原子性或跨文件 ACID** | 做不到；承诺了就会有人依赖它 | I09、I11 失效 |

### 3.2 平台排除

UNC、网络盘、WSL 映射路径、未验证的云占位/同步目录、大小写敏感目录特例、
其它特殊文件系统直写、重解析点（Junction / 符号链接 / 硬链接）（方案 §5.1、§5.2）。
**V1 不支持，且必须在检测到时报错，而不是「尽力而为」。**

### 3.3 内容排除

硬拒绝（无论是否在工作区内）：`.env` 及其**全部变体**（含 `.env.example` 等样例，
样例在实践中经常被填真值）、私钥、凭证文件、插件自身状态目录、系统启动/浏览器凭证目录。
清单与实现见 `packages/secure-store/src/protected-paths.ts`。

**`.env.example` 不被自动豁免**（方案 §4.3、LWB-007）。
操作者可以在明确的本地策略中为**确定的样例**另设规则——但那是操作者的动作，不是默认。

### 3.4 不宣称抵抗的威胁

已控制当前 Windows 账户的任意恶意进程、管理员/内核、原始磁盘写入、不诚实的存储硬件（方案 §4.2）。
**这不是「次要威胁」，而是「本设计的前提」**：单用户本地程序无法防御同一用户下的任意代码，
把这一条写进范围是为了避免后续把「防不住」当成缺陷来补，从而引入复杂度而没有真实收益。

另有一条容易被忽略的：**「不执行 Shell」不等于「编辑代码没有风险」**——
被编辑的文件可能影响下一次构建或启动（package 脚本、CI、编辑器任务）。
因此对 package 脚本、CI 配置、编辑器任务这类文件的写入需要**额外的风险提示**，
不能与普通源码同等对待。

## 4. 默认限制（V1 初值）

方案 §9.3 的初值，逐条抄录，**可本地调整，不是平台限制**。

| 项 | 初值 |
| --- | --- |
| 可编辑文本文件原始大小 | 2 MiB |
| 单次返回正文 | 64 KiB |
| 单次读取 | 最多 400 行且遵守字节上限 |
| 目录页 | 最多 200 项 |
| 搜索页 | 最多 100 个匹配且不超过正文限制 |
| 单次搜索时间预算 | 3 秒，超时返回有界部分结果 |
| MCP 单请求 JSON | 1 MiB（含编码膨胀） |
| 修改集文件数 | 20 |
| 修改集最终文件字节总量 | 8 MiB |
| 修改集有效期 | 24 小时 |
| 本地批准有效期 | 10 分钟，执行开始时再次校验 |
| 全局读取并发 / 单工作区写并发 | 4 / 1 |
| 连接每小时出站内容预算 | 32 MiB |
| 终结操作快照保留 | 7 天起步；**未终结/恢复引用不清理** |

**性能目标是目标，不是已测结果。** 方案 §13 给出的「小文件读取 P95 500 ms、
限定模块 20 MiB 字面量检索 P95 3 s」是**初始目标**，需在指定机器上测量后才算数。
目前**未测量**（见 §7）。

上述初值取自方案表格。**夹具中的实际取值是独立设计的边界样本**，
不是照着这张表取的：

- `large/big.txt` = 2 544 000 字节，**刚超过**「可编辑文本 2 MiB（2 097 152）」的上限。
  因此它必须**可被有界读取、但不可编辑**——这正是 A23 要验证的分界。
- `edge/long-line.txt` = 9 001 字节的**单行**，验证行数限制与字节限制是两件事。
- `edge/bom-only.txt` = 3 字节（只有 BOM，无正文），是「非空但无内容」的退化输入。

## 6. 验收负责人

**当前状态：未指定。这是一个开放项，不是已完成的记录。**

任务书的验收标准要求「范围、默认限制、排除项和**验收负责人**有可审阅记录」。
前四项已由本文件记录；负责人一项**无法由实现者单方面填写**——
实现者给自己指定验收人是无效的。

需要操作者（本仓库的所有者）明确：

1. **谁是验收负责人**（可以是操作者本人，但需要显式写明，而不是默认）；
2. 该负责人是否接受 §3 的排除项与 §4 的限制初值；
3. 是否接受「A01–A28 中大部分目前无法执行」这一事实（见 §7）。

在收到明确答复之前，LWB-001 记为 **PARTIAL**，不记为 DONE。
